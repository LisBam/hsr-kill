# 技术设计：选将期间统一座次显示取值序

父任务：`10-05-character-selection-timing-and-seat-refresh`
需求见同目录 `prd.md`。

## 一、结论先行

**缺陷确认属实，且落在默认路径上**（`GameSettings.custom_character_assignment_enabled` 默认 `false`，`scripts/autoload/game_settings.gd:371`）。

**关键修正：UI 没有重算任何座次。** `match_table.gd:1981` 读的是快照字段 `player.get("seat_number")`，该字段由**权威层**填写：

```gdscript
# scripts/data/game_state.gd:191
serialized_player["seat_number"] = seat_index + 1     # ← 数组下标
```

而选将标题读的是选将服务的领袖旋转序（`character_selection_service.gd:899` + `:718-721` + `:425-429`）。**因此本缺陷属于核心/状态层，不属于表现层**，修法必须让权威层只保留一份座次真值。

> 调研同时修正了我在上一轮的一个错误假设：**本地玩家在两个序列下并不恒等**——标签序是 `c + 1`（创建序），标题序是 `((c - ℓ + n) mod n) + 1`（领袖旋转序），只有领袖的创建下标 `ℓ = 0` 时才重合。本地座次之所以看不出问题，纯粹因为本地座次标签被**永久清空**（`match_table.gd:1228-1229`、`:1997`）。该分歧还会在对局日志中显现——`match_controller.gd:4244-4246` 用 `state.players.find(player) + 1` 取座次，构成**第三个**座次来源。

## 二、根因与两套口径

| 显示位置 | 取值来源 | 序列 |
|---|---|---|
| 选将标题「你的座次为N号位」 | `CharacterSelectionService.to_dict.local_seat_number`（`:899`）→ `get_preview_seat_number`（`:718-721`）→ `_initial_seats_by_player`（`:425-429`） | **领袖旋转序** `S(c) = ((c-ℓ+n) mod n)+1` |
| 对手牌桌座次标签 | `game_state.gd:191` → `match_table.gd:1981` | **创建序** `A(c) = c+1` |
| 对局日志「武将名（X号位）」 | `match_controller.gd:4244-4246` | **创建序** |
| 本地牌桌座次标签 | 无（被 `match_table.gd:1997` 永久清空，且 `:1228-1229` 建卡时即隐藏） | — |

`game_state.gd:187`/`:189` 的注释写明该字段的本意是「MatchController 会在身份确定后把领袖旋转到数组首位」「供界面显示领袖为一号位且不依赖稳定 player_id」——**即该字段本来就该是领袖旋转后的座次，但实现取了原始下标**。这就是缺陷的根。

### 2.1 各模式在选将阶段的实际情况

| 模式（选将阶段） | `state.players` 顺序 | 标题 vs 对手标签 |
|---|---|---|
| 身份局 / 机缘乱斗，自选**关**（默认） | 创建序（直到 `:11422` 才旋转） | **不一致**（除非 ℓ=0） |
| 身份局，自选**开**，首次有效预览/确认之前 | 创建序 | **不一致** |
| 身份局，自选开，首次预览/确认之后 | 已按座次投射（`:11293`） | 一致 |
| 斗地主 | 创建时即按座次重排（`:9547-9548`） | 一致（但**显示名**与座次不符，见 §6） |
| 2v2 / 过关斩将 / 车轮战 | 创建序，且永不旋转（`leader_index == -1`） | 一致（`index+1` 本就等于其座次） |

对局开始后数组必定已是座次序，故四者全部一致——与用户描述的「开局后标签又变了」吻合。

## 三、为什么「创建序标签」是缺陷而不是契约

- **没有任何文档、注释或测试把「选将期间标签用创建序」写成预期行为**。`character_selection_service.gd:406` 只描述数组本身；`match_controller.gd:9549` 把创建序限定在「其他模式」。
- **反向证据**：`docs/游戏机制与玩法内容.md:546` 明确「首次随机身份产生首任领袖与**按该领袖旋转的一号位真实座次**，并作为按钮默认选中值」——文档已经承认领袖旋转序从「首次随机身份」起就是权威座次，也就是**在选将期间**。
- `docs/架构说明.md:35` 声称「`CharacterSelectionService` 的首次随机座次身份已进入权威 `PlayerState`」——今天只在自选路径成立，修完后才真正成立。
- **项目对斗地主已经这么做**：创建玩家后立即重排（`:9547-9548`），注释写明理由是「**保证选将快照与最终座次完全一致**」（`:9544-9545`）。身份局只是这个意图的漏网之鱼。
- `docs/游戏机制与玩法内容.md:539` 的「领袖在**身份确认后**固定为一号位」是**结果描述**而非时序禁令；它与 `:546` 只有在把「身份确认」理解为「身份确定」时才能并存。修完后需把这一时机表述补正（§8）。

## 四、选定策略：创建后立即把数组排成最终座次（策略 A）

### 4.1 改动点

在 `match_controller.gd:9498 _create_players()` 内，**斗地主重排分支之后、座次顺序快照之前**（即 `:9549` 位置）调用一次：

```gdscript
	# 斗地主重排之后，统一把玩家数组排成最终座次顺序：身份局等领袖优先模式在此按领袖旋转，
	# 与斗地主同一意图——选将快照、牌桌座次标签、对局日志与开局后的最终座次必须同源，
	# 避免选将期间同时存在「领袖旋转序」与「创建序」两套座次口径。
	# 对斗地主本调用幂等（函数内部走同一重排），对 2v2/过关斩将/车轮战无首任身份而自然不旋转。
	# 必须放在下面的座次顺序快照之前，使该快照对所有模式都记录真实的最终座次。
	_reorder_players_from_leader()
```

**为什么选这个插入点**（调研把它列为未决项，这里据代码定了）：

1. `_create_players()` **全局只有一个调用点**（`:1567`），因此放在函数内与放在 `:1568` 功能等价。
2. 该位置**与斗地主重排同处一地**，让「创建后确定座次顺序」只有一处实现与一段说明，符合项目「单一职责 + 参数与逻辑就近」的风格；若改放 `:1568`，座次排序会分裂成两处（斗地主在 `_create_players` 内、领袖旋转在 `start_match` 内），下一个读者必须同时知道两处。
3. 该位置在**座次顺序快照之前**（`:9550-9553` 的 `state.random_history["identity_distribution"].seat_player_ids`），使该快照对所有模式都记录真实座次，符合其字段本意「供回放与诊断区分『稳定ID』与『座次』」。若放在 `:1568`，该快照对身份局会记录已过期（创建序）的座次。
4. 该位置在 `character_selection.begin()`（`:1594`）**之前**，这是 §4.2 数值不变性的前提。

### 4.2 关键安全性质：座次数值完全不变（一行改动即安全的依据）

`begin()` 在**旋转之后**执行（`:1594` > `:9549`），因此服务看到的数组已经是座次序：

- `initial_leader_index`（`character_selection_service.gd` 内按 `_player_ids` 查找领袖）变为 `0`；
- 于是 `_initial_seats_by_player[i] = (i - 0 + n) % n + 1 = i + 1`。

而**同一名玩家**（创建下标 `c`，领袖创建下标 `ℓ`）在新数组中的位置正是 `p = (c - ℓ + n) % n`，所以

```
新座次(c) = p + 1 = ((c - ℓ + n) % n) + 1 = 旧座次(c)
```

**逐玩家数值完全一致。** 因此下列既有表现的数值**一个都不变**：选将标题的座次号、座次/身份按钮默认高亮、`has_unique_first_seat_identity()` 的一号位↔领袖双绑（`:336-351`）、2v2 的座次身份表、`get_preview_seat_number`/`get_initial_seat_number` 的返回值。

这条性质是本设计选择「旋转数组」而非「新增座次字段」的**决定性理由**：它让改动面从「多处同步一份新真值」收缩为「一处顺序调整 + 零数值变化」。

### 4.3 为什么不选另外两个方案

**方案 B（保留数组不旋转，把权威座次发布给界面）**：需要给 `PlayerState` 或 `GameState` 新增座次字段，并在**至少 5 个写入点**（创建、选将开始、每次预览/确认、`_reorder_players_from_leader`、存档恢复）保持与服务映射同步；`PlayerState` 是逐字段文档化并进入每份快照与权威存档的（`docs/架构说明.md:55`）。同时**仍然必须**改 `match_controller.gd:4244-4246` 否则日志继续与牌桌矛盾。结果是**在数组下标之外再materialize 第二份座次真值**——正是项目禁止的双源模式。为「一行改动能消除的问题」引入一个序列化字段与 5 个同步点，不划算。

**方案 C（UI 侧另算座次）**：明确违反 R3-3；等于把领袖旋转公式复制进 UI。**拒绝**。

**另一条近似路线（在选将开始时调用 `_apply_custom_assignment_preview()`）**：对身份局会得到同样的旋转结果，但它同时会覆写 `player.identity`（`:11285`）并清空未确认玩家的武将预览（`:11308-11309`）——同一结果、更多副作用。**不采用**。

## 六、顺带修复的同类缺陷（调研发掘，零额外代价）

**C6：斗地主选将期间「座次标签」与「悬停显示名」不符。** `_create_players` 在 `:9530` 按**创建下标**生成显示名，随后在 `:9548` 重排数组却**没有**刷新显示名；而 `_resolve_seat_display_name` 只在 `:11755` 与 `:11763` 被写，二者的可达路径都不覆盖这里。于是斗地主选将期间可能出现「座次标签显示『一』、悬停名显示『玩家3』」。

本设计的 `_reorder_players_from_leader()` 调用**自带** `_refresh_player_display_names_for_current_seats()`（斗地主分支 `:11735`；普通分支 `:11752-11755`），因此 C6 被同一次改动免费消除，符合用户「所有角色的座位」一致性的诉求。PRD 以 R3-8 收录。

## 十一、实测发现（2026-10-05 22:30，策略A的副作用实测，按评审门回写）

### 11.1 策略A的有效性已实测通过

- 新增 `tests/seat_display_source_test.tscn`：改动前 **FAIL**（`identity_during_selection seat_source_mismatch player_id=0 snapshot_seat=1 authoritative_seat=2 seed=1`），改动后 **PASS**（`SEAT_DISPLAY_SOURCE_PASS identity+doudizhu+team2v2`）。兄弟子任务 B 的面板缓存无关，本用例不依赖界面。
- `docs/游戏机制与玩法内容.md` §4.2 主张的「座次数值完全不变」**已由实测确证**：同种子对照下，修复前后每名角色的 `seat_number` 与 `identity` 逐项完全一致（见 11.3 探针输出）。

### 11.2 策略A的副作用：同种子的 AI 随机武将会变化（真实、可复现）

`_reorder_players_from_leader()` 在创建玩家后立即旋转 `state.players`，**改变了 `CharacterSelectionService` 内 `_player_ids` 的顺序**。AI 候选是**在确认时惰性生成**的（`_make_candidates`），因此 AI 补选的推进顺序改变 → `_rng` 的消耗顺序改变 → **同一种子下 AI 抽到的武将不同**。

A/B 实证（暂存/恢复 `scripts/core/match_controller.gd` 单文件）：

| 用例 | 改动前 | 改动后 |
| --- | --- | --- |
| `pre_game_customization_test` | PASS | **FAIL** |
| `pre_game_deal_gain_test` | PASS | **FAIL** |

- `tests/pre_game_customization_test.gd:1006`：`PRE_GAME_CUSTOMIZATION_FAIL round_start_choice_after_mulligan phase=choice chooser=2`（期望 `chooser_id == 0`）。
- `tests/pre_game_deal_gain_test.gd:179`：`PRE_GAME_DEAL_FAIL pending_choice_left kind=yaota_cost_target`。

**成因（探针实测，非推导）**：同种子、同身份、同座次下，唯一差异是 AI 武将：

```
leader=1 chooser=2 | id=1 seat=1 leader aisida ai=true  | id=0 seat=4 rebel xing_cunhu human
                   | id=2 seat=2 loyalist huohua ai=true | id=3 seat=3 renegade huke ai=true     ← 有改动
leader=1 chooser=0 | id=1 seat=1 leader aisida ai=true  | id=0 seat=4 rebel xing_cunhu human
                   | id=2 seat=2 loyalist huke   ai=true | id=3 seat=3 renegade bronya ai=true   ← 无改动
```

座次与身份**逐项相同**，仅 2 号位/3 号位的 AI 武将互换（`huohua`/`huke` ↔ `huke`/`bronya`）。AI 抽到带回合开始技能的武将（`huohua`）后多出一条**真实合法**的回合开始选择请求，因此「最后落定的选择请求归属」由真人变为该 AI。两条用例失败的是**固定种子下的具体轨迹**，不是功能本身。

### 11.3 影响面与三个可选处置（待用户裁决）

- 影响面：仅「固定种子 → AI 随机武将」这一映射，以及依赖它的固定种子用例（本次实测仅上述 2 条；`lan_match_flow`、`lan_custom_identity`、`lan_turn_control`、`conquest_mode`、`conquest_coop`、`wheel_duel_mode` 与其余全量用例均通过）。玩家侧不体现为缺陷：座次、身份、牌序规则与数值均未改变。
- 处置一（接受副作用，改用例）：把这两条用例对「AI 随机武将」的隐含依赖改为不敏感的判据（例如断言「等待中的选择归属是持有该回合开始技能的角色」而不是写死 `chooser_id == 0`）。
- 处置二（消除副作用，改服务）：让 `CharacterSelectionService` 的候选生成/补选推进顺序**不依赖数组顺序**（按稳定 `player_id` 排序），使 `_rng` 消耗顺序与改动前一致 —— 语义上更干净（随机结果不应依赖表现层数组顺序），但改动落在选将服务内部，需重跑兄弟子任务 A 的等待门禁用例。
- 处置三（放弃策略A，换显示方案）：不旋转数组，改为让快照座次在选将期间直接取自权威座次。**不推荐**：会使座次真值分裂成两份（违反 R3-3 与 `design.md` §4.3），且需扩展快照契约。
