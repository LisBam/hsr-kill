# 架构说明

## 总体原则

项目采用单向依赖的五层结构：静态数据层负责声明内容，状态与规则层负责权威结算，事件运行时负责嵌套、暂停和恢复，动作协议层统一外部输入，AI/网络适配层提供不同操作来源，UI 层只渲染快照并提交动作。任何界面、AI 或网络模块都不得直接改写 `GameState`。

```text
game_data 独立卡牌 / 武将 / 技能源码 + 牌堆 / 势力数据
  ↓
GameDatabase → CardInstance / PlayerState / GameState
                         ↓
PlayerAction / ChoiceResponse → MatchController → EventScheduler → CharacterSelectionService / CardRuleService / CardEffectResolver / IdentityRules
                         ↓
 RuleTimingCatalog → RuleTimingService + TriggerManager + RuleModifierPipeline + CardMovementService + 状态快照
                ↙          ↓          ↘
              UI       AICoordinator   NetworkGateway
```

## 模块职责

### 自动加载节点

- `GameSettings`：保存全局卡牌名称模式、AI 响应延迟与当前 UI 风格 ID。它不保存颜色字典或对局状态，切换后通过独立信号通知界面刷新。
- `GameDatabase`：自动扫描 `game_data/cards`、`game_data/characters` 和 `game_data/skills` 的独立 GDScript 定义，并读取 `data/decks.json` 与 `game_data/factions.json`。卡牌、武将和技能通过唯一 ID 建立元数据与源码索引，调用方获得深拷贝；目录新增文件不需要修改集中注册表。

### 内容源码层

- `CardDefinition`：单张卡牌的源码基类。具体卡牌文件同时保存静态信息、同步效果、共享上下文、目标组合校验、濒死救援、回合状态、异步恢复、延时判定、装备响应和主动动作钩子。使用次数、AI 牌值与收益方向也由卡牌元数据提供；新增卡牌不需要修改控制器、AI 白名单或集中结算器。
- `CharacterDefinition`：单名武将的源码基类。武将文件保存名称、性别、势力、体力与说明，并直接 `preload` `game_data/skills` 中的技能脚本。
- `SkillDefinition`：单个技能的源码基类。每名持有者获得独立实例；技能文件通过 `subscribe_timing` 注册带 `player/source/target/global` 关系的标准被动触发，通过 `enable` 声明 `phaseUse/chooseToUse/chooseToRespond/chooseCard` 主动入口，通过 `can_activate/activate` 实现主动技能，通过 `continue_choice/continue_response` 恢复异步步骤，通过 `append_play_phase_actions/get_activation_preview` 提供 AI 动作与只读预览，并通过 `uninstall` 清理事件订阅。`get_skill_player/get_owner_skill_player` 创建独立 `SkillPlayer` 角色操作对象，供技能使用 `who.shield`、`who.loseHp` 与 `source.damage` 语法而不直接写入状态。
- 文件名使用小写拼音，并允许数字与下划线，例如【顺手牵羊】为 `game_data/cards/shunshouqianyang.gd`，扩展变体可使用 `shunshouqianyang_2.gd`。文件名负责维护定位，规则、网络与存档仍使用稳定 `id`。

### 数据结构

- `CardInstance`：实体牌 UID、配置 ID、花色、点数、区域和所有者。
- `PlayerState`：身份、武将、武将公开状态、体力、护盾、存活状态、手牌、装备区、判定区、连环状态、回合标记和木牛“粮”。护盾是公开非负整数，初始为0且不并入体力或体力上限。
- `GameState`：玩家数组、摸牌堆、弃牌堆、处理区、当前阶段、回合数、动作序号与胜负状态；公开快照额外提供处理区实体 UID 集合，供表现层核对生命周期而不暴露可变对象。
- `PlayerAction`：统一操作结构。核心动作包括 `select_character`、`use_card`、`use_skill`、`recast_card` 和 `end_play`；装备主动动作名由对应卡牌文件动态声明，控制器不维护具体装备动作白名单。
- `VirtualCard`：逻辑牌与实体材料牌 UID 的分离描述，支持视为牌、属性和扩展存储。
- `ChoiceRequest / ChoiceResponse`：统一 use/respond/card/target/button/control/discard 选择协议；请求保存 base/active 上下文，响应只包含可序列化 ID。
- `CardMoveEvent`：实体牌移动的来源、目的、关联事件、可见者和原因记录。
- `CardPresentationEvent`：使用、展示和判定共用的只读表现事件，保存表现序号、规则事件 ID、事件名、牌快照、来源、目标以及是否接管后续弃牌移动。
- `GameState` 额外保存根事件 ID、事件历史、移牌历史、随机种子、轮数、濒死队列和终局原因；快照会裁剪非响应者的私有选择候选。

### 权威规则层

- `MatchController`：创建对局、推进阶段、执行区域移动、处理判定、护盾、伤害、失去体力、濒死、死亡、连环、奖惩和胜负。`damage` 先扣护盾后扣体力并独占伤害事件；`lose_hp` 绕过护盾与伤害事件，只在实际体力减少时与伤害共同汇入 `hp_reduced`。
- `CardRuleService`：只做距离、攻击范围、配置化次数、通用目标、区域和延时锦囊同名校验；专属目标组合回调对应卡牌文件，不执行效果。
- `CardEffectResolver`：纯卡牌源码调度器。它只保存 `host/state`，按卡牌 ID 调用 `resolve/resolve_target`，并按父牌 UID 把选择、响应和专用无懈结果交回原卡牌文件；不包含摸牌、回复、装备、群体响应或任何具体卡牌名称的效果函数。
- `CardUseEventService`：只构建 `CardUseEvent`、五组使用时机、四组动态逐目标时机、`contentBefore/content/contentAfter` 与 `orderingDiscard` 的事件拓扑；不读取 `GameState`、不执行牌效、不持有实体牌对象。
- `IdentityRules`：集中维护 2 至 10 人身份表、胜负条件和死亡奖惩类型；控制器对完整身份表洗牌，不为主公保留固定座次。
- `CharacterSelectionService`：纯数据选将状态机，集中维护主公先选、其他玩家同时选、每人随机候选、候选私密性与统一完成条件。它不加载界面、不注册 AI，也不修改卡牌区域。
- `RuleEventBus`：按优先级同步派发 `RuleEvent`。武将技能、装备扩展和模式规则可订阅事件，不需反向引用控制器。
- `RuleTimingCatalog`：无状态时机目录，集中保存220个不重复监听事件和4个主动技能入口。它不读取对局状态、不派发效果，只提供名称校验与稳定分类顺序。
- `RuleTimingService`：同步标准时机派发组件。它先调用兼容 `RuleEventBus`，再依据当前状态的存活座次把事件交给独立 `TriggerManager`，最后完成事件；它不执行任何具体牌效、伤害、移动或阶段逻辑。
- `EventScheduler`：维护根事件、事件栈、`next`/`after` 队列、步骤游标、`goto`/`redo`、多通道暂停 token、选择请求与终局中断。长期根事件通过 `held_open` 等待后续子树，不占用暂停 token，也不会阻塞新阶段或卡牌事件。事件状态区分 `finished`、`cancelled`、`neutralized` 和 `aborted`。
- `GameplayPauseService`：对局级令牌暂停组件。首个调用方申请时保存原场景树暂停状态并暂停对局，最后一个调用方释放后恢复；`MatchController` 同步持有 `EventScheduler` 全局 token，并在所有 AI 调度与动作入口查询同一状态。
- `TriggerManager`：先按 `player/source/target/global` 过滤技能持有者与 `RuleEvent` 角色关系，再按 `firstDo/lastDo`、技能优先级、起始座次和注册顺序排列触发器，并在执行前重新检查动态条件。
- `RuleModifierPipeline`：独立于触发器的纯查询修正链，供 `RuleQuery` 实现 card/target enabled、usable、respondable 和 in-range 查询。
- `RuleQuery`：只读合法性门面；不创建选择、不移动牌、不消耗次数。
- `CardMovementService`：统一维护实体牌区域和牌面知识，追加 `CardMoveEvent` 历史，并在权威移动完成后发出唯一 `card_moved` 增量；同一实体在同一区域且持有者未改变时拒绝重复移动，控制器只把进入手牌和弃牌堆的有效增量转为客户端表现，规则调用点不得重复发信号。

### 外部适配层

- `AICoordinator`：管理玩家与 AI 策略映射，把权威完整快照和合法动作交给策略选择。
- `BasicAIPolicy`：示例启发式策略。它不能修改状态，只返回可序列化动作；卡牌基础价值、目标收益方向和无懈收益方向读取卡牌元数据，不维护具体卡牌 ID 表。
- `NetworkGateway`：封装离线、局域网和远程模式的消息协议、序号与收发信号。
- `match_table.gd`：桌面协调器，只渲染本地裁剪快照、按实体 UID 对账并复用正式手牌节点、按玩家 ID 持久复用座位节点、维护出牌临时选择、读取只读规则预览并构建 `PlayerAction`；本地非摸牌获得直接驱动正式手牌节点从右侧入场，菜单布局和选将候选布局由独立组件负责。全体目标模式只显示“规则自动展开”，不把角色牌暴露为可点击目标；主题变化时只协调各表现组件重绘。
- `card_view.gd`：以 `Node2D` 为根的单张实体牌组件，只处理牌面、选中反馈和手牌入场表现偏移；`card_input_area.gd` 负责点击、悬停与拖放协议。外部容器与动画层拥有绝对位置，牌面样式刷新默认不能重置非手牌纵坐标。
- `player_target_view.gd`：以 `Node2D` 为根的全玩家共用纵版武将牌协调组件，渲染势力、竖排武将名、体力与灰色护盾、手牌数、全宽公开装备和目标反馈；圆点体力模式把护盾显示在体力上方，数字体力模式同步显示灰色护盾数字。`player_target_input_area.gd` 负责点击与卡牌拖放协议，`damage_shake_feedback.gd` 只负责体力下降后的临时位置抖动并恢复布局原位。
- `judgment_zone_view.gd`：无状态判定区表现组件，只接收牌名数组并在武将牌底边按顺序生成菱形首字标记。
- `player_state_overlay.gd`：无状态武将状态表现组件，只接收存活与横置布尔值并渲染阵亡黑白滤镜、红色文字或中心链条。
- `card_use_animation_layer.gd`：接管已经存在的正式 `CardView` 节点播放使用、展示、判定与弃牌表现；本地出牌直接移动手牌中的同一节点，纯展示与隐藏牌实例化同一正式场景。表现 ID 在节点创建前去重，真实使用牌和判定牌按实体 UID 原子取得后续弃牌转移所有权，普通弃牌首次观察到 UID 时也登记表现生命周期；所有权消费后继续保留幂等状态，重复移动增量、同区域无效移动或不同表现 ID 的迟到包都不会再次生成中央牌面。桌面只为存在真实玩家锚点的来源和目标创建玩家转移动画，座位缺失时跳过表现而不回退中央；新节点完成坐标初始化后才显示。桌面只为有玩家来源的普通弃牌或已认领的处理区牌创建表现，未认领的 `processing -> discard_pile` 收尾创建0张牌面。接管所有权的牌把中央节点实例与开始时间绑定到实体 UID，响应、选择或判定完成前不创建淡出补间，最终区域移动后才补足未完成飞行并完整停留；若最终移动通知缺失，下一份 `processing_card_uids` 快照确认实体离开处理区后执行相同收尾。只有权威实体进入非弃牌新区域时才释放旧待消费与已消费状态，下一次使用不能自行绕过旧生命周期。单一收尾生命周期 Tween 负责停留与淡出，多次出牌拥有独立目标线，中央卡牌按队列铺开，同一帧进入弃牌堆的成员由单一消费者作为完整批次同时移除。
- `match_menu.gd`：统一管理右上“菜单”、卡牌名称切换、UI 风格下拉框、AI 响应速度、重新开局与下一局人数输入；风格选项来自注册表，人数只在重开时传给控制器。组件在父场景初始化完成后提升真实 GUI 命中顺序，保证菜单面板不会被动态武将牌或选将遮罩抢占输入。
- `match_log_panel.gd`：只管理“记录”按钮与日志正文的折叠状态并发出 `expanded_changed`；日志内容仍来自规则核心的 `log_added` 信号，不读取通信模式或修改对局状态。`match_table.gd` 只在 `NetworkGateway.Mode.OFFLINE` 下通过 `MatchController` 申请 `GameplayPauseService` 令牌，收起日志或退出牌桌时释放；LAN/REMOTE 不暂停。
- `character_selection_panel.gd`：只渲染观察者可见的选将快照，以正式 `PlayerTargetView` 展示候选并提交稳定武将 ID。
- `skill_button_view.gd`：武将技能元数据展示组件，只发出技能 ID 请求；可主动发动的技能由桌面构造 `use_skill` 动作，实际条件与效果仍由对应技能文件执行。
- `artwork_loader.gd`：卡牌与武将共用的可选插画加载边界，只返回 `Texture2D` 或空值。
- `ui_style_registry.gd`：纯数据 UI 风格注册表，集中维护稳定 ID、显示名、默认风格和语义配色。当前内置 `space_mono` 与 `decade_wood`，不读取场景节点、设置控件或对局状态。
- `battle_ui_style.gd`：动态 UI 的统一样式工厂，只读取当前风格的语义色并生成圆角、描边、内容边距与阴影；组件不得重新保存主题专属颜色常量。
- `decade_battle_layout.gd`：无状态座次布局组件，只消费角色视图数组和总人数，按无名杀百分比模板写入 Control 几何信息。全屏容器自身使用 `MOUSE_FILTER_IGNORE`，输入只由动态武将牌子节点处理。
- `decade_hand_container.gd`：无状态手牌容器，只根据子节点数量、悬停索引和可视宽度计算重叠、抬升、悬停顶置与按需滚动范围，并在布局位置上叠加正式手牌节点自身的入场偏移；悬停不会改变其他手牌位置。

`assets/ui/table_ornament.svg` 是代码仓库内的矢量桌面装饰资源。它不包含输入或规则逻辑，可由后续主题资源替换；中央牌堆与阶段区域的数据仍只来自本地裁剪快照。

`MatchController.get_card_use_preview()` 是 UI 使用的只读查询边界。它返回当前卡牌是否可提交、合法候选目标、规范化目标、目标模式、规则修正后的最少/最多目标数和说明文本，不返回 `GameState`、`PlayerState` 或 `CardInstance` 对象引用。点击出牌与拖拽出牌最终仍统一构造 `PlayerAction` 并进入 `submit_action()`。

座次与手牌排版不再由 `match_table.gd` 保存像素表。桌面先把绝对座次数组旋转为“本地下家至本地上家”的相对顺序，再把动态视图交给布局组件；布局组件不认识玩家身份、卡牌效果、阶段或动作协议，因此本地座次随机化不会改变环桌行动方向。

技能栏通过 `GameDatabase.get_skill()` 读取技能元数据深拷贝。选将完成后，`MatchController` 根据武将源码直接引用的技能脚本为每名玩家创建独立实例并调用 `install()`；预留技能点击只更新界面说明，可主动技能通过 `use_skill` 动作调用自身 `can_activate/activate`。技能创建的选择上下文携带 `skill_id/skill_owner_id`，提交后会回到同一运行时实例的 `continue_choice/continue_response`；AI 动作与预览也由技能文件提供。`SkillButtonView` 与 `match_table.gd` 始终不能直接修改状态。

插画路径属于静态表现元数据，不写入 `CardInstance` 或对局快照。卡牌定义可直接提供 `art_path`；武将定义不维护该字段，`GameDatabase._load_characters()` 会根据每个武将源码文件的完整基础名，在 `res://game_data/characters/image/` 按 PNG、JPG 顺序自动发现同名资源，并只向对外武将元数据副本注入命中路径。该过程不修改 `CharacterDefinition` 源对象，也不依赖武将稳定 ID、中文显示名、技能或对局状态。

`CardView` 和全玩家共用的 `PlayerTargetView` 只把最终元数据中的 `art_path` 交给 `ArtworkLoader`，因此插画缺失不会影响规则层、AI 或网络层。同名 PNG 与 JPG 并存时选择 PNG；两种格式均缺失时不产生数据校验错误并显示占位图。本地玩家与其他玩家使用同一武将牌类和148.35×197.8像素的3:4原生场景规格，差异仅来自布局位置和快照可见性；装备横条读取141.35像素插画宽度，判定区和状态覆盖由独立无状态子组件渲染。正式卡牌统一为111×148像素的3:4规格。

## 开局与选将边界

`MatchController.start_match()` 只创建身份、空武将玩家状态和牌堆，然后把阶段设为 `character_selection`。标准身份局使用同一对局随机源先为本地人类玩家分配有效座次，再对包含主公的完整身份池洗牌，因而本地玩家、主公和一号位三者互不绑定。主公先获得候选并单独确认，控制器立即把主公武将写入 `PlayerState` 且公开；随后其他玩家各自同时确认，具体选择在所有人完成前不进入其他观察者快照。全员完成后控制器统一公开非主公武将、按武将配置初始化体力、安装每名武将直接引用的独立技能实例、每人摸4张起始手牌，并直接查找唯一主公开始首回合；预留的 `first_turn_seat_number` 不参与标准身份局顺序判定。只有对局人数不少于5人时，主公才在武将基础体力上限上增加1点。

`CardRuleService.normalize_targets()` 是多目标的统一权威顺序入口。群体目标牌从使用者开始按环形行动顺序展开：`all_players` 先结算使用者本人，`all_others` 先结算使用者的下一名存活角色；方天画戟和铁索连环等手动多目标牌也在提交后按相同行动顺序重排，只有【借刀杀人】保留“持刀者、被杀者”的双目标语义顺序。【无懈可击】每轮把全部存活玩家加入同一公开响应名单，并为当前确有合法候选的玩家分别登记私有 `ChoiceRequest`；请求彼此并行，首个到达权威端且通过实体牌复核的响应取得本轮结算权，同轮其他请求立即以系统放弃关闭。成功响应后重新开启下一轮，直到完整一轮无人响应。公开 `simultaneous_response_display.responder_ids` 始终包含全部存活玩家，不携带候选数量；连环传导与濒死救援仍从当前回合角色开始按存活座次进行，若一名濒死响应者回复后目标仍未脱离濒死，下一轮从该响应者重新开始。

死亡结算先标记死亡并亮出身份，然后立即调用 `IdentityRules.evaluate_winner()`。若已满足胜负条件，`GameState.game_over` 会成为规则操作与 `CardEffectResolver` 的统一终止条件：当前死亡弃牌、奖惩、群体牌后续目标、响应、伤害、回复、摸牌及使用牌结束区域移动全部停止。若对局继续，则清理死者区域并执行击杀奖惩。当前回合角色在自己行为的插入结算中死亡时，当前事件完整结算后直接从其下名存活角色开始新回合；若死于开始阶段事件或判定阶段，则由 `_start_turn()` 在该阶段结算返回后执行同一转交，不会停留在死亡角色的回合。

候选数量由 `MatchController.character_candidate_count` 前置配置，默认 5，实际不超过已登记武将数量。人类、AI 和网络玩家都提交 `select_character` 标准动作；任何适配层都不能直接写 `character_id`、`character_revealed`、`hp` 或 `max_hp`。

选将完成后玩家数组从主公旋转，使主公成为一号位，并按旋转后的数组索引刷新“玩家1”“玩家2”“玩家3”等显示名；稳定 `player_id` 始终不变，继续用于网络、回放和实体所有权。

## 触发事件

标准技能时机由 `RuleTimingCatalog` 统一维护，共220个名称，覆盖游戏与阶段、使用牌与响应、伤害、体力与生死、牌移动、判定与拼点、选择、技能自身及武将模式规则。核心通过 `MatchController._emit_rule_timing()` 创建包含 `player_id/source_id/target_id/data` 的 `RuleEvent`，由 `RuleTimingService` 统一派发并记录历史。完整名称与制作语义以《内容制作指南》的“无名杀220时机系统”为准，架构文档不维护第二份易漂移清单。

阶段、伤害、用牌与移动组件只负责在自己的真实边界调用统一派发端口：阶段使用成功进入 Begin 的生命周期集合防止取消或跳过后伪造 End/After；伤害在濒死选择期间把 `damageSource/End/After` 保存在待收尾上下文；使用牌由 `CardUseEventService` 维护五组整牌时机和四组动态目标时机；区域移动由控制器语义端口在 `CardMovementService.move_card()` 前后派发复合生命周期。目录和服务均不反向调用这些业务组件，因此不会形成“时机服务执行牌效”的胖模块。

以下蛇形命名事件继续作为迁移期兼容层：

- `phase_start`：回合开始阶段。
- `phase_finish`：回合结束阶段。
- `card_used`：实体牌进入处理区并声明目标后。
- `damage_before`：伤害扣减前，可修改 `amount` 或取消。
- `damage_after`：护盾与体力扣减后、濒死结算前；即使护盾完整吸收伤害也会触发，并公开 `shield_absorbed` 与 `hp_lost`。
- `lose_hp_before` / `lose_hp_after`：独立失去体力流程，绕过全部伤害事件与伤害历史。
- `hp_reduced`：体力实际减少后的统一事件，通过 `reduction_type` 区分伤害与失去体力；护盾完整吸收时不触发。
- `shield_after`：角色实际获得护盾后触发，包含来源、实际增加量和累计护盾。
- `recover_after`：实际回复完成后。
- `dying_begin`：角色进入濒死流程时。
- `dying_end`：角色回复至1点体力或以上并完成求桃流程结算时；上下文包含最终体力和救援成功标志。

旧兼容技能可继续通过 `RuleEventBus.subscribe(event_name, owner, callback, priority)` 注册；新标准技能使用 `SkillDefinition.subscribe_timing()`，由基类绑定技能持有者 ID 和四角色关系。组件卸载时基类会同时清理普通总线与独立 `TriggerManager` 订阅。

## 状态可见性

`GameState.to_dict(viewer_id, reveal_private)` 是唯一快照入口：

- 本人可见自己的身份、手牌与木牛“粮”。
- 本人可见自己已经确认的武将；主公确认后立即对所有人可见，其他玩家在全员完成选将后同时公开。
- 他人只看到手牌数量和“粮”数量。
- 装备区、判定区、体力、护盾、存活与连环状态始终公开。
- 处理区实体 UID 始终公开，但快照不额外暴露非公开牌面；UI 仅用该集合核对中央表现是否仍属于活动处理区生命周期。
- `reveal_private=true` 仅供权威 AI、服务器调试与回放使用。

## 设计边界

工程不实现国战身份、势力明置、双将、暗将和国战专属牌。样例武将技能当前只提供数据接口，不批量实现角色库。所有后续扩展应新增配置或独立组件，避免把角色 ID、UI 节点或网络模式硬编码进规则服务。

## 事件运行时边界

`EventScheduler` 是所有可暂停规则流程的唯一运行入口。事件内容步骤接收 `(GameEvent, EventScheduler)`，通过 `create_child()` 插入主体子事件，通过 `create_event(..., queue="after")` 插入收尾事件；父事件在子事件和暂停 token 全部完成前不会推进步骤。长期 `RootGameEvent` 使用 `held_open=true` 留在栈底，空闲状态为 `waiting_children`，不会把生命周期等待误当作暂停。`finish()`、`cancel()`、`neutralize()` 和 `abort()` 具有不同的回放与触发语义，不能用单个 `cancelled` 布尔值替代。

`ChoiceRequest` 的请求 ID、事件 ID、响应者、候选 UID、选择数量和 `base_context/active_context` 由权威端保存。技能临时替换选择上下文必须使用 `backup_context()`，取消或 AI 失败时使用 `restore_context()`；UI、AI、网络都提交 `ChoiceResponse`，迟到或跨事件响应会被拒绝。现有 `PlayerAction.choose_cards` 是桌面兼容封装，控制器会在边界转换成同一 `ChoiceResponse`。

`CardMovementService` 是迁移期的唯一实体牌移动入口。新代码必须传递 `event_id`、`reason` 和 `visible_to`，不得直接写入牌的 `zone/owner_id` 或同时修改多个区域数组。尚未迁移的旧规则操作只允许通过控制器兼容函数调用，并应在后续版本移除。

`CardUseEvent` 已是可暂停的真实调度栈父事件。实体材料先在 `lose` 子事件进入 `processing`，随后依次执行 `useCard0/useCard1/yingbian/useCard2/useCard`。四组目标时机采用“阶段优先、每次执行后重新读取目标数组”的 `redo` 循环：全部当前目标完成 `useCardToPlayer` 后才进入 `useCardToTarget`、`useCardToPlayered` 和 `useCardToTargeted`；每轮按当前行动座次生成遍历副本，并按目标出现次数判断是否已经触发，因此动态新增目标会补齐当前及后续时机。死亡、离场或 `excluded` 目标不会进入虚假 `content`。`directHit`、`excluded` 和 `customArgs` 保存在父事件共享上下文，直击同时限制【闪】和【无懈可击】响应。每个实际目标拥有独立 `content` 子事件，响应与装备选择直接挂在该事件下；全部同步效果和暂停 token 完成后只创建1次 `contentAfter`。默认弃置通过 `CardUseEvent.after -> orderingDiscard -> cardsDiscard` 移出处理区，终局中断时不会提前回收。判定继续使用 `judge -> judgeResult -> cardsDiscard` 关系，判定牌先从牌堆进入 `processing` 并公开表现，再进入弃牌堆。

当前状态：当前标准身份局已登记卡牌的使用生命周期、逐目标效果、响应选择与处理区回收已经进入真实事件树；选择请求、暂停 token、触发排序、查询修正、虚拟牌和移牌历史均可关联稳定父事件。宏观六阶段主体、伤害、濒死、死亡与部分判定流程仍包含同步兼容段；样例武将技能没有规则实现，真实房间联机与回放执行器也未提供。因此“当前标准卡牌使用流程完成事件化”不等于“无名杀全部模式、武将和扩展包已完整复刻”。
