# 架构说明

## 终局统计与结算表现边界

- `PlayerState` 保存并序列化 `total_damage_dealt`、`total_damage_received`、`total_healing_done`、`total_cards_drawn`、`total_kill_count`。计数由 `MatchController` 的 `damage()`、`recover()`、`draw()` 与死亡分支在权威规则结算时更新；UI、AI和网络客户端均不自行从日志、体力差或牌区差推算。
- `GameSettlementPanel` 是独立的快照表现组件：输入为 `GameState.to_dict()` 中的 `players` 数组，输出为纯列表节点；不依赖模式、卡牌或技能实现。角色单元格只从公开 `character_id/display_name` 解析同一行“武将名（玩家名）”，武将资料缺失时回退玩家名。面板只保留右上角1个关闭按钮。`match_table.gd` 仅负责首个终局快照的自动打开、关闭后的抑制标记、终局按钮重开和主题刷新；其主菜单导航边界统一关闭结算面板并清空自动展示标记，局域网会话结束与主菜单可见性同步也复用该入口，防止高层模态残留。
- `MatchController.start_match(seed=0)` 统一调用 `_resolve_match_seed()`：自动路径混合Unix系统微秒、进程内单调微秒、进程号与控制器私有自增序号，使菜单重进、局内连续重开和完整退出重启都取得新的随机源；最终实际种子写入 `GameState.random_seed` 与身份启动事件。显式种子路径不混入自动分量但同样写入唯一随机源，继续支持确定性测试与回放。离线自动斗地主在玩家与身份都完成正常随机后，以控制器私有的上一局本地“座次索引+身份ID”作为防重复键；只有新结果完全相同时才从其他合法座次中按同一随机源改选，显式种子、固定座次和局域网映射不受影响。斗地主身份洗牌后不调用领袖座次旋转，首回合由地主身份单独查询。

## 总体原则

项目采用单向依赖的五层结构：静态数据层负责声明内容，状态与规则层负责权威结算，事件运行时负责嵌套、暂停和恢复，动作协议层统一外部输入，AI/网络适配层提供不同操作来源，UI 层只渲染快照并提交动作。任何界面、AI 或网络模块都不得直接改写 `GameState`。

```text
game_data 独立卡牌 / 武将 / 技能源码 + 牌堆 / 势力数据
  ↓
GameDatabase → CardInstance / PlayerState / GameState
                         ↓
PlayerAction / ChoiceResponse → MatchController → EventScheduler → CharacterSelectionService / CardRuleService / CardEffectResolver / IdentityRules
                         ↓
 RuleTimingCatalog → RuleTimingService + TriggerManager + RuleModifierPipeline + CardMovementService + 状态快照
                ↙          ↓          ↘
              UI       AICoordinator   NetworkGateway

OpportunityCatalog → OpportunitySystem → OpportunityEffectResolver → MatchController公开规则端口
```

## 模块职责

- 选将与目标顺序补充：`CharacterSelectionService` 的首次随机座次身份已进入权威 `PlayerState`；控制器在自选预览或每名玩家确认时即时投射完整座次身份，并且每名确认者的武将只应用一次，完成阶段不再重置已显示武将。`CardRuleService.normalize_targets()` 是普通多目标牌与虚拟牌的唯一顺时针规范化入口，只有拥有明确角色顺序语义的【借刀杀人】可保留请求顺序。

### 自动加载节点

- `GameSettings`：在 `user://game_settings.cfg`（格式版本1）持久化全局卡牌名称模式、均为0.10至1.00秒且步长0.05秒的游戏流程间隔与 AI 响应延迟、当前 UI 风格 ID、默认开启的自动身份标记、下一局人数（身份2–10/斗地3或5/2v2固定4/过关斩将玩家数2–4）、六项房主开局规则、过关斩将难度与机缘选择方式（`conquest_opportunity_choice_mode`，稳定值 `vote` 投票选择或 `individual` 各自选择，默认投票），以及最长20字符的联机玩家名称和稳定武将形象 ID。速度设置直接按0.05秒取整，使0.10至1.00秒范围内的每个档位都可写入。手气卡数量只接受 `0/1/2/3/4/5/10/-1`，其中`-1`表示无限张；换将卡数量只接受 `0/3/5/8/10/20`，随机选将牌数限制为1至20。设置变化先更新内存，文件写入使用0.25秒单次计时器合并；应用进入后台或节点退出时强制刷新。卡牌名称与UI风格的重绘信号延迟到GUI输入结束后的空闲帧。它不保存颜色字典、身份推断、网络对等体、地址、密码、房间成员或对局状态。
- `GameDatabase`：自动扫描 `game_data/cards`、`game_data/characters` 和 `game_data/skills` 的独立 GDScript 定义，并读取 `data/decks.json` 与 `game_data/factions.json`。编辑器目录中的`.gd`与导出PCK中的`.gd.remap`、`.gdc`、`.gde`都会规范化为原始`.gd`资源路径，因此Android导出后仍能登记完整卡牌、技能和武将。卡牌、武将和技能通过唯一 ID 建立元数据与源码索引，调用方获得深拷贝；目录新增文件不需要修改集中注册表。卡牌加载时额外建立原版名/项目名到定义的只读索引；`resolve_card_names_in_text()` 逐段扫描完整 `【】`，允许括号内文本精确匹配已登记牌的 `original_name` 或 `custom_name`，并直接映射为当前模式名称，普通文本与未登记括号内容保持原样。完整说明按名称模式缓存，每种模式最多512条，数据库重载时统一清空；`resolve_character_name()` 只返回不可变字符串，直接读取内部武将索引而不复制整份元数据。

### 内容源码层

- `CardDefinition`：单张卡牌的源码基类。具体卡牌文件同时保存静态信息、同步效果、共享上下文、目标组合校验、濒死救援、回合状态、异步恢复、延时判定、装备响应和主动动作钩子。`uses_immediate_equipment_response_prompt()/get_immediate_equipment_response_prompt()` 允许装备在普通响应候选前建立独立询问；`modify_ai_negation_effect_utility()` 允许复杂锦囊按来源、目标和团队后果修正无懈效用。使用次数、AI 牌值与收益方向也由卡牌元数据提供；新增卡牌不需要修改控制器、AI 白名单或集中结算器。
- `CharacterDefinition`：单名武将的源码基类。武将文件保存名称、性别、势力、体力与说明，并直接 `preload` `game_data/skills` 中的技能脚本。
- `SkillDefinition`：单个技能的源码基类。每名持有者获得独立实例；技能文件通过 `subscribe_timing` 注册带 `player/source/target/global` 关系的标准被动触发，基类会把内容条件与持有者有效性条件组合，普通技能在持有者死亡、离场或状态缺失后不再接收新时机。`out_of_game_skill=true` 明确声明离场技：持有者存活但离场时仍可接收时机、完成该技能自身的强制选择并参与纯查询修正，死亡后仍失效；一般临时离场恢复仍可覆盖 `can_trigger_while_owner_inactive(event)`。每个实例还拥有默认0.0的非负浮点 `sell_blood_value`，1.0点按1张牌的统一资源价值修正友方或敌方造成伤害的AI收益，当前【百折】为1.0。技能通过 `enable` 声明 `phaseUse/chooseToUse/chooseToRespond/chooseCard` 主动入口，通过 `can_activate/activate` 实现主动技能，通过 `continue_choice/continue_selection/continue_response/continue_extra_phase` 恢复异步步骤与额外阶段。基类提供只选牌、只选目标、目标加文字选项、牌与目标组合等统一请求包装，并通过 `append_play_phase_actions/get_activation_preview` 提供 AI 动作与只读预览；`modify_ai_incoming_card_effect()` 允许目标技能以纯查询方式修正受到来牌后的预期结局。`can_convert_response_card/get_converted_response_definition_id` 允许技能把当前拥有的实体材料转化为合法响应。主动单材料转化可复用 `get_owned_conversion_material_card()`、`build_virtual_rule_overrides()`、`validate_virtual_use_for_material()` 与 `build_virtual_target_selection_data()`，让真实材料颜色统一进入玩家候选、AI枚举和提交校验。`get_skill_player/get_owner_skill_player` 创建独立 `SkillPlayer` 角色操作对象，供技能使用 `who.shield`、`who.loseShield`、`who.loseHp` 与 `source.damage` 语法而不直接写入状态。
- 文件名使用小写拼音，并允许数字与下划线，例如【顺手牵羊】为 `game_data/cards/shunshouqianyang.gd`，扩展变体可使用 `shunshouqianyang_2.gd`。文件名负责维护定位，规则、网络与存档仍使用稳定 `id`。

### 数据结构

- `CardInstance`：实体牌 UID、配置 ID、花色、点数、区域和所有者，并保存互相独立的手牌临时牌名与 `hand_mark_tags`。手牌标记按来源保存标签、排序和规则覆写；统一移牌边界在实体成功离开当前持有者手牌区时清除，不改变原牌名或复制实体。
- `PlayerState`：身份、武将、武将公开状态、体力、护盾、存活状态、手牌、装备区、判定区、连环与翻面状态、回合标记、公开 `public_marks`、武将牌左上角文本条目和木牛“粮”。`face_down` 明确区分正面与背面；`non_locked_skills_disabled` 由 `non_locked_skill_disable_sources` 的稳定来源记录派生，进入公开快照并支持多个失效来源叠加。`character_corner_text_entries` 以稳定来源ID保存可序列化 `text/order`，控制器排序、去重后写入只读合成字段 `character_corner_text`；技能不能直接覆盖合成字符串。【追歼】与【酩酊】使用来源唯一提示条目，而不使用 `public_marks`。`public_marks` 只保存可序列化的单字图标、数量、说明、来源与顺序，由 `PlayerMarkService` 修改并进入所有观察者快照；`wine_used` 与 `wine_bonus` 属于公开回合规则状态，进入所有观察者快照供酒杀表现与AI攻防评估；`auto_managed` 表示手动或掉线 AI 托管，`auto_managed_offline` 区分掉线托管并进入所有观察者快照；`acquired_skills` 保存机缘等局内来源获得的技能、每回合/每轮/总共次数与来源，`hand_limit_bonus` 保存可累加的额外手牌上限，最终手牌上限为 `max(hp + hand_limit_bonus, 0)`；`acquired_opportunity_ids` 仍是允许重复且只追加的公开权威历史，`opportunity_effect_totals_cache` 与处理游标只在权威端增量汇总其新增尾项，不进入快照、不构成第二份玩法状态；公开序列化仅在机缘历史长度或首尾哨兵变化时生成新的只读数组，不同观察者与重复广播共享该数组，正式整体替换接口会显式失效缓存，已经发出的旧快照不会被原地改写；护盾是公开非负整数，初始为0且不并入体力或体力上限；累计 `damage_taken_count` 让表现层识别护盾完全吸收的伤害，当前回合 `ai_failed_card_target_ids` 让 AI 避免重复无效牌目标。
- `PlayerMarkService`：每局独立的公开标记状态组件。它负责标记数据规范化、`1..999` 数量限制、全场唯一标记转移、来源查询与死亡尾部清理；不读取 UI、AI 或技能 ID。`MatchController` 只提供设置、移除、查询和查找持有者的转发端口。
- `GameState`：玩家数组、摸牌堆、弃牌堆、处理区、当前阶段、回合数、动作序号与胜负状态；公开快照额外提供处理区实体 UID 集合，供表现层核对生命周期而不暴露可变对象。`opportunity_state` 保存机缘流程的阶段、当前选择者、完成进度与权威候选；`to_dict(viewer_id, false)` 只保留该观察者自己的三张候选，并移除已选卡正文。快照中的模式技能查询复用一份无状态 `IdentityRules`，不再为2至10名玩家逐个创建临时规则对象。
- `PlayerAction`：统一操作结构。核心动作包括 `select_character`、`use_card`、`use_skill`、`recast_card`、`end_play`、`choose_opportunity` 和 `set_auto_managed`；`choose_opportunity` 只提交稳定机缘卡 ID，权威端再按当前选择者与本人候选复核；`set_auto_managed` 仅允许真人修改自己的手动托管状态，装备主动动作名由对应卡牌文件动态声明，控制器不维护具体装备动作白名单。
- 离线“控制所有角色”由 `MatchController._prepare_offline_controlled_view()` 集中解析当前规则操作者，并通过 `_set_offline_manual_control_player()` 在运行期临时注销/恢复单名基础AI。开局创建玩家时仍只有最初本地玩家属于真人，其余角色保持AI，因此初次选将、车轮战选将与手气卡不受该开关影响。进入正式回合后才切换 `local_human_player_id` 并重新生成观察者快照；关闭开关立即恢复 `_primary_offline_human_player_id`，递增AI驱动令牌并通过统一续接入口重新安排当前选择或出牌动作，不复制玩家状态或创建多套牌桌。普通选择显式以 `chooser_id` 切换，并行无懈在本地依次发布，LAN模式强制关闭该能力。
- `VirtualCard`：逻辑牌与实体材料牌 UID 的分离描述，支持视为牌、属性和扩展存储。
- `RuleContinuationQueue`：只保存稳定续接类型与可序列化上下文的后进先出规则栈。同步规则在响应牌、费用牌、区域移动或回合开始时机已经成立后若插入新选择，只登记尚未执行的后半段；恢复时不重复消费实体牌、不重复发布已完成时机，也不保存 `Callable`、节点、`PlayerState` 或 `CardInstance` 引用。
- `ChoiceRequest / ChoiceResponse`：统一 `use/respond/card/target/target_control/card_target/button/control/discard/arrange` 选择协议；请求保存 base/active 上下文、各维度独立数量范围和可选牌到目标映射。`target_control` 在同一响应中同时校验目标数组与唯一控制项，避免拆成两个窗口产生状态竞态；私有展示牌只能放入请求响应者定向收到的 `context.display_candidates`，不得写回公共快照、实体 `shown` 或 `known_to`；响应只包含可序列化 ID。
- `CardMoveEvent`：实体牌移动的来源、目的、关联事件、可见者和原因记录。
- `CardPresentationEvent`：使用、展示和判定共用的只读表现事件，保存表现序号、规则事件 ID、事件名、牌快照、来源、目标、顺序目标指示阶段以及是否接管后续弃牌移动。
- `GameState` 额外保存根事件 ID、事件历史、移牌历史、随机种子、轮数、濒死队列和终局原因；快照会裁剪非响应者的私有选择候选。

### 权威规则层

- `MatchController`：创建对局、推进阶段、执行区域移动、处理判定、护盾、伤害、失去体力、额外弃牌阶段、额外出牌阶段、濒死、死亡、连环、翻面、奖惩和胜负。相邻标准阶段、额外阶段、结束阶段到下回合均先完成当前规则时机，再交给 `GameFlowPacer` 延时进入下一阶段；响应提示同样通过请求 ID 防止迟到显示。`roundStart → phaseBefore → 翻面检查 → phaseBeforeStart → phaseBeforeEnd → phaseBeginStart → phaseBegin → phaseZhunbei` 使用稳定回合开始游标逐段发布，因此【振旗】等回合前选择必须完整结束后才会进入【加护】等准备阶段选择；背面角色在 `phaseBefore` 维护效果完成后翻回正面并直接完成跳过回合，不发布 `phaseBegin` 且不运行六阶段主体，只有依赖实际回合开始的效果才能在下一次真正进入 `phaseBegin` 时到期。准备与弃牌阶段的 Begin/End/After 选择会保存当前阶段并在提交后从唯一续接入口恢复，已完成时机不会重复派发，额外出牌阶段队列不会丢失；`phase_transition` 已存在时恢复入口保持幂等，不用同一业务键覆盖已经排队的额外阶段，阶段恢复若暴露新的技能后续则延后一帧继续排空。主动技能权威入口在枚举和提交两处统一校验持有者仍存活且未离场，并统一调用 `can_use_effect()` 屏蔽“非锁定技失效”下的主动、响应与查询钩子；半锁定技的锁定后段由订阅元数据独立放行。LAN 客户端也先读取远端公开快照复核该状态，再使用房主下发的私有技能白名单，旧按钮、旧请求或伪造动作均不能让失效角色发动技能。`execute_virtual_card_use(actor_id, definition_id, material_uids, target_ids, log_message, rule_overrides={})` 在材料仍由使用者拥有时构建虚拟牌代理；恰好1张材料时强制以该实体真实颜色覆盖调用方 `card_color`，在移动材料、创建处理区表现前再次执行完整虚拟牌目标校验，并把原材料定义与逻辑定义写入使用表现快照供统一牌名横条绘制。AI 的动作、同步主动技能和普通选择完成后统一经过进度恢复出口；选择提交失败时使用规则层完整合法动作回退，有限重试后只终止对应无解请求并继续父流程。统一结算管线固定按“同一时机剩余触发 → 装备延后触发 → 通用规则后半段 → 技能自行登记的后续 → 阶段或父牌游标”恢复；通用规则后半段按嵌套层级后进先出，技能同层后续仍保持原登记顺序。响应、无懈、濒死救援、目标区域牌移动、重铸、弃牌阶段、回合开始、【杀】武器费用和伤害尾部都通过该边界等待插入事件，已消费牌只以稳定 UID 快照恢复结果。卡牌使用上下文累计直接响应数和真实响应者ID，反响应只归属直接父牌；【制动】可排除持有者本人响应，伤害来源上下文携带父牌UID与逻辑目标数穿过四个修改窗口。`damage` 先扣护盾后扣体力并独占伤害事件；`damage`、兼容 `damage_after`、`hp_reduced`、濒死、`damageSource/End/After`、按最终伤害点数逐次派发的 `damagePointAfter` 与属性连环之间均会检查嵌套屏障。`lose_hp` 绕过护盾与伤害事件，只在实际体力减少时与伤害共同汇入 `hp_reduced`；减少护盾只派发护盾变化时机，不属于伤害或体力减少。手牌限时视为效果以实体UID登记，进入持有者下个回合时锁定到期回合，回合结束或实体提前离开手牌区时恢复原牌名；通用手牌标记同样以实体UID保存，但只在移动确认成立后、实体真正离手前清除，移动被取消时仍保留。离场濒死者在标准濒死时机后跳过救援请求，死亡入口先复用 `restore_player_to_game()` 派发 `enterGame` 并清除限时离场标记，再进入 `dieBefore/dieBegin/die`，保证死亡技能、日志和公开快照均观察到已返场状态。弃牌阶段插入的额外出牌阶段在当前弃牌生命周期完成后执行，结束后直接进入结束阶段，不重复弃牌。
- `CardRuleService`：只做距离、攻击范围、配置化次数、通用目标、区域和延时锦囊同名校验；专属目标组合回调对应卡牌文件，不执行效果。`all_players/all_others` 自动展开时会逐名应用卡牌与技能目标限制，只保留合法角色并再次检查卡牌最少目标数，因此【破风】等限制可把群体锦囊收敛为少量目标，而不会被任一非法角色否决整张牌。
- `CardEffectResolver`：纯卡牌源码调度器。它只保存 `host/state`，按卡牌 ID 调用 `resolve/resolve_target`，并按父牌 UID 把选择、响应和专用无懈结果交回原卡牌文件；不包含摸牌、回复、装备、群体响应或任何具体卡牌名称的效果函数。
- `CardUseEventService`：只构建 `CardUseEvent`、五组使用时机、四组动态逐目标时机、`contentBefore/content/contentAfter` 与 `orderingDiscard` 的事件拓扑；不读取 `GameState`、不执行牌效、不持有实体牌对象。
- `IdentityRules`：集中维护 2 至 10 人身份表、胜负条件和死亡奖惩类型；胜负生存集合只依据 `PlayerState.alive`，`out_of_game` 不等同死亡。控制器对完整身份表洗牌，不为领袖保留固定座次。
- `CharacterSelectionService`：纯数据选将状态机，集中维护首次身份下的领袖先选、普通同时选将或最终座次身份自选、1至20张普通随机候选、仅首任领袖的领袖技固定候选、每人私有换将张数、候选私密性与统一完成条件。真人首任领袖在 `PHASE_LEADER` 的同一次 `select_character` 中确认武将、座次和身份，成功后立即从 `PHASE_CUSTOM` 待选集合排除；其余玩家最终自选不附加固定前缀，因此候选数严格等于房主设置。领袖技武将只在当前领袖身份中锁定换将。首任领袖为AI时允许先公开武将并延后占用最终名额，`retains_selected_character=true`、`local_selected_character_id` 和空候选只服务于该AI之后复用同一武将补选座次身份，不会发给已确认真人形成第二个面板。其他观察者仍只收到本人第一次 `local_identity`、候选、锁定/可换 ID 与剩余换将卡，不泄漏其他玩家身份或张数。`get_pending_player_ids()` 在领袖、普通其他玩家和最终自选三个阶段分别返回真实未确认集合，避免 AI 漏选或重复处理领袖。它不加载界面、不注册 AI，也不修改卡牌区域。控制器完成全员选择后先切换到 `game_start` 并同步亮将结果，发完默认4张起始手牌、旋转或应用最终座次后再次同步，随后才允许首轮 `roundStart` 创建技能询问。
- `RuleEventBus`：按优先级同步派发 `RuleEvent`。武将技能、装备扩展和模式规则可订阅事件，不需反向引用控制器。
- `RuleTimingCatalog`：无状态时机目录，集中保存221个不重复监听事件和4个主动技能入口。它不读取对局状态、不派发效果，只提供名称校验与稳定分类顺序；新增 `damagePointAfter` 专门承载最终伤害的逐点触发。
- `RuleTimingService`：同步标准时机派发组件。它先调用兼容 `RuleEventBus`，再依据当前状态的存活座次把事件交给独立 `TriggerManager`，最后完成事件；它不执行任何具体牌效、伤害、移动或阶段逻辑。
- `EventScheduler`：维护根事件、事件栈、`next`/`after` 队列、步骤游标、`goto`/`redo`、多通道暂停 token、选择请求与终局中断。长期根事件通过 `held_open` 等待后续子树，不占用暂停 token，也不会阻塞新阶段或卡牌事件。无法构造任何合法提交的单个选择可通过 `abort_choice()` 只中断所属事件并释放自己的暂停 token，不会扩大为整局中断。事件历史通过最新记录增量同步到 `GameState`，状态层与调度器使用独立数组但共享写入后不再修改的条目字典；状态广播只在条目数失配时复制数组引用进行全量校准，不随长局历史长度重复深拷贝第二份事件上下文。对外调试接口仍返回深拷贝，不能借共享存储修改归档。事件完成后立即释放含 `Callable`、可变上下文和步骤队列的完整 `GameEvent`；按ID快速查询只索引最多4096份与历史共享的最终摘要，旧事件仍从完整历史逆序恢复并提升回热索引，近期或重复规则查询保持常量时间而索引内存不随长局增长。同步 `record_event()` 只记录父ID关系，不进入长期根事件的待执行队列。事件状态仍区分 `finished`、`cancelled`、`neutralized` 和 `aborted`。
- `GameplayPauseService`：对局级令牌暂停组件。首个调用方申请时保存原场景树暂停状态并暂停对局，最后一个调用方释放后恢复；`MatchController` 同步持有 `EventScheduler` 全局 token，并在所有 AI 调度与动作入口查询同一状态。
- `GameFlowPacer`：对局流程节奏组件。它只按业务键管理可取消计时器与回调令牌，不读取 `GameState`、不决定阶段、不执行响应；重新开局会取消全部旧任务，场景暂停期间计时不推进。
- `TriggerManager`：先按 `player/source/target/global` 过滤技能持有者与 `RuleEvent` 角色关系，再按 `firstDo/lastDo`、技能优先级、起始座次和注册顺序排列触发器，并在执行前重新检查动态条件。同一时机内部始终沿用初次排列；回调内又创建暂停时机时，续列按最内层优先恢复，必须先完成子时机剩余处理器再返回外层座次。
- `RuleModifierPipeline`：独立于触发器的纯查询修正链，供 `RuleQuery` 实现 card/target enabled、usable、respondable 和 in-range 查询。
- `RuleQuery`：只读合法性门面；不创建选择、不移动牌、不消耗次数。
- `CardMovementService`：统一维护实体牌区域和牌面知识，追加 `CardMoveEvent` 历史，并在权威移动完成后发出唯一 `card_moved` 增量；同一实体在同一区域且持有者未改变时拒绝重复移动，控制器只把进入手牌和弃牌堆的有效增量转为客户端表现，规则调用点不得重复发信号。组件同时按“全局回合号+行动角色”维护出牌阶段进入弃牌堆的 UID 顺序索引；晚于状态创建时会一次性从既有历史重建，之后增量追加，使指定回合候选查询只处理该短桶和当前弃牌堆，而不扫描整局移动记录。

### 外部适配层

- `AICoordinator`：管理玩家与 AI 策略映射，把权威完整快照和合法动作交给策略选择；共享 `IdentityAIModel` 观察公开用牌，即使没有内置策略也保留忠反推断，并通过只读查询和变化信号提供给本地界面。
- `BasicAIPolicy`：示例启发式策略。它不能修改状态，只返回可序列化动作；卡牌基础价值、目标收益方向和无懈收益方向读取卡牌元数据，不维护具体卡牌 ID 表。策略、`NonameAIEvaluator` 与 `IdentityStrategyEvaluator` 分别缓存数据库返回的静态元数据独立副本；同一合法动作集合内按技能 ID 复用纯 AI 技能实例。`IdentityAIModel` 在普通行动、统一选择、无懈判断和装备材料排序的单次同步决策边界内，先完成固定身份观察同步，再额外遍历最多10名玩家1次建立玩家ID、存活身份人数、身份首名玩家与存活总数索引，并按需复用局势和反贼暴露判断；返回动作前连同技能实例一起清空，绝不跨决策缓存权威快照或决策结果。`NonameAIEvaluator` 统一对酒杀响应、最后【闪】保牌、预期伤害、护盾和属性连环进行评分，技能文件只叠加自身专属奖励。
- `NetworkGateway`：封装离线、局域网和远程模式。LAN 分支直接管理 `ENetMultiplayerPeer` 建房/加入、房主内存密码与公共 `has_password`、成员形象、位置、聊天历史、踢出及按远端地址计时的5000毫秒重新加入冷却、peer 与稳定玩家 ID 的大厅位置顺序映射、每发送端封包序号去重、真实发送者 actor 防伪、定向私有快照和只读表现事件；释放会话时先以 `OfflineMultiplayerPeer` 脱离 `SceneMultiplayer`，再关闭旧 ENet peer，使同端口可立即复用。对局内断线重连同样收敛在网关：房主开局时为每名远端真人签发32字符会话令牌，掉线时按令牌登记座位预约，客户端断线后以2秒间隔自动重拨最多15次并携令牌重新登记；令牌命中即重绑 peer 映射并以 `lan_match_peer_reconnected` 通知控制器解除离线托管，令牌还能直接接管房主尚未察觉掉线的旧连接，对局结束或重开新局时预约整体失效。客户端不能上传状态、取得密码明文或伪造其他玩家操作。REMOTE 继续保留外部适配器信号。
- `match_table.gd`：桌面协调器，只读保存控制器刚生成的裁剪快照，按玩家 ID 建立当帧索引，缓存不会在运行期间变化的卡牌、武将和势力定义，并按实体 UID 对账复用正式手牌节点与座位节点；本地手牌排序只复用当前只读快照引用，不逐牌深拷贝。对局时长使用仅在进行中启动的0.25秒 `Timer` 检查整秒变化，终局或返回主菜单后停止，不注册每帧 `_process`。它维护出牌临时选择、读取只读规则预览并构建 `PlayerAction`。手动选目标时，它把合法候选、已选目标与“当前处于手动选目标”三项状态传给武将牌组件；全体目标模式仍只显示“规则自动展开”。【桃】【酒】【无中生有】【闪电】和自身装备只有在规则预览确认本人是唯一合法目标时才自动锁定本人。主动技能创建可取消的内联选择后，原技能按钮保持选中与可点击，再次点击提交标准 `confirmed=false`；响应转化技能再次点击只退出材料转化模式。未被 GUI 消费的牌桌空白左键会同时收起已展开的对局记录与局内菜单；离线日志暂停时由始终处理的 `MatchLogPanel` 发出关闭意图，再由牌桌复用同一关闭入口。`MatchLogPanel` 独立保存本局完整纯文本日志：折叠时清空 `RichTextLabel` 排版文档，展开时一次恢复全部历史，展开期间同一帧的新增记录合并为一次追加和滚动；重新开局通过组件端口同时清空历史与正文。托管按钮与 `PlayerAutoManagedHandOverlay.cancel_requested` 都只构造 `set_auto_managed`，独立覆盖组件负责0.76透明度黑色滤镜、0.45秒省略号循环、文字区域取消意图与输入拦截；牌桌根据手牌、本地座位和当前手牌层级计算175像素高的覆盖矩形，并把技能栏提升到其上方，牌桌仍以快照禁用其他操作。本地非摸牌获得直接驱动正式手牌节点从右侧入场；同一次 `draw()` 的牌堆到手牌移动先按批次 ID 收集，完成后一次性提交动画层，使同批牌背按42像素间距整体居中并行播放。每个已收齐的批次立即启动，多个玩家或连续摸牌的批次可以重叠播放。它在主菜单发出开局信号前不调用 `MatchController.start_match()`，收到单机信号后统一开始离线对局（身份/斗地主/2v2）；局域网则协调连接入口、`OnlineLobbyPanel`、`NetworkGateway` 与房主权威控制器，客户端只绑定房主按大厅位置顺序分配的本地玩家 ID并渲染远端快照。局内重开先读取控制器的只读前置校验：失败时不清理旧表现并调用局内菜单恢复入口；通过后才清理旧表现并替换权威状态，若后置初始化仍失败则缓存同步拒绝原因并调用主菜单恢复入口。牌桌依据 `NetworkGateway.is_lan_client()` 统一隐藏非房主无法生效的局内权威控件；五谷等公共模态窗口保持在手牌层级之上，其牌位结构不变时复用原 `CardView`，只更新交互权限、领取虚影和领取者标签。菜单布局、联机大厅位置和选将候选布局由独立组件负责。身份徽记按公开身份、手动标注和自动忠反标记的优先级渲染，但不写回快照。桌面只把各视图的统一信息信号连接到唯一 `InformationBoxLayer`，并在离线武将详情显示期间管理独立暂停令牌；信息组件本身不读取控制器或网络模式。主题变化时只协调各表现组件重绘。
- `card_view.gd`：以 `Node2D` 为根的单张实体牌组件，只处理牌面、选中反馈、手牌入场表现偏移与统一信息请求；视为牌名与 `hand_mark_tags` 共用整体居中的标签行，标签均使用纸张白色底、4像素间距和对应边框，视为标签在前、手牌标记按稳定顺序在后。装备主类型按子类型映射为武器、防具、两类坐骑和宝物牌底部文本；`card_input_area.gd` 负责点击、悬停与拖放协议。可见牌面悬停时发出内容字典与全局锚点矩形，牌背不发出；外部容器与动画层拥有绝对位置，牌面样式刷新默认不能重置非手牌纵坐标。

- `card_use_animation_layer.gd` 为摸牌设置独立的0.24秒飞行、0.10秒停留和0.18秒淡出参数；批次接口和带摸牌堆叠键的兼容转移都使用这三段时长，普通出牌与弃牌继续使用既有通用动画参数。本地正式手牌节点从右侧进入布局的时长为0.24秒，所有这些数值只影响客户端表现。
- `match_log_panel.gd`：只管理“记录”按钮与日志正文的折叠状态并发出 `expanded_changed`；公开 `is_expanded()` 与 `set_expanded()` 让按钮和牌桌空白点击复用同一显隐入口，避免绕过暂停信号。日志内容仍来自规则核心的 `log_added` 信号，不读取通信模式或修改对局状态。`match_table.gd` 只在 `NetworkGateway.Mode.OFFLINE` 下通过 `MatchController` 申请 `GameplayPauseService` 令牌，收起日志或退出牌桌时释放；LAN/REMOTE 不暂停。
- `player_auto_managed_hand_overlay.gd`：只管理本地托管滤镜、输入拦截和0.45秒省略号循环；`auto_managed=false` 时同步隐藏并关闭 `_process`，开启后才恢复帧处理，常态不产生空轮询。
- `character_selection_panel.gd`：只渲染观察者可见的选将快照，以正式 `PlayerTargetView` 原尺寸展示候选，通过纵向 `ScrollContainer` 承载多行牌面，并分别提交选将数据或单张换将稳定 ID；候选牌手势、空白内容手势、滚轮和原生拖条同步同一个内容位移。自选模式中的真人首任领袖第一次面板就读取默认座次身份并显示两组按钮，确认时一次提交武将、座次与身份；权威回包变为 `can_select=false` 后整个面板关闭，不创建第二组候选或第二次确认。全武将模式只改变主框和控件显隐，确认按钮始终位于滚动区外。候选与公开领袖牌的统一信息信号由组件向牌桌转发，不直接依赖 `InformationBoxLayer` 实例。
- `skill_button_view.gd`：武将技能元数据展示组件，只发出技能 ID 请求；可主动发动的技能由桌面构造 `use_skill` 动作，实际条件与效果仍由对应技能文件执行。
- `artwork_loader.gd`：卡牌与武将共用的可选插画加载边界，只返回 `Texture2D` 或空值。
- `ui_style_registry.gd`：纯数据 UI 风格注册表，集中维护稳定 ID、显示名、默认风格、语义配色和仅影响表现的主题数值。当前内置 `space_mono`、`decade_wood` 与 `premium_black_gold`；模式卡选中加深比例同样由注册表按主题覆盖，不读取场景节点、设置控件或对局状态。
- `battle_ui_style.gd`：动态 UI 的统一样式工厂，只读取当前风格的语义色并生成圆角、描边、内容边距与阴影；组件不得重新保存主题专属颜色常量。
- `decade_battle_layout.gd`：无状态座次布局组件，只消费角色视图数组和总人数，按无名杀百分比模板写入 Control 几何信息。节点身份、顺序和总人数与上次完全一致时跳过重复位置与缩放写入；尺寸变化信号仍强制重排。全屏容器自身使用 `MOUSE_FILTER_IGNORE`，输入只由动态武将牌子节点处理。
- `decade_hand_container.gd`：无状态手牌容器，只根据子节点数量、悬停索引和可视宽度计算重叠、抬升、悬停顶置与按需滚动范围，并在布局位置上叠加正式手牌节点自身的入场偏移；悬停不会改变其他手牌位置。组件以宽度、节点身份与顺序、悬停、选中、拖动和布局参数生成结构签名，签名未变化时跳过重复位置计算，任一输入变化时自动失效。

`assets/ui/table_ornament.svg` 是代码仓库内的矢量桌面装饰资源。它不包含输入或规则逻辑，可由后续主题资源替换；中央牌堆与阶段区域的数据仍只来自本地裁剪快照。

`MatchController.get_card_use_preview()` 是 UI 使用的只读查询边界。它返回当前卡牌是否可提交、合法候选目标、规范化目标、目标模式、规则修正后的最少/最多目标数和说明文本，不返回 `GameState`、`PlayerState` 或 `CardInstance` 对象引用。只有点击选牌与点击目标才构造 `PlayerAction` 并进入 `submit_action()`；拖拽只处理本地手牌排序。

座次与手牌排版不再由 `match_table.gd` 保存像素表。桌面先把绝对座次数组旋转为“本地下家至本地上家”的相对顺序，再把动态视图交给布局组件；布局组件不认识玩家身份、卡牌效果、阶段或动作协议，因此本地座次随机化不会改变环桌行动方向。

技能栏通过 `GameDatabase.get_skill()` 读取技能元数据深拷贝，其中布尔 `lock` 明确标识锁定技，布尔 `leader_skill` 明确标识只有 `identity=leader` 才实际拥有的领袖技。选将完成后，`MatchController` 根据武将源码直接引用的技能脚本为每名玩家创建独立实例并调用 `install()`；非领袖的领袖技在实例安装前被过滤且技能栏不创建按钮，其他不可发动、预留、被动、触发和锁定技能按钮保持禁用灰显且点击静默，可主动技能通过 `use_skill` 动作调用自身 `can_activate/activate`。描述为“出牌阶段开始时”的技能在 `phaseUseBegin` 回调内直接创建询问，不能延后到普通出牌按钮。出牌阶段主动技能先以 `button_ids` 完成当前 `chooseToUse`，再在同一事件链内创建后续选择；技能若同步完成且没有建立嵌套请求，也会由控制器统一恢复 AI 的下一次 `chooseToUse`，寒鸦【录事】等主动技能不需要自行调度 AI。技能基类自动把 `skill_id/skill_owner_id` 写入选择上下文；跨角色选牌与文字选项另保存真实选择者，提交的牌、目标或 `control_id` 回到同一运行时实例的 `continue_choice/continue_selection/continue_response`，额外弃牌阶段完整结束后通过 `continue_extra_phase` 恢复。技能顺序效果若被嵌套选择暂停，则用 `defer_settlement()` 登记纯数据步骤；控制器在选择、同一时机续列和装备触发均无等待后调用原实例的 `continue_settlement()`，避免业务函数在选择存在时继续同步结算。响应候选会同时查询技能实体转换钩子，但可转换材料默认禁用，只有玩家显式点击匹配技能后才以 `response_skill_id` 提交；控制器消费前重新复核技能、材料区域与转换条件。同一规则时机出现多个可选技能时，`TriggerManager` 保存已排序续列，当前选择及其后续选择完全恢复后再从当前回合角色起按座次继续询问，不能覆盖后续技能请求。技能在确认支付费用、锁定效果或主动效果实际成立后调用 `SkillDefinition.announce_activation()`（跨角色领袖技用 `announce_activation_for_player()`）；控制器统一追加“角色发动了【技能】。”日志、保存公开只读 `skill_history` 并发出信号，`match_table.gd` 在发动者武将牌中心以高于手牌的黑色描边文字短暂显示技能名。AI 动作与预览也由技能文件提供，非领袖不会应用领袖技牌效钩子。`SkillButtonView` 与 `match_table.gd` 始终不能直接修改状态。

技能元数据中的 `half_locked=true` 表示正文同时具有非锁定前段与锁定后段；正文中“锁定技”标签位于非开头位置时，基类也会自动识别该结构。所有主动、响应、查询、异步恢复和额外阶段回调都通过 `can_use_effect()` 复核“非锁定技失效”状态；半锁定技后段订阅显式传入 `locked_segment=true`，只负责清理既有持续效果的维护回调使用 `maintenance=true`。该分段不复制技能实例，也不改变玩家可见原文。

手牌临时牌名由 `CardInstance` 保存原定义与来源技能，只有统一移牌边界可以清除。实体在手牌区时，合法动作、显示与AI读取当前临时定义；实体作为使用或响应材料离手时，当前逻辑牌先保存该定义，再把持久实体恢复为原定义并移入处理区或弃牌堆。该模型保留唯一UID、花色、点数和区域历史，不为【药理】复制一张永久新牌。【亲酿】在实体进入接收者手牌后额外登记“下个回合结束”到期记录；实体提前离手时由同一移动边界恢复，不能由技能直接改写牌区数组。不改变牌名的 `hand_mark_tags` 使用独立来源字典；【鸣弦】通过其中的 `ignore_distance_limit` 使该实体【杀】在手牌内忽略距离，标签与规则在实体成功离手时一并清除，移动被时机取消时保留。临时牌名和标记可同时存在，清理一类状态不得覆盖另一类。

插画路径属于静态表现元数据，不写入 `CardInstance` 或对局快照。卡牌定义可直接提供 `art_path`；武将定义不维护该字段，`GameDatabase._load_characters()` 会根据每个武将源码文件的完整基础名，在 `res://game_data/characters/image/` 按 PNG、JPG 顺序自动发现同名资源，并只向对外武将元数据副本注入命中路径。该过程不修改 `CharacterDefinition` 源对象，也不依赖武将稳定 ID、中文显示名、技能或对局状态。

`CardView` 和全玩家共用的 `PlayerTargetView` 只把最终元数据中的 `art_path` 交给 `ArtworkLoader`，因此插画缺失不会影响规则层、AI 或网络层。同名 PNG 与 JPG 并存时选择 PNG；两种格式均缺失时不产生数据校验错误并显示占位图。本地玩家与其他玩家使用同一武将牌类和148.35×197.8像素的3:4原生场景规格，差异仅来自布局位置和快照可见性；装备横条读取141.35像素插画宽度，判定区和状态覆盖由独立无状态子组件渲染。正式卡牌统一为111×148像素的3:4规格。

濒死入口维护“存活角色体力不大于0时必须处于濒死或进入死亡确认”的权威不变量。`dyingBefore/dyingBegin` 的取消或中立化只有在处理器已恢复正体力、确认死亡或令角色离场时才能终止；单独设置事件标志不会让伤害尾部留下非正体力存活角色。

## 开局与选将边界

`MatchController.get_match_start_validation_error()` 是开局前不修改任何状态的只读校验边界，统一返回人数与全局数据配置错误；`MatchController.start_match()` 复用同一结果，只有空字符串时才取消旧任务并替换状态。随后控制器创建身份、空武将玩家状态和牌堆，并把阶段设为 `character_selection`。标准身份局使用同一对局随机源先为本地人类玩家分配有效座次，再对包含领袖的完整身份池洗牌，因而本地玩家、领袖和一号位三者互不绑定。领袖先获得候选并单独确认，控制器立即把领袖武将写入 `PlayerState` 且公开；随后其他玩家各自同时确认，具体选择在所有人完成前不进入其他观察者快照。开启最终座次身份自选时，真人首任领袖在第一次公开选将动作中同时确认最终座次身份，随后不再进入其他玩家选将流程；AI首任领袖只先亮将，待真人完成后复用同一武将补选剩余名额。全员完成后控制器统一公开非领袖武将、按武将配置初始化体力、安装每名武将直接引用的独立技能实例、每人摸4张起始手牌，并直接查找唯一领袖开始首回合；预留的 `first_turn_seat_number` 不参与标准身份局顺序判定。只有对局人数不少于5人时，领袖才在武将基础体力上限上增加1点。

首任AI领袖补选采用优先队列：全部真人确认后，控制器先检查该AI是否仍保留首次公开武将且尚未确认座次身份；若一号位与领袖仍空缺，则该AI先以同一稳定武将ID取得二者，再处理其他AI。真人已确认领袖时，首任AI领袖只按剩余名额补选，不能改写真人的最终选择或自身公开武将。

首任AI领袖首次确认时，控制器从服务提供的全部合法候选中使用本局 `RandomNumberGenerator` 取一张；领袖技固定候选仍位于普通随机候选前端并保持不可换将，但不构成AI取将优先级，普通AI继续取其首个未被确认占用的随机候选。该随机调用与身份、牌堆、候选生成共享同一对局随机源，因此同一种子可完整复现。

房主权威开局设置在 `start_match()` 创建新状态时复制到 `GameState.match_options`，当前对局不再读取菜单后续变化，其中 `mulligan_limit` 为 `0/1/2/3/4/5/10/-1`、`character_candidate_count` 为1至20、`character_replacement_count` 为 `0/3/5/8/10/20`。即使开启“自选全武将、座次与身份”，服务也先按第一次身份进入 `PHASE_LEADER` 并公开首任领袖武将，再进入 `PHASE_CUSTOM`：真人首任领袖阶段快照直接开放最终座次、身份控件与“所有武将”入口（`allow_all_characters=true`）；首次座次按该领袖旋转，使默认领袖与一号位组成真实状态。真人提交必须包含武将、座次和身份，座次全局唯一，身份总量等于标准身份分布，一号位与领袖身份双向联动。首任真人领袖成功提交后立即占用名额并从待选集合移除；首任AI领袖只先亮将，等真人完成后再占用剩余名额。最终自选候选严格等于设置张数，不附加领袖技固定前缀；服务保存不可变的首任领袖玩家 ID、首次生效值、预览值、最终稳定玩家ID、武将ID、座次号、身份ID、锁定候选和私有换将张数。控制器收到有效 `preview_custom_assignment` 后立即投射预览座次与身份、重排 `PlayerState` 显示顺序，并清空未确认角色的背景亮将；首任领袖继续占一号位时保留其公开武将，新一号位为AI时才应用其公开预览武将，并在AI最终确认时复用该稳定武将ID，未确认真人成为一号位时快照显式清空旧领袖武将。每次最终 `select_character` 只应用一次权威武将结果并按最终身份刷新基础体力，全部完成不会再次覆盖座次或武将。全部真人确认后，AI才从剩余座次和身份名额中完成选择。身份局在唯一首任身份尚未落定时可预留一号位；2v2 无首任身份绑定（`get_first_seat_identity()` 为空），但座次与蓝/红按开局表 `team2v2_identity_by_seat` 强制一致。AI 必须从完整可用座次中选合法绑定对并优先沿用首次随机座次，禁止无条件移除一号位以免最后一名 AI 提交无效座次。预览补位 `_apply_custom_assignment_preview` 同样遵守绑定表。

首任领袖公开武将是该稳定玩家不可改写的最终武将：真人在 `PHASE_LEADER` 第一次确认时已经同时落定座次身份，进入 `PHASE_CUSTOM` 后服务不再把该玩家列入待选集合；其余玩家才获得严格等于房主设置张数的随机候选。首任领袖为AI时服务保留其选择、清空候选和全武将入口（`retains_selected_character=true` 仅服务该 AI 补交座次身份，不用于真人首任领袖），AI驱动在真人完成后直接提交同一稳定武将ID补足座次身份，因而不会停住、抢占真人名额或在开局前后再次随机。

`AICharacterAdjustmentService` 是初次选将与技能安装之间的独立阶段组件。它只保存房主ID、可调整AI ID、当前目标和本次随机候选；房主点击AI武将牌后按本局1至20张普通候选数重新生成，确认时由 `MatchController` 重新初始化该AI的武将与体力，座次和身份保持不变。`StartingHandMulliganService` 是起始手牌发放与领袖首回合之间的独立手气卡张数/完成状态组件，支持关闭、一至五张、十张与无限张；实体牌洗回、重洗和重发仍由控制器通过 `CardMovementService` 执行。手气卡重发不进入普通摸牌生命周期，避免开局配置替换触发摸牌技能或被摸牌修正改变张数。各设置与阶段组件均遵循单一职责，阶段推进只由控制器编排。

`CardRuleService.normalize_targets()` 是多目标的统一权威顺序入口。群体目标牌从使用者开始按环形行动顺序展开：`all_players` 先结算使用者本人，`all_others` 先结算使用者的下一名存活角色；方天画戟和铁索连环等手动多目标牌也在提交后按相同行动顺序重排。【借刀杀人】在使用动作中保留“持刀者、被【杀】者”两名声明角色，`CardDefinition.get_resolution_target_ids()` 将实际目标时机收敛为唯一持刀者，`configure_requested_target_context()` 将第二名角色写入结算上下文，因此牌效不会再创建独立目标请求。【无懈可击】每轮把全部存活玩家加入同一公开响应名单，并为当前确有合法候选的玩家分别登记私有 `ChoiceRequest`；请求彼此并行，首个到达权威端且通过实体牌复核的响应取得本轮结算权，同轮其他请求立即以系统放弃关闭。成功响应后重新开启下一轮，直到完整一轮无人响应。公开 `simultaneous_response_display.responder_ids` 始终包含全部存活玩家，不携带候选数量；连环传导与濒死救援仍从当前回合角色开始按存活座次进行，若一名濒死响应者回复后目标仍未脱离濒死，下一轮从该响应者重新开始。

死亡结算先标记死亡并亮出身份，然后立即调用 `IdentityRules.evaluate_winner()`。该服务只把 `alive=false` 视为死亡；`out_of_game=true` 的角色仍计入身份局、斗地主与2v2阵营生存，虽然其继续从行动、距离、目标和响应集合排除。若已满足胜负条件，`GameState.game_over` 会成为规则操作与 `CardEffectResolver` 的统一终止条件：当前死亡弃牌、奖惩、群体牌后续目标、响应、伤害、回复、摸牌及使用牌结束区域移动全部停止。若对局继续，则清理死者区域并执行击杀奖惩。当前回合角色在自己行为的插入结算中死亡时，当前事件完整结算后直接从其下名存活角色开始新回合；若死于开始阶段事件或判定阶段，则由 `_start_turn()` 在该阶段结算返回后执行同一转交，不会停留在死亡角色的回合。

普通候选数量由房主 `GameSettings.character_candidate_count` 设置为1至20并在 `MatchController` 开局时锁定，默认5、实际不超过可用武将数量；所有拥有领袖技的武将由控制器扫描技能元数据后额外传给服务，固定前置且不占普通数量。人类、AI 和网络玩家都提交 `select_character` 标准动作；换将统一提交 `replace_character_candidate`，任何适配层都不能直接改候选数组、剩余张数、`character_id`、`character_revealed`、`hp` 或 `max_hp`。

选将完成后玩家数组从领袖旋转，使领袖成为一号位，并按旋转后的数组索引刷新“玩家1”“玩家2”“玩家3”等显示名；稳定 `player_id` 始终不变，继续用于网络、回放和实体所有权。

## 触发事件

标准技能时机由 `RuleTimingCatalog` 统一维护，共221个名称，覆盖游戏与阶段、使用牌与响应、伤害、体力与生死、牌移动、判定与拼点、选择、技能自身及武将模式规则。核心通过 `MatchController._emit_rule_timing()` 创建包含 `player_id/source_id/target_id/data` 的 `RuleEvent`，由 `RuleTimingService` 统一派发并记录历史。完整名称与制作语义以《内容制作指南》的“无名杀221时机系统”为准，架构文档不维护第二份易漂移清单。

阶段、伤害、用牌与移动组件只负责在自己的真实边界调用统一派发端口：阶段使用成功进入 Begin 后保存 `body/end_emitted/after_emitted` 生命周期游标，选择恢复时从游标继续而不重复主体或时机；选择窗口通过 `resume_phase` 暴露真实规则阶段。`phaseUse` 的 Begin 或主体内选择必须等待父事件排空后再重建唯一 `chooseToUse`，只有已进入 End/After 的生命周期才由恢复器继续结束阶段；没有生命周期记录的独立规则结算不会被误判为阶段结束。额外出牌阶段在登记时把 `discard/finish/turn_complete` 明确后继与次数一同排队，不再从恢复后的临时阶段反推去向。伤害在濒死选择期间把 `damageSource/End/After` 保存在待收尾上下文；使用牌由 `CardUseEventService` 维护五组整牌时机和四组动态目标时机；区域移动由控制器语义端口在 `CardMovementService.move_card()` 前后派发复合生命周期。目录和服务均不反向调用这些业务组件，因此不会形成“时机服务执行牌效”的胖模块。

以下蛇形命名事件继续作为迁移期兼容层：

- `phase_start`：回合开始阶段。
- `phase_finish`：回合结束阶段。
- `card_used`：实体牌进入处理区并声明目标后。
- `damage_before`：伤害扣减前，可修改 `amount` 或取消。
- `damage_after`：护盾与体力扣减后、濒死结算前；即使护盾完整吸收伤害也会触发，并公开 `shield_absorbed` 与 `hp_lost`。
- `lose_hp_before` / `lose_hp_after`：独立失去体力流程，绕过全部伤害事件与伤害历史。
- `hp_reduced`：体力实际减少后的统一事件，通过 `reduction_type` 区分伤害与失去体力；护盾完整吸收时不触发。
- `shield_after`：角色实际获得护盾后触发，包含来源、实际增加量和累计护盾。
- `recover_after`：实际回复完成后。
- `dying_begin`：角色进入濒死流程时。
- `dying_end`：角色回复至1点体力或以上并完成求桃流程结算时；上下文包含最终体力和救援成功标志。

旧兼容技能可继续通过 `RuleEventBus.subscribe(event_name, owner, callback, priority)` 注册；新标准技能使用 `SkillDefinition.subscribe_timing()`，由基类绑定技能持有者 ID 和四角色关系。组件卸载时基类会同时清理普通总线与独立 `TriggerManager` 订阅。

兼容 `damage_after` 表示伤害事实，但技能原文精确写作“当你的体力值受到伤害”时还必须检查 `hp_lost>0`；护盾完全抵消不满足。直接失去体力不进入伤害事件，失去护盾既不进入伤害事件也不进入 `hp_reduced`，因此两者均不能触发该措辞。

## 状态可见性

`GameState.to_dict(viewer_id, reveal_private)` 是唯一快照入口：

- 本人可见自己的身份、手牌与木牛“粮”。
- 本人可见自己已经确认的武将；领袖确认后立即对所有人可见，其他玩家在全员完成选将后同时公开。
- 他人只看到手牌数量和“粮”数量。
- 装备区、判定区、体力、护盾、存活与连环状态始终公开。
- 处理区实体 UID 始终公开，但快照不额外暴露非公开牌面；UI 仅用该集合核对中央表现是否仍属于活动处理区生命周期。
- `reveal_private=true` 仅供权威 AI、服务器调试与回放使用。
- 非响应者的活动选择快照会清空卡牌、目标、按钮、控制项、已选结果与活动上下文；局域网客户端不能从他人请求推断私有候选。
- 局域网客户端不接收 `random_seed`；当前行动玩家额外收到仅属于自己的 `local_legal_actions` 以完成无状态 UI 预览。

## 设计边界

工程不实现国战身份、势力明置、双将、暗将和国战专属牌。当前武将目录包含28名正式武将，合计引用55个唯一武将技能；技能目录另登记飞扬、跋扈、共苦3个斗地主模式技能。所有后续扩展应新增配置或独立组件，避免把角色 ID、UI 节点或网络模式硬编码进规则服务。

## 平台适配边界

Android 平台差异由表现与输入组件消化，不进入 `MatchController`、规则事件树或数据快照：

- `project.godot` 维护1280×720逻辑视口、`canvas_items + keep` 等比缩放、固定横屏方向、Vulkan Mobile渲染、HiDPI，以及触点到标准鼠标指针的GUI兼容入口。
- `CardInputArea` 只把标准指针或未启用模拟时的单指触摸转换为卡牌激活、说明与手牌拖动信号；启用触摸模拟鼠标时忽略原始触点，长按和拖动不会直接提交规则动作。
- `PlayerTargetInputArea` 只把标准指针或未启用模拟时的单指触摸转换为目标激活、武将详情和局部指针信号；启用触摸模拟鼠标时忽略原始触点，武将牌自身仍不读取合法目标规则。
- `AndroidBackAdapter` 只把系统返回通知转换为标准 `ui_cancel`，未消费的页面级回退再交给 `MatchTable` 协调主菜单或局内菜单。
- `AndroidDisplayStability` 只在Android启动与应用恢复时设置60 FPS上限和VSync；Vulkan Mobile渲染与固定横屏由项目配置维护，组件不进入逐帧业务循环。
- `MobileKeyboardGuard` 是无状态平台工具，只在Android释放当前`LineEdit/TextEdit`焦点并隐藏系统软键盘；主菜单、连接入口和联机大厅在页面切换边界调用它，文本框主动编辑期间不参与输入内容处理。
- `export_presets.cfg` 只描述 APK 包、Android SDK、架构、权限与启动入口，不固定产物保存路径；局域网仍由 `NetworkGateway` 使用相同 ENet 协议，Android声明`INTERNET`与网络状态权限。

## 事件运行时边界

`EventScheduler` 是所有可暂停规则流程的唯一运行入口。事件内容步骤接收 `(GameEvent, EventScheduler)`，通过 `create_child()` 插入主体子事件，通过 `create_event(..., queue="after")` 插入收尾事件；父事件在子事件和暂停 token 全部完成前不会推进步骤。长期 `RootGameEvent` 使用 `held_open=true` 留在栈底，空闲状态为 `waiting_children`，不会把生命周期等待误当作暂停。`finish()`、`cancel()`、`neutralize()` 和 `abort()` 具有不同的回放与触发语义，不能用单个 `cancelled` 布尔值替代。

`ChoiceRequest` 的请求 ID、事件 ID、响应者、候选 UID、选择数量和 `base_context/active_context` 由权威端保存。技能临时替换选择上下文必须使用 `backup_context()`，取消或 AI 失败时使用 `restore_context()`；UI、AI、网络都提交 `ChoiceResponse`，迟到或跨事件响应会被拒绝。现有 `PlayerAction.choose_cards` 是桌面兼容封装，控制器会在边界转换成同一 `ChoiceResponse`。

`CardMovementService` 是迁移期的唯一实体牌移动入口。新代码必须传递 `event_id`、`reason` 和 `visible_to`，不得直接写入牌的 `zone/owner_id` 或同时修改多个区域数组。尚未迁移的旧规则操作只允许通过控制器兼容函数调用，并应在后续版本移除。

`CardUseEvent` 已是可暂停的真实调度栈父事件。实体材料先在 `lose` 子事件进入 `processing`，随后依次执行 `useCard0/useCard1/yingbian/useCard2/useCard`。四组目标时机采用“阶段优先、每次执行后重新读取目标数组”的 `redo` 循环：全部当前目标完成 `useCardToPlayer` 后才进入 `useCardToTarget`、`useCardToPlayered` 和 `useCardToTargeted`；每轮按当前行动座次生成遍历副本，并按目标出现次数判断是否已经触发，因此动态新增目标会补齐当前及后续时机。死亡、离场或 `excluded` 目标不会进入虚假 `content`。`directHit`、`excluded` 和 `customArgs` 保存在父事件共享上下文，直击同时限制【闪】和【无懈可击】响应。每个实际目标拥有独立 `content` 子事件，响应与装备选择直接挂在该事件下；全部同步效果和暂停 token 完成后只创建1次 `contentAfter`。响应牌不建立第二个 `CardUseEvent`，而是派发 `respondBefore/respondBegin/respond/respondEnd/respondAfter`；因此需要同时覆盖普通使用与响应使用的技能应订阅 `useCard` 和 `respond`，再按定义类别统一过滤。默认弃置通过 `CardUseEvent.after -> orderingDiscard -> cardsDiscard` 移出处理区，终局中断时不会提前回收。判定继续使用 `judge -> judgeResult -> cardsDiscard` 关系，判定牌先从牌堆进入 `processing` 并公开表现，再进入弃牌堆。

当前状态：当前标准身份局已登记卡牌的使用生命周期、逐目标效果、响应选择与处理区回收已经进入真实事件树；选择请求、暂停 token、触发排序、查询修正、虚拟牌、技能延迟结算、阶段生命周期游标和移牌历史均可关联稳定父事件。局域网 ENet 房间已经提供权威房主、成员大厅、私有快照、掉线 AI 托管与携会话令牌的对局内断线重连；公网匹配、主机迁移和回放执行器仍未提供。宏观六阶段主体、伤害、濒死、死亡与部分判定流程仍包含同步兼容段。因此“当前标准卡牌使用流程完成事件化并可局域网游玩”不等于“无名杀全部模式、武将和扩展包已完整复刻”。

## 停滞自修复边界

`StallWatchdogService` 是挂载在 `MatchController` 下的独立看门狗组件（缺失时由控制器兜底创建），采用与其他组件相同的解耦边界：只调用控制器三个公开端口，不直接读写事件栈、请求索引或玩法状态。

- `get_stall_diagnostics()`：返回“是否可监控、是否有人类待办、进度指纹”。进度指纹覆盖对局ID、动作序号、事件历史条数、待办请求（含修订号）、活动暂停令牌、兼容选择与同时无懈数量、AI调度标记、流程任务、机缘进度、换将过渡与判定标志；任何真实推进都会改变指纹。局域网客户端（非权威）与终局不监控；用户主动打开日志或武将详情造成的对局暂停不监控，机缘选择暂停仍继续监控。
- `is_waiting_for_human_input()`：判定是否存在“可以实际作答的人类”待办。AI、托管、死亡与无人认领座位不算人类待办；离场但存活的角色仍可作答。座位归属判定：离线模式为本地第一视角或控全接管，局域网房主模式为本机或已映射远端 peer。该函数为真时看门狗永远不会执行强制修复。
- `perform_stall_self_repair(repair_kind)`：执行分级修复并返回可序列化报告。`human_reminder` 只重发界面提示；`soft` 只重排既有异步任务（预开局AI统一分派 `_redrive_pre_game_ai_progress`、AI兼容选择重排、同时无懈AI计时器重启 `_redrive_pending_negation_ai_tasks`、机缘结算轻推）；`hard` 在软修复之上追加：孤儿暂停令牌清扫 `_release_orphan_runtime_pause_tokens`（gameplay/conquest_replacement按权威标志、choice按待办请求、未知通道按所属事件终态判定）、无人认领存活座位转入标准托管、死亡应答者待办关闭 `_close_unanswerable_choice_requests`（无懈走标准放弃提交，其余走统一中断保护）、连续两轮硬修复仍卡住的AI兼容请求强制中断。修复前后指纹对比决定“有效”；只有有效修复才写入对局日志并发出 `self_repair_performed` 信号，由牌桌经 `InformationBoxLayer.show_notice()` 显示提醒横幅。

看门狗以 `PROCESS_MODE_ALWAYS` 运行（机缘选择等待期间场景树暂停，而这正是需要监控的窗口），检测节奏与三级阈值全部为 `@export` 参数。托管接管、暂停恢复与看门狗软修复共用同一预开局AI分派与无懈重排入口，避免多份阶段清单彼此漂移；机缘代选统一走 `OpportunitySystem.choose_for_managed_player()`（AI估值+权威 `submit_choice` 复核），不形成第二条写路径。

## 对局模式

- 标准身份局 `identity` 与斗地主 `doudizhu` 共用 `MatchController` / `IdentityRules`。
- 机缘大乱斗 `opportunity_brawl` 是独立模式 ID，支持2至10人并继承身份分配、胜负、死亡奖惩与选将规则；只有该模式默认启用 `OpportunitySystem`，普通身份局保持原规则。
- 1v1车轮战 `wheel_duel` 由独立 `WheelDuelSelectionService` 管理公共候选槽、明暗可见性、`122221` 抓将游标、双方私有五将集合与最终三将顺序；槽位被选后写入 `picked_by_player_id` 而不从池中移除，观察者快照只投射 `self/opponent` 相对归属并保持槽位原始明暗状态，暗置槽仍不公开真实武将ID。该服务不读取牌堆、体力、技能实例或UI节点。
- 过关斩将 `conquest` 由独立 `ConquestModeService` 集中维护关卡、难度、逐玩家复活次数与全局敌方机缘历史。角色总数支持2（离线单人：1玩家+1敌人）与4/6/8（局域网2至4名玩家+等量敌人），座次按“玩家1、敌人1、玩家2、敌人2”交替且偶红奇蓝；`configure_participants()` 接收玩家与敌人ID数组并为每名玩家独立授予难度机缘，旧 `configure()` 单人签名与旧存档标量字段（`player_id/enemy_player_id/player_revives_remaining`）继续通过回退读取保持兼容。关卡奖励写入全体敌人的公开机缘历史，控制器把体力上限增量、手牌上限重算与新技能安装同步给在场存活敌人；胜负规则为全部红方玩家死亡才判蓝方胜。联机局的初始与换将机缘经 `MatchController._begin_conquest_group_opportunity()` 按 `match_options.conquest_opportunity_choice_mode` 分流为投票或各自选择；临时退出存档仍仅限离线单人局。
- 模式选择保存在 `GameSettings.next_match_mode`，开局锁定到 `GameState.match_mode`。
- 身份分配、胜负、队友关系、模式技能与开局体力加值集中在 `IdentityRules`，控制器只负责执行移动与安装。
- `PlayerState.wheel_duel_lineup`、`wheel_duel_lineup_index` 与 `wheel_duel_defeated_count` 保存对战阶段最小权威进度。完整阵容只进入本人或权威快照，公共快照只暴露当前已亮武将与累计阵亡数。
- 车轮战换将由 `MatchController` 编排区域移动、武将应用、单玩家技能重装、补满体力、摸4张与当前回合中断；胜负仍由 `IdentityRules.evaluate_winner()` 统一返回，避免选将服务或界面直接结束游戏。

### 机缘组件边界

- `OpportunityCatalog` 只保存102张机缘卡的稳定 ID、品质、主公钦定正文和可序列化效果参数，其中5张灰色机缘仅由过关斩将关卡或难度授予；目录不读取对局状态，也不执行任何效果。首次查询建立稳定ID和品质索引；完整定义接口继续返回独立副本，高频规则使用 `has_card/get_effect_id/get_effect_count/get_skill_id` 读取不可变标量。玩家机缘效果按只追加历史增量汇总；红色刷新机缘例外地通过控制器端口整体替换历史并主动失效缓存、重装机缘来源技能、按差额调整体力上限与额外手牌上限，过关斩将服务则在每次奖励追加后统一重建敌方ID、效果合计与有限技能机缘缓存，同一关内伤害、摸牌、次数、换将技能恢复均不再扫描完整历史或深复制定义。新增的单体翻面与全体其他角色翻面效果由解析器排入可暂停队列，逐名调用控制器公开翻面端口，嵌套结算结束后才继续下一张机缘。
- `OpportunitySystem` 是可插拔场景组件，负责每轮 `1/N` 同概率检定、轮末保底、每人私有三选一、选择暂停令牌和从当前回合角色开始的逆时针结算队列。`force_trigger_vote_for_players()` 提供“投票选择”流程：只抽取一组共享候选并复制给每名参与者，逐人经同一 `submit_choice` 投票，全部提交后按票数取最高者（平票用对局随机源在同票中随机），当选机缘写入每名存活参与者的公开历史并逐人结算；`opportunity_state.vote_mode` 是公共快照标志，计票摘要写入 `opportunity_vote_result` 随机历史，单参与者时行为与各自选择一致。额外回合不进行触发检定；同一轮成功触发后不再重复触发。组件按局缓存五种随机品质的ID池，随机历史只保存候选ID；连续AI选择合并状态广播，同步效果的结算者游标不单独触发整桌刷新。
- `GameState.to_dict()` 对普通观察者先复制机缘公共字段，再只投射该观察者的3张私有候选，不会先深复制全体2至10名角色的候选后再删除。已选完整机缘定义保留在组件私有结算映射，`opportunity_state` 只承担公共进度与权威候选交互。
- `OpportunityEffectResolver` 只把机缘效果转换为 `MatchController` 的摸牌、体力、伤害、区域选牌、技能授予、座位/武将牌/手牌/装备交换、虚拟用牌、持续视为、限时离场、分类取牌与额外回合公开端口。批量实体移动按稳定UID逐张执行，目标选择、濒死、装备触发等嵌套流程通过 `defer_opportunity_resolution()` 和 `has_nested_settlement_barrier()` 完成后再继续下一张机缘。
- `MatchController.swap_player_seats()` 交换 `GameState.players` 中两名完整角色对象而不改变稳定玩家 ID；当前回合角色仍按 ID 保持，回合结束后从交换后的座次数组寻找下一名角色，因此座位变化会立即影响后续行动顺序。
- `grant_acquired_skill()`、`can_use_acquired_skill()`、`consume_acquired_skill_use()` 与 `remove_acquired_skill()` 组成局内技能生命周期端口；相同技能不重复安装，每回合限制按全局 `turn_number` 重置，累计限制在本次成功发动完整生效后移除技能。

### 过关斩将存档边界

- `ConquestSaveStore` 是纯静态持久化边界（`scripts/core/conquest_save_store.gd`）：只负责把控制器生成的可序列化存档字典写入 `user://conquest_save.dat`、读取并做版本/模式基础校验、以及清除文件；使用 `var_to_str` 文本格式完整保留64位整数与类型化数组，不读取 `GameState`、不理解规则语义、不持有节点。当前存档格式版本为1，版本不符或无法解析的文件统一按无存档处理。所有函数都接受可选路径参数，回归测试使用独立测试路径，绝不触碰玩家真实存档。
- `MatchController` 提供四个临时退出端口：`supports_conquest_temporary_exit()`（仅离线进行中的过关斩将）、`request_conquest_temporary_exit()`、`cancel_conquest_temporary_exit()` 与 `is_conquest_temporary_exit_requested()`。请求入口先尝试立即捕获，失败时只设置控制器私有挂起标志并写日志，不中断任何进行中的结算。
- 存档捕获共用同一空闲判定 `_is_conquest_settlement_quiescent()`（处理区、濒死队列、机缘流程、待办选择与判定、活动卡牌结算、延后技能结算、规则续接、待派发触发、伤害收尾、装备触发队列、回合尾部等待、独立阶段与额外弃牌阶段全部为空），并存在两级捕获点：
  - **出牌询问空闲点** `_try_capture_conquest_temporary_exit_at_play_idle()`：请求时若当前处于出牌阶段且空闲判定通过（另加技能多步间隔与已排队阶段切换检查），先以系统响应关闭常驻 `chooseToUse` 并排空事件树，再以 `resume_kind="play_phase"` 捕获。同一函数也挂在 `_begin_play_choice()` 顶部——每次操作结算完成、出牌询问即将重建时就是“操作后”的最近空闲点。常驻询问不属于结算，恢复时按当时合法动作原样重建，因此存档仍不需要序列化事件栈或选择请求。
  - **回合边界** `_try_capture_conquest_temporary_exit()`：挂在 `_start_turn` 入口，以 `resume_kind="turn_start"` 捕获尚未开始的下一回合。额外回合链的进度已随 `turn_flow` 入档，边界捕获不再要求额外回合队列为空；换将过渡仍然阻塞。
  - 两类捕获都递增 `_ai_drive_token` 作废旧AI计时器、消费挂起标志、由 `_build_conquest_save_data(resume_kind, acting_player_id)` 构建存档并发出 `conquest_exit_save_ready(save_data)`。文件写入与返回主菜单由牌桌在信号回调中完成（写档后延迟一帧调用标准主菜单返回流程），规则核心不接触文件系统。
- 存档内容：`conquest_state` 全量、双方 `PlayerState.to_dict(本人, reveal_private)` 加每回合字段与完整回合/响应/伤害历史、摸牌堆与弃牌堆完整顺序、`match_options`、轮数/回合数/动作序号、恢复类型与行动角色、`phase_index`、`turn_flow`（额外回合链、额外出牌阶段计数/返回点/活动上下文、主要阶段转换、阶段生命周期游标、本回合用牌记录）、`CardInstance._next_uid`、随机源种子与内部状态，以及 `_capture_skill_runtime_states()` 反射捕获的全部技能实例可序列化脚本变量（限定技已用标记、每轮限次记录等跨回合状态；Object/Callable 等引用类型自动过滤，由恢复流程的 bind/install 重新建立）。
- `resume_conquest_match(save_data)` 与 `start_match()` 共用三个运行时重建入口：`_teardown_previous_match_runtime()`（上一局清理）、`_rebuild_match_rule_services_and_root_event()`（规则服务与长期根事件）与 `_reset_per_match_progress_state()`（每局私有游标），保证两条开局路径的清理与重建清单不彼此漂移。恢复路径跳过选将、起始手牌与手气卡：直接以 `PlayerState.from_authoritative_dict()` 重建双方角色与牌区、按存档顺序重建两个公共牌堆、`ConquestModeService.restore()` 绑定既有 `conquest_state` 而不重建关卡历史、`_restore_conquest_turn_flow_state()` 回填全部回合与阶段游标、`_install_all_character_skills()` 重装固有与模式技能、`_reinstall_saved_runtime_skills()` 补装获得/临时技能实例（保留存档限次记录）、`_apply_skill_runtime_states()` 回写技能内部状态。最后按恢复类型分流：`turn_start` 调用 `_start_turn(存档行动角色)` 开始下一回合；`play_phase` 恢复当前角色与出牌阶段、新建回合运行时事件并把恢复的阶段生命周期重挂到该事件（`_remap_restored_phase_lifecycle_parents()`），再经 `_begin_play_choice()` 与统一AI安全出口继续同一回合，不发生摸牌或阶段时机重放。恢复前 `get_conquest_resume_validation_error()` 在破坏旧状态之前完成深层校验：版本、模式、离线、恢复类型合法、行动角色存活、双方武将与全部实体牌（含视为牌原始定义）在当前目录中的存在性。
- 存档生命周期由界面层维护：过关斩将终局（`match_finished`）清除存档；全新过关斩将开局（主菜单或局内重开走 `start_match`）清除存档；恢复失败清除存档并提示。恢复成功不清除，未再次临时退出便放弃对局时保留旧检查点。主菜单按“选中过关斩将且存档可解析”切换主按钮文字，牌桌以同一条件分流“继续”与“新开局”，二者判断来源一致。

## 离场与内容扩展架构

`PlayerState.out_of_game` 是临时离场的唯一权威状态，不创建“半死亡”角色或 UI 专用状态。`out_of_game_until_round` 只记录“离场直到本轮结束”的自动返场轮数，默认 `-1` 表示普通离场且不自动返回。`GameState.get_alive_players()`、`get_next_alive_player()`、`get_previous_alive_player()`、`CardRuleService`、`MatchController`、`SlashCardEffect` 与 `SkillDefinition` 分层过滤离场状态：状态层处理下家与上家座次，规则层拒绝普通用牌和目标，控制器拒绝普通动作和资源变化，效果层中止已失效目标，技能基类停止普通订阅。离场技与机缘只通过明确参数获得严格限定的选择、虚拟用牌或资源例外，不会放宽其他角色的普通操作。

牌堆观看与排序由三个控制器端口组成：私有快照、按 UID 获得、按 UID 重排。它们不保存 UI 引用，也不把观看牌提前移入公共处理区。`choice_type="arrange"` 将顺序与顶行长度编码到 `ChoiceResponse`，`CardSelectionPanel` 只是该通用协议的一个视图实现，后续观星、预知和换序效果可直接复用。目标区域选牌同样保持视图通用性：【过河拆桥】与【顺手牵羊】只在规则上下文区分弃置/获得，窗口均使用固定尺寸、纵向区域与纵向滚动。面板只转发明置 `CardView` 的 `information_requested/information_dismissed`，牌桌再接入唯一 `InformationBoxLayer`；因此选择组件不持有信息框实例，也不会从牌背构造隐藏信息。

无材料虚拟牌沿用 `CardUseEvent`，但逻辑代理与实体材料严格分离。`VirtualCard.material_card_uids=[]` 表示没有实体费用；`virtual_proxy=true` 时 `lose` 子事件只处理真实材料数组。该约定让主动视为牌、响应视为牌、日志、时机、目标结算与回放保持同一事件树，且不会把代理牌错误当作玩家区域内的材料。

新内容的规则修正优先放入 `SkillDefinition` 的纯查询钩子，例如距离解除、外部弃置保护和无材料响应定义。`MatchController` 仅负责汇总实例和执行二次校验，`CardRuleService` 保持不依赖具体武将 ID；这使技能组件可独立安装、卸载、测试和复用。
