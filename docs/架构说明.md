# 架构说明

## 总体原则

项目采用单向依赖的五层结构：静态数据层负责声明内容，状态与规则层负责权威结算，事件运行时负责嵌套、暂停和恢复，动作协议层统一外部输入，AI/网络适配层提供不同操作来源，UI 层只渲染快照并提交动作。任何界面、AI 或网络模块都不得直接改写 `GameState`。

```text
JSON 配置
  ↓
GameDatabase → CardInstance / PlayerState / GameState
                         ↓
PlayerAction / ChoiceResponse → MatchController → EventScheduler → CharacterSelectionService / CardRuleService / CardEffectResolver / IdentityRules
                         ↓
             TriggerManager + RuleModifierPipeline + CardMovementService + 状态快照
                ↙          ↓          ↘
              UI       AICoordinator   NetworkGateway
```

## 模块职责

### 自动加载节点

- `GameSettings`：保存全局卡牌名称模式。它不保存对局状态，切换后通过信号通知界面刷新。
- `GameDatabase`：读取并校验卡牌、牌堆、势力、武将和技能 JSON。配置通过唯一 ID 建立索引，调用方获得深拷贝；势力索引只保存牌面名称、简称和颜色，不参与身份局胜负判定。

### 数据结构

- `CardInstance`：实体牌 UID、配置 ID、花色、点数、区域和所有者。
- `PlayerState`：身份、武将、武将公开状态、体力、存活状态、手牌、装备区、判定区、连环状态、回合标记和木牛“粮”。
- `GameState`：玩家数组、摸牌堆、弃牌堆、处理区、当前阶段、回合数、动作序号与胜负状态。
- `PlayerAction`：统一操作结构，当前支持 `select_character`、`use_card`、`recast_card`、`store_wooden_ox` 和 `end_play`。
- `VirtualCard`：逻辑牌与实体材料牌 UID 的分离描述，支持视为牌、属性和扩展存储。
- `ChoiceRequest / ChoiceResponse`：统一 use/respond/card/target/button/control/discard 选择协议；请求保存 base/active 上下文，响应只包含可序列化 ID。
- `CardMoveEvent`：实体牌移动的来源、目的、关联事件、可见者和原因记录。
- `GameState` 额外保存根事件 ID、事件历史、移牌历史、随机种子、轮数、濒死队列和终局原因；快照会裁剪非响应者的私有选择候选。

### 权威规则层

- `MatchController`：创建对局、推进阶段、执行区域移动、处理判定、伤害、濒死、死亡、连环、奖惩和胜负。
- `CardRuleService`：只做距离、攻击范围、次数、目标、区域和延时锦囊同名校验，不执行效果。
- `CardEffectResolver`：按 `effect_id` 执行基本牌、锦囊和装备效果，只通过控制器公开的规则操作端口改变状态。
- `IdentityRules`：集中维护 2 至 10 人身份表、胜负条件和死亡奖惩类型；控制器对完整身份表洗牌，不为主公保留固定座次。
- `CharacterSelectionService`：纯数据选将状态机，集中维护主公先选、其他玩家同时选、每人随机候选、候选私密性与统一完成条件。它不加载界面、不注册 AI，也不修改卡牌区域。
- `RuleEventBus`：按优先级同步派发 `RuleEvent`。武将技能、装备扩展和模式规则可订阅事件，不需反向引用控制器。
- `EventScheduler`：维护根事件、事件栈、`next`/`after` 队列、步骤游标、`goto`/`redo`、多通道暂停 token、选择请求与终局中断。事件状态区分 `finished`、`cancelled`、`neutralized` 和 `aborted`。
- `TriggerManager`：按 `firstDo/lastDo`、技能优先级、起始座次和注册顺序排列触发器，并在执行前重新检查动态条件。
- `RuleModifierPipeline`：独立于触发器的纯查询修正链，供 `RuleQuery` 实现 card/target enabled、usable、respondable 和 in-range 查询。
- `RuleQuery`：只读合法性门面；不创建选择、不移动牌、不消耗次数。
- `CardMovementService`：统一维护实体牌区域和牌面知识，追加 `CardMoveEvent` 历史；控制器的旧区域操作正在通过该边界迁移。

### 外部适配层

- `AICoordinator`：管理玩家与 AI 策略映射，把权威完整快照和合法动作交给策略选择。
- `BasicAIPolicy`：示例启发式策略。它不能修改状态，只返回可序列化动作。
- `NetworkGateway`：封装离线、局域网和远程模式的消息协议、序号与收发信号。
- `match_table.gd`：桌面协调器，只渲染本地裁剪快照、维护出牌临时选择、读取只读规则预览并构建 `PlayerAction`；菜单布局和选将候选布局由独立组件负责。
- `card_view.gd`：以 `Node2D` 为根的单张实体牌组件，只处理牌面和选中反馈；`card_input_area.gd` 负责点击、悬停与拖放协议。
- `player_target_view.gd`：以 `Node2D` 为根的全玩家共用纵版武将牌组件，渲染势力、竖排武将名、体力圆点、手牌数、公开装备和目标反馈；`player_target_input_area.gd` 负责点击与卡牌拖放协议。
- `card_use_animation_layer.gd`：接管已经存在的正式 `CardView` 节点播放使用与弃牌表现；本地出牌直接移动手牌中的同一节点，隐藏牌则实例化同一正式场景。多次出牌拥有独立目标线，线条先从来源动态延伸到目标再淡出，中央卡牌按队列铺开并由单一淡出消费者依次移除。
- `match_menu.gd`：统一管理右上“菜单”、卡牌名称切换、重新开局与下一局人数输入；人数只在重开时传给控制器。组件在父场景初始化完成后提升真实 GUI 命中顺序，保证菜单面板不会被动态武将牌或选将遮罩抢占输入。
- `match_log_panel.gd`：只管理“记录”按钮与日志正文的折叠状态；日志内容仍来自规则核心的 `log_added` 信号，不读取或修改对局状态。
- `character_selection_panel.gd`：只渲染观察者可见的选将快照，以正式 `PlayerTargetView` 展示候选并提交稳定武将 ID。
- `skill_button_view.gd`：武将技能元数据展示组件，只发出技能 ID 请求，不调用规则效果。
- `artwork_loader.gd`：卡牌与武将共用的可选插画加载边界，只返回 `Texture2D` 或空值。
- `battle_ui_style.gd`：动态 UI 的统一样式工厂，集中维护颜色、圆角、描边、内容边距与阴影。
- `decade_battle_layout.gd`：无状态座次布局组件，只消费角色视图数组和总人数，按无名杀百分比模板写入 Control 几何信息。全屏容器自身使用 `MOUSE_FILTER_IGNORE`，输入只由动态武将牌子节点处理。
- `decade_hand_container.gd`：无状态手牌容器，只根据子节点数量和可视宽度计算重叠、抬升与滚动范围。

`assets/ui/table_ornament.svg` 是代码仓库内的矢量桌面装饰资源。它不包含输入或规则逻辑，可由后续主题资源替换；中央牌堆与阶段区域的数据仍只来自本地裁剪快照。

`MatchController.get_card_use_preview()` 是 UI 使用的只读查询边界。它返回当前卡牌是否可提交、合法候选目标、规范化目标、目标模式和说明文本，不返回 `GameState`、`PlayerState` 或 `CardInstance` 对象引用。点击出牌与拖拽出牌最终仍统一构造 `PlayerAction` 并进入 `submit_action()`。

座次与手牌排版不再由 `match_table.gd` 保存像素表。桌面先把绝对座次数组旋转为“本地下家至本地上家”的相对顺序，再把动态视图交给布局组件；布局组件不认识玩家身份、卡牌效果、阶段或动作协议，因此本地座次随机化不会改变环桌行动方向。

技能栏通过 `GameDatabase.get_skill()` 读取技能元数据深拷贝。预留技能点击只更新界面说明；实际技能必须由独立规则组件实现，并通过标准动作或 `RuleEventBus` 接入，不能由 `SkillButtonView` 或 `match_table.gd` 直接修改状态。

插画路径属于静态表现元数据，不写入 `CardInstance` 或对局快照。`CardView` 和全玩家共用的 `PlayerTargetView` 只把数据定义的 `art_path` 交给 `ArtworkLoader`，因此插画缺失不会影响规则层、AI 或网络层。本地玩家与其他玩家使用同一武将牌类和148.35×197.8像素的3:4原生场景规格，差异仅来自布局位置和快照可见性；武将信息控件保持原尺寸，仅牌框与插画宽度增大。正式卡牌统一为111×148像素的3:4规格。

## 开局与选将边界

`MatchController.start_match()` 只创建身份、空武将玩家状态和牌堆，然后把阶段设为 `character_selection`。标准身份局使用同一对局随机源先为本地人类玩家分配有效座次，再对包含主公的完整身份池洗牌，因而本地玩家、主公和一号位三者互不绑定。主公先获得候选并单独确认，控制器立即把主公武将写入 `PlayerState` 且公开；随后其他玩家各自同时确认，具体选择在所有人完成前不进入其他观察者快照。全员完成后控制器统一公开非主公武将、按武将配置初始化体力、每人摸4张起始手牌，并直接查找唯一主公开始首回合；预留的 `first_turn_seat_number` 不参与标准身份局顺序判定。只有对局人数不少于5人时，主公才在武将基础体力上限上增加1点。

`CardRuleService.normalize_targets()` 是多目标的统一权威顺序入口。群体目标牌从使用者开始按环形行动顺序展开：`all_players` 先结算使用者本人，`all_others` 先结算使用者的下一名存活角色；方天画戟和铁索连环等手动多目标牌也在提交后按相同行动顺序重排，只有【借刀杀人】保留“持刀者、被杀者”的双目标语义顺序。【无懈可击】每轮询问、连环传导与濒死救援首次询问都从当前回合角色开始按存活座次进行；若一名濒死响应者回复后目标仍未脱离濒死，下一轮从该响应者重新开始。

死亡结算先标记死亡并亮出身份，然后立即调用 `IdentityRules.evaluate_winner()`。若已满足胜负条件，`GameState.game_over` 会成为规则操作与 `CardEffectResolver` 的统一终止条件：当前死亡弃牌、奖惩、群体牌后续目标、响应、伤害、回复、摸牌及使用牌结束区域移动全部停止。若对局继续，则清理死者区域并执行击杀奖惩。当前回合角色在自己行为的插入结算中死亡时，当前事件完整结算后直接从其下名存活角色开始新回合；若死于开始阶段事件或判定阶段，则由 `_start_turn()` 在该阶段结算返回后执行同一转交，不会停留在死亡角色的回合。

候选数量由 `MatchController.character_candidate_count` 前置配置，默认 5，实际不超过已登记武将数量。人类、AI 和网络玩家都提交 `select_character` 标准动作；任何适配层都不能直接写 `character_id`、`character_revealed`、`hp` 或 `max_hp`。

## 触发事件

当前核心提供以下长期稳定事件名：

- `phase_start`：回合开始阶段。
- `phase_finish`：回合结束阶段。
- `card_used`：实体牌进入处理区并声明目标后。
- `damage_before`：伤害扣减前，可修改 `amount` 或取消。
- `damage_after`：伤害扣减后、濒死结算前。
- `recover_after`：实际回复完成后。
- `dying_begin`：角色进入濒死流程时。

技能组件通过 `RuleEventBus.subscribe(event_name, owner, callback, priority)` 注册，组件卸载时使用 `unsubscribe_owner(owner)` 清理。优先级数值越大越先执行。

## 状态可见性

`GameState.to_dict(viewer_id, reveal_private)` 是唯一快照入口：

- 本人可见自己的身份、手牌与木牛“粮”。
- 本人可见自己已经确认的武将；主公确认后立即对所有人可见，其他玩家在全员完成选将后同时公开。
- 他人只看到手牌数量和“粮”数量。
- 装备区、判定区、体力、存活与连环状态始终公开。
- `reveal_private=true` 仅供权威 AI、服务器调试与回放使用。

## 设计边界

工程不实现国战身份、势力明置、双将、暗将和国战专属牌。样例武将技能当前只提供数据接口，不批量实现角色库。所有后续扩展应新增配置或独立组件，避免把角色 ID、UI 节点或网络模式硬编码进规则服务。

## 事件运行时边界

`EventScheduler` 是所有可暂停规则流程的唯一运行入口。事件内容步骤接收 `(GameEvent, EventScheduler)`，通过 `create_child()` 插入主体子事件，通过 `create_event(..., queue="after")` 插入收尾事件；父事件在子事件和暂停 token 全部完成前不会推进步骤。`finish()`、`cancel()`、`neutralize()` 和 `abort()` 具有不同的回放与触发语义，不能用单个 `cancelled` 布尔值替代。

`ChoiceRequest` 的请求 ID、事件 ID、响应者、候选 UID、选择数量和 `base_context/active_context` 由权威端保存。技能临时替换选择上下文必须使用 `backup_context()`，取消或 AI 失败时使用 `restore_context()`；UI、AI、网络都提交 `ChoiceResponse`，迟到或跨事件响应会被拒绝。现有 `PlayerAction.choose_cards` 是桌面兼容封装，控制器会在边界转换成同一 `ChoiceResponse`。

`CardMovementService` 是迁移期的唯一实体牌移动入口。新代码必须传递 `event_id`、`reason` 和 `visible_to`，不得直接写入牌的 `zone/owner_id` 或同时修改多个区域数组。尚未迁移的旧规则操作只允许通过控制器兼容函数调用，并应在后续版本移除。

当前状态：事件树、选择请求、暂停 token、触发排序、查询修正、虚拟牌和移牌历史已经接入基础身份局流程；阶段、卡牌、响应、伤害、濒死与死亡已生成稳定事件摘要。完整角色技能库、真实联机传输和全部卡牌效果的逐目标事件化仍处于迁移中，项目状态应描述为“事件化迁移中、规则部分等价”。
