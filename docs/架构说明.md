# 架构说明

## 战斗结算入口

运行时与内容协议见[战斗结算框架](战斗结算框架.md)。`EventScheduler` 管父子所有权，`TriggerManager` 管排序，`RuleStepSequence` 管可暂停内容游标，`DamageResolutionService` 管伤害步骤，控制器保留权威写入和兼容协调。步骤仍由原 `RuleContinuationQueue` 调度，没有第二套主循环。

伤害修改窗口和卡牌生命周期等待时机及子选择完成，再应用最终结果；宏观阶段、濒死/死亡和部分判定仍有兼容段。技能顺序效果优先使用 `run_steps()`；复杂响应、额外阶段与虚拟牌结果继续遵守正式恢复接口。

## 终局统计与结算表现边界

- `PlayerState` 保存并序列化 `total_damage_dealt`、`total_damage_received`、`total_healing_done`、`total_cards_drawn`、`total_kill_count`。计数由 `MatchController` 的 `damage()`、`recover()`、`draw()` 与死亡分支在权威规则结算时更新；UI、AI和网络客户端均不自行从日志、体力差或牌区差推算。
- `GameSettlementPanel` 是独立的快照表现组件：输入为 `GameState.to_dict()` 中的 `players` 数组，输出为纯列表节点；不依赖模式、卡牌或技能实现。角色单元格只从公开 `character_id/display_name` 解析同一行“武将名（玩家名）”，武将资料缺失时回退玩家名。面板保留右上角1个关闭按钮，并在统计列表下方提供“保存回放”按钮；该按钮只发出 `save_replay_requested` 信号，回放数据采集与文件写入由牌桌持有的 `MatchReplayRecorder` 负责，面板不接触回放内容。`match_table.gd` 仅负责首个终局快照的自动打开、关闭后的抑制标记、终局按钮重开和主题刷新；其主菜单导航边界统一关闭结算面板并清空自动展示标记，局域网会话结束与主菜单可见性同步也复用该入口，防止高层模态残留。
- `MatchController.start_match(seed=0)` 统一调用 `_resolve_match_seed()`：自动路径混合Unix系统微秒、进程内单调微秒、进程号与控制器私有自增序号，使菜单重进、局内连续重开和完整退出重启都取得新的随机源；最终实际种子写入 `GameState.random_seed` 与身份启动事件。显式种子路径不混入自动分量但同样写入唯一随机源，继续支持确定性测试与回放。离线自动斗地主在玩家与身份都完成正常随机后，以控制器私有的上一局本地“座次索引+身份ID”作为防重复键；只有新结果完全相同时才从其他合法座次中按同一随机源改选，显式种子、固定座次和局域网映射不受影响。斗地主身份洗牌后不调用领袖座次旋转，首回合由地主身份单独查询。

## 总体原则

项目采用单向依赖的五层结构：静态数据层负责声明内容，状态与规则层负责权威结算，事件运行时负责嵌套、暂停和恢复，动作协议层统一外部输入，AI/网络适配层提供不同操作来源，UI 层只渲染快照并提交动作。任何界面、AI 或网络模块都不得直接改写 `GameState`。

```text
game_data 独立卡牌 / 武将 / 技能源码 + 牌堆 / 势力数据
  ↓
GameDatabase → CardInstance / PlayerState / GameState
                         ↓
PlayerAction / ChoiceResponse → MatchController → EventScheduler → CharacterSelectionService / CardRuleService / CardEffectResolver / IdentityRules
                         ↓
 RuleTimingCatalog → RuleTimingService + TriggerManager + RuleModifierPipeline + CardMovementService + 状态快照
                ↙          ↓          ↘
              UI       AICoordinator   NetworkGateway

OpportunityCatalog → OpportunitySystem → OpportunityEffectResolver → MatchController公开规则端口
```

## 模块职责

- 选将与目标顺序补充：`CharacterSelectionService` 的首次随机座次身份已进入权威 `PlayerState`；控制器在自选预览或每名玩家确认时即时投射完整座次身份，并且每名确认者的武将只应用一次，完成阶段不再重置已显示武将。`CardRuleService.normalize_targets()` 是普通多目标牌与虚拟牌的唯一顺时针规范化入口，只有拥有明确角色顺序语义的【借刀杀人】可保留请求顺序。

### 自动加载节点

- `GameSettings`：在 `user://game_settings.cfg`（格式版本1）持久化全局卡牌名称模式、背景音乐音量（默认0.8）与音效音量（默认0.9）以及全局静音开关（默认关闭，两项音量的取值范围均为0.00至1.00、步长0.05）、均为0.10至1.00秒且步长0.05秒的游戏流程间隔与 AI 响应延迟、当前 UI 风格 ID、默认开启的自动身份标记、下一局人数（身份2–10/斗地3或5/2v2固定4/过关斩将玩家数2–4）、六项房主开局规则、过关斩将难度与机缘选择方式（`conquest_opportunity_choice_mode`，稳定值 `vote` 投票选择或 `individual` 各自选择，默认投票），以及最长20字符的联机玩家名称和稳定武将形象 ID。速度设置直接按0.05秒取整，使0.10至1.00秒范围内的每个档位都可写入。手气卡数量只接受 `0/1/2/3/4/5/10/-1`，其中`-1`表示无限张；换将卡数量只接受 `0/3/5/8/10/20`，随机选将牌数限制为1至20。设置变化先更新内存，文件写入使用0.25秒单次计时器合并；应用进入后台或节点退出时强制刷新。卡牌名称与UI风格的重绘信号延迟到GUI输入结束后的空闲帧。它不保存颜色字典、身份推断、网络对等体、地址、密码、房间成员或对局状态。
- `GameDatabase`：自动扫描 `game_data/cards`、`game_data/characters`、`game_data/skills` 和 `game_data/effects` 的独立 GDScript 定义，并读取 `data/decks.json` 与 `game_data/factions.json`。编辑器目录中的`.gd`与导出PCK中的`.gd.remap`、`.gdc`、`.gde`都会规范化为原始`.gd`资源路径，因此Android导出后仍能登记完整卡牌、技能、角色持续效果和武将。卡牌、武将、技能与角色持续效果通过唯一 ID 建立元数据与源码索引，调用方获得深拷贝；目录新增文件不需要修改集中注册表。卡牌加载时额外建立原版名/项目名到定义的只读索引；`resolve_card_names_in_text()` 逐段扫描完整 `【】`，允许括号内文本精确匹配已登记牌的 `original_name` 或 `custom_name`，并直接映射为当前模式名称，普通文本与未登记括号内容保持原样。完整说明按名称模式缓存，每种模式最多512条，数据库重载时统一清空；`resolve_character_name()` 只返回不可变字符串，直接读取内部武将索引而不复制整份元数据。
- `GameDatabase.get_selectable_character_ids(include_special=false)`：普通选将、随机候选和模式换将共用的武将池边界。默认排除元数据 `special=true` 的特殊武将；完整静态目录仍保留特殊定义，只有特定规则显式传入 `true` 或指定稳定ID时才能生成。
- `AudioService`：音频表现层对外的唯一门面，不读取 `GameState`、`MatchController` 或任何技能运行时对象。它在就绪时通过 `AudioServer` 运行时创建 `BGM` 与 `SFX` 两条总线并挂到 `Master`，订阅 `GameSettings` 的音量与静音信号把线性音量换算为总线分贝，并把核心层下发的只读语音表现负载翻译为候选路径解析与播放调用，同时向界面层开放 `play_effect()` 端口，供终局胜负这类“每个客户端视角各自不同、不能走核心层广播”的效果音直接播放。零音量统一改用总线静音开关，避免把负无穷写入分贝属性。它内部装配三个无节点依赖的子组件：`AudioCatalog`（纯逻辑路径解析与音频流缓存；技能按角色专属四级短路，武将阵亡语音按武将专属两级短路，卡牌由“每张牌都播放的基础伴随音效 ＋ 按性别与名称体系逐级命中的专属配音”两层叠加，全局效果音则按固定标识在 `game_data/audio/effect` 下精确探测、不做任何近似回退）、`AudioVoicePlayer`（按需分配播放器、播放结束回收、池内随机且避免连续重复，不设并发上限与最小重播间隔）、`AudioBgmPlayer`（强制循环、场景切换淡入淡出、同场景重复请求幂等，并以 `PROCESS_MODE_ALWAYS` 保证记录面板、武将详情与机缘选择冻结场景树时背景音乐不中断）。全部素材按约定文件名自动发现，缺失时静默跳过。

### 内容源码层

- `CardDefinition`：单张卡牌的源码基类。具体卡牌文件同时保存静态信息、同步效果、共享上下文、目标组合校验、濒死救援、回合状态、异步恢复、延时判定、装备响应和主动动作钩子。`uses_immediate_equipment_response_prompt()/get_immediate_equipment_response_prompt()` 允许装备在普通响应候选前建立独立询问；`modify_ai_negation_effect_utility()` 允许复杂锦囊按来源、目标和团队后果修正无懈效用。使用次数、AI 牌值与收益方向也由卡牌元数据提供；新增卡牌不需要修改控制器、AI 白名单或集中结算器。装备主动动作支持**两段式**：`execute_play_phase_action()` 成功返回后，控制器才读取 `get_play_phase_follow_up_request()` 并创建第二段独立选择请求，响应经 `continue_equipment_selection()` 带着完整 `ChoiceResponse`（含 `target_ids`）回到同一卡牌文件。因此“先选牌确定、再选一名角色”的装备不需要在同一次提交里同时携带材料与目标，控制器也不认识任何具体装备 ID。
- `CharacterDefinition`：单名武将的源码基类。武将文件保存名称、性别、势力、体力与说明，并直接 `preload` `game_data/skills` 中的技能脚本。
- `SkillDefinition`：单个技能的源码基类。每名持有者获得独立实例；技能文件通过 `subscribe_timing` 注册带 `player/source/target/global` 关系的标准被动触发，基类会把内容条件与持有者有效性条件组合，普通技能在持有者死亡、离场或状态缺失后不再接收新时机。`out_of_game_skill=true` 明确声明离场技：持有者存活但离场时仍可接收时机、完成该技能自身的强制选择并参与纯查询修正，死亡后仍失效；一般临时离场恢复仍可覆盖 `can_trigger_while_owner_inactive(event)`。该覆盖只有两种合法用途：①持有者失效后完成**持续效果的到期清理**（真珠【补缀】在持有者阵亡后仍于轮末扣掉已发放的护盾）；②**仅由技能持有者本人承担、且必须在失效后补做的清理**（爻光【凶星】阵亡后清掉自己残留的“防止体力上限减少”额度，只放行 `dieAfter`）。两种用途都必须把放行范围收敛到该效果真正需要的时机，禁止无条件 `return true` 放行全部时机——否则失效持有者会连无关时机一起接收，等于绕过统一生存校验。非锁定技失效仍会压制这两类订阅，因为该检查只由 `maintenance=true` 跳过。**已经挂在目标身上的持续效果不使用本覆盖**：技能实例还会被换将整体卸载，放行覆盖救不了换将场景，因此这类效果统一由 `PlayerEffect`（`game_data/effects`）承载，与施加者的实例彻底解耦。每个实例还拥有默认0.0的非负浮点 `sell_blood_value`，1.0点按1张牌的统一资源价值修正友方或敌方造成伤害的AI收益，当前【百折】为1.0。技能通过 `enable` 声明 `phaseUse/chooseToUse/chooseToRespond/chooseCard` 主动入口，通过 `can_activate/activate` 实现主动技能，通过 `continue_choice/continue_selection/continue_response/continue_extra_phase` 恢复异步步骤与额外阶段。基类提供只选牌、只选目标、目标加文字选项、牌与目标组合等统一请求包装，并通过 `append_play_phase_actions/get_activation_preview` 提供 AI 动作与只读预览；`modify_ai_incoming_card_effect()` 允许目标技能以纯查询方式修正受到来牌后的预期结局，`modify_ai_lethal_damage_consequence()` 允许行动者技能以同样方式修正“自己击杀该目标”的规则后果（例如击杀奖惩被整体改写为摸四张牌），`modify_death_reward()` 则在规则侧真正替换 `MatchController.resolve_death_reward()` 给出的奖惩类型。`can_convert_response_card/get_converted_response_definition_id` 允许技能把当前拥有的实体材料转化为合法响应。主动单材料转化可复用 `get_owned_conversion_material_card()`、`build_virtual_rule_overrides()`、`validate_virtual_use_for_material()` 与 `build_virtual_target_selection_data()`，让真实材料颜色统一进入玩家候选、AI枚举和提交校验。`get_skill_player/get_owner_skill_player` 创建独立 `SkillPlayer` 角色操作对象，供技能使用 `who.shield`、`who.loseShield`、`who.loseHp` 与 `source.damage` 语法而不直接写入状态。
- 文件名使用小写拼音，并允许数字与下划线，例如【顺手牵羊】为 `game_data/cards/shunshouqianyang.gd`，扩展变体可使用 `shunshouqianyang_2.gd`。文件名负责维护定位，规则、网络与存档仍使用稳定 `id`。
- `PlayerEffect`：**角色持续效果**的源码基类，文件位于 `game_data/effects`，由 `GameDatabase` 自动扫描注册。它表达“一旦施加就属于被施加角色、与施放它的技能实例无关”的持续状态，因此刻意**不做**技能的三项校验：不比对武将代次、不检查“非锁定技失效”、不计算获得技能额度；承载角色只要存在且存活就继续接收时机。基类在 `install()` 中先登记“承载者死亡即回收”再转交 `install_effect()`，在 `uninstall()` 中先转交 `uninstall_effect()` 再统一退订，因此子类只覆盖 `install_effect()` / `uninstall_effect()` 而不会破坏回收链路。`has_persisted_state(player)` 是纯只读查询，对局开始与存档恢复由 `PlayerEffectService.restore_effects()` 依据它重建实例（重建只看角色自己的 `character_form_state`，**不要求施加者仍在场**，因此施加者换将或失去技能后效果依旧恢复）。实例由 `PlayerEffectService` 持有强引用：效果是 `RefCounted`，失去引用会被回收且订阅随之失效。内容侧通过 `MatchController.install_player_effect()/get_player_effect()/has_player_effect()/remove_player_effect()/clear_player_effects()` 转发端口协作。

### 数据结构

- `CardInstance`：实体牌 UID、配置 ID、花色、点数、区域和所有者，并保存互相独立的手牌临时牌名与 `hand_mark_tags`。手牌标记按来源保存标签、排序和规则覆写；统一移牌边界在实体成功离开当前持有者手牌区时清除，不改变原牌名或复制实体。多材料转化代理额外使用 `color_override` 保存聚合颜色，因为“红色无花色牌”无法只由 `suit` 表达；`get_color()` 优先读取该覆写，其余情况统一按 `color_of_suit()` 从花色推导，防具与来牌限制只能通过该入口读取颜色。
- `PlayerState`：身份、武将、武将公开状态、体力、护盾、存活状态、手牌、装备区、判定区、连环与翻面状态、回合标记、公开 `public_marks`、武将牌左上角文本条目和木牛“粮”。`face_down` 明确区分正面与背面；`abolished_equipment_slots` 保存五种单装备栏的公开废除事实，`equipment_area_abolished` 只派生表示五栏是否全部废除，`judgment_area_abolished` 独立表示判定区可用性，规则层与移牌边界共同拒绝向已废除栏位或区域放牌；旧权威存档只有整区布尔值时会迁移为五栏字典。`character_form_state` 只保存换形链的纯数据私有上下文，仅权威存档可见。`dynamic_skill_descriptions` 以技能稳定ID保存**当前显示正文**，只收录“进度与静态原文不同”的技能（例如【断界】被删除的选项），由控制器端口 `set_skill_display_description()` 写入并进入所有观察者快照；未收录的技能由界面回退 `GameDatabase` 的静态描述，正文中成对的 `[s]`…`[/s]` 标记由 `SkillDescriptionView` 渲染为**自绘加粗删除线**（字体内置删除线粗细不可设置且在本项目字体上几乎不可见，故按被划片段区间由覆盖层绘制 `STRIKE_THICKNESS` 像素的水平线）。`non_locked_skills_disabled` 由 `non_locked_skill_disable_sources` 的稳定来源记录派生，进入公开快照并支持多个失效来源叠加。`character_corner_text_entries` 以稳定来源ID保存可序列化 `text/order`，控制器排序、去重后写入只读合成字段 `character_corner_text`；技能不能直接覆盖合成字符串。【追歼】与【酩酊】使用来源唯一提示条目，而不使用 `public_marks`。【永劫】使用固定条目ID `eternal`，由 `ReincarnationSkillService` 在任一轮回技进入或退出永劫时统一重算，因此同一角色多个轮回技同时处于永劫也只显示1行，全部退出后移除。`public_marks` 只保存可序列化的单字图标、数量、说明、来源、来源技能、可选首牌族距离规则与顺序，由 `PlayerMarkService` 修改并进入所有观察者快照；其中 `source_player_id` 是死亡清理的唯一来源归属，跨角色标记不得省略。`wine_used` 与 `wine_bonus` 属于公开回合规则状态，进入所有观察者快照供酒杀表现与AI攻防评估；`auto_managed` 表示手动或掉线 AI 托管，`auto_managed_offline` 区分掉线托管并进入所有观察者快照；`acquired_skills` 保存机缘等局内来源获得的技能、每回合/每轮/总共次数与来源，`hand_limit_bonus` 保存可累加的额外手牌上限，最终手牌上限为 `max(hp + hand_limit_bonus, 0)`；`acquired_opportunity_ids` 仍是允许重复且只追加的公开权威历史，`opportunity_effect_totals_cache` 与处理游标只在权威端增量汇总其新增尾项，不进入快照、不构成第二份玩法状态；公开序列化仅在机缘历史长度或首尾哨兵变化时生成新的只读数组，不同观察者与重复广播共享该数组，正式整体替换接口会显式失效缓存，已经发出的旧快照不会被原地改写；护盾是公开非负整数，初始为0且不并入体力或体力上限；累计 `damage_taken_count` 让表现层识别护盾完全吸收的伤害，当前回合 `ai_failed_card_target_ids` 让 AI 避免重复无效牌目标。限定技运行时对象仍由控制器持有，广播前只向每名玩家快照补充公开 `used_limited_skill_ids` 稳定ID数组，UI与AI不得取得技能对象或用历史猜测复原后的额度。
- `PlayerState.reincarnation_skills`：按技能ID保存轮回数、当前轮回节、永劫与通用限次的公开权威状态；`card_use_limit_exempt_history` 与 `play_phase_card_use_limit_exempt_history` 只保存不计入限制的使用子集，完整用牌事实仍留在原历史。三类状态都进入权威存档和观察者快照，UI与AI不维护副本。
- `PlayerMarkService`：每局独立的公开标记状态组件。它负责标记数据规范化、`1..999` 数量限制、全场唯一标记转移、来源查询、通用“每个全局回合首张指定牌族忽略距离”声明查询与死亡尾部清理；不读取 UI、AI 或具体技能 ID。死亡清理同时清空死者自身标记和全场来源指向死者的标记。`MatchController` 提供设置、移除、查询、查找持有者和组合用牌事实历史的转发端口。
- `PlayerEffectService`：每局独立的**角色持续效果**托管组件。它按“承载角色ID → 效果ID → `PlayerEffect`”维护实例注册表并持有强引用，负责创建/复用、按 `has_persisted_state()` 重建、移除与整局清空；不读取任何具体技能或效果 ID，也不决定何时施加效果，因此新增效果不需要修改本服务或控制器。它额外记录订阅所属的高级触发器：对局重建会整体替换该对象，检测到替换时丢弃全部旧实例并重新登记，避免效果“看起来还在”却不再收到时机。`MatchController` 提供同名转发端口，并在 `_rebuild_match_rule_services_and_root_event()` 中重建服务、清空旧实例并按角色状态恢复效果。
- `ReincarnationSkillService`：每局独立的轮回技状态组件。它只维护轮回数、轮回节、永劫、永劫每回合次数和每节出牌阶段次数，并通过控制器派发四个轮回生命周期时机；不执行具体技能效果、不持有技能实例或界面节点。技能安装只登记静态节数，重复安装保留进度；完整技能复原才显式重置并解除永劫。
- `PlayerZoneAbolitionService`：每局独立的区域废除权威组件。它规范化装备栏数组，编排装备栏与判定区废除/恢复时机，调用控制器的标准弃牌端口，并写入日志和可回放历史；不读取卡牌定义、技能ID、AI或界面节点。`MatchController` 只暴露整区、单栏、判定区设置和只读查询转发，`CardRuleService` 与最终移牌端口分别承担预览和落地防线。
- `GameState`：玩家数组、摸牌堆、弃牌堆、处理区、当前阶段、回合数、动作序号与胜负状态；公开快照额外提供处理区实体 UID 集合，供表现层核对生命周期而不暴露可变对象。`opportunity_state` 保存机缘流程的阶段、并行待选集合 `pending_chooser_ids`、完成进度与权威候选（`current_chooser_id` 在全部模式中恒为 `-1`，仅保留给旧快照兼容）；`to_dict(viewer_id, false)` 在 `choosing` 阶段只保留该观察者自己的三张候选并移除已选卡正文，投票全部收齐进入 `revealing` 后才向所有观察者公开 `revealed_votes` 与 `winner_card_id`。快照中的模式技能查询复用一份无状态 `IdentityRules`，不再为2至10名玩家逐个创建临时规则对象。
- `PlayerAction`：统一操作结构。核心动作包括 `select_character`、`use_card`、`use_skill`、`recast_card`、`end_play`、`choose_opportunity` 和 `set_auto_managed`；`choose_opportunity` 只提交稳定机缘卡 ID，权威端统一按 `pending_chooser_ids` 成员资格复核（全部参与者同时开放，重复提交与名单外提交被拒绝，不再读取 `current_chooser_id`），并始终校验提交者本人的候选；`set_auto_managed` 仅允许真人修改自己的手动托管状态，装备主动动作名由对应卡牌文件动态声明，控制器不维护具体装备动作白名单。
- 离线“控制所有角色”由 `MatchController._prepare_offline_controlled_view()` 集中解析当前规则操作者，并通过 `_set_offline_manual_control_player()` 在运行期临时注销/恢复单名基础AI。开局创建玩家时仍只有最初本地玩家属于真人，其余角色保持AI，因此初次选将、车轮战选将与手气卡不受该开关影响。进入正式回合后才切换 `local_human_player_id` 并重新生成观察者快照；关闭开关立即恢复 `_primary_offline_human_player_id`，递增AI驱动令牌并通过统一续接入口重新安排当前选择或出牌动作，不复制玩家状态或创建多套牌桌。普通选择显式以 `chooser_id` 切换，并行无懈在本地依次发布，LAN模式强制关闭该能力。
- **与「回合操控」的关系与差异**：回合操控（`PlayerState.turn_input_delegate_id` + `begin/end_turn_input_delegation()`）是**独立于该设置的规则事实**，二者都复用 `_set_offline_manual_control_player()` 这唯一的第一视角落点，但**优先级与语义不同**——回合操控优先级更高，「控制所有角色」关闭时操控仍然生效；前者表达「谁提供本回合输入」（登记是权威规则事实、随快照与存档往返、到期由回合结束或死亡自动清理），后者只是本机的一个显示/操作偏好且 LAN 恒为关闭。为避免两套语义在同一字段上互相覆盖，控制器把「本机界面当前在操作谁」与「本机真人是谁」拆成两个值：`local_human_player_id`（会被上述两条路径改写）与离线影子值 `_offline_human_identity_id`（从不被接管改写），后者是识别操控者并完成归位的唯一依据。
- **规则字段位置**：操控事实存放在 `PlayerState.turn_input_delegate_id`（与 `public_marks`、`auto_managed` 同区），属公开事实，写入 `to_dict()` 公开部分与权威存档、并由 `from_authoritative_dict()` 恢复，因此观察者快照、AI 快照、回放重演与读档恢复四条通道自动往返。过程性的回合匹配索引 `MatchController._turn_input_delegation_turns` **不是权威**、不进快照也不进存档（性质同 `_extra_turn_queue`）。
- **局域网授权表的依赖方向**：`MatchController` 通过 `NetworkGateway.set_lan_proxy_actor_ids(peer_id, actor_ids)` **单向下发**「哪个 peer 可以代哪个 actor 提交」，网关只保存集合并提供只读查询 `is_lan_proxy_actor_authorized()`，**零规则语义**；因此本机制不引入网络层对规则层或 `GameState` 的反向依赖。授权表的唯一写点是操控登记的写入与清除路径，掉线时网关自行回收该 peer 的授权项。
- `VirtualCard`：逻辑牌与实体材料牌 UID 的分离描述，支持视为牌、属性、花色、颜色和扩展存储。多材料转化由 `resolve_suit_aggregate()` 与 `resolve_material_aggregate()` 统一聚合：全部材料同花色取该花色，同色不同花色取该颜色且无花色，异色或含无花色材料为无色；聚合结果同时写入逻辑描述与代理实体，保证表现、回放与规则读取同一事实。
- `SequentialVirtualSkillDefinition`：需要连续使用多张无材料虚拟牌的技能基类。它只保存可序列化队列与活动项，在 `useCardAfter/useCardCancelled` 后逐张继续；【天裁】和【弑魂】因此不复制响应、无懈或选择的暂停管线。
- `RuleContinuationQueue`：只保存稳定续接类型、可序列化上下文与统一结算因果链元数据的后进先出规则栈。同步规则在响应牌、费用牌、区域移动或回合开始时机已经成立后若插入新选择，只登记尚未执行的后半段；恢复时不重复消费实体牌、不重复发布已完成时机，也不保存 `Callable`、节点、`PlayerState` 或 `CardInstance` 引用。控制器在入栈时校验稳定类型白名单，子续接继承当前因果链的语义键访问次数与总步数，异常自我入栈只局部熔断。
- `ChoiceRequest / ChoiceResponse`：统一 `use/respond/card/target/target_control/card_target/button/control/discard/arrange` 选择协议；请求保存 base/active 上下文、各维度独立数量范围和可选牌到目标映射。`target_control` 在同一响应中同时校验目标数组与唯一控制项，避免拆成两个窗口产生状态竞态；私有展示牌只能放入请求响应者定向收到的 `context.display_candidates`，不得写回公共快照、实体 `shown` 或 `known_to`；响应只包含可序列化 ID。
- `CardMoveEvent`：实体牌移动的来源、目的、关联事件、可见者和原因记录。
- `CardPresentationEvent`：使用、展示和判定共用的只读表现事件，保存表现序号、规则事件 ID、事件名、牌快照、来源、目标、顺序目标指示阶段以及是否接管后续弃牌移动。
- `GameState` 额外保存根事件 ID、事件历史、移牌历史、随机种子、轮数、濒死队列和终局原因；快照会裁剪非响应者的私有选择候选。单槽位 `current_choice_request` 只能表达一条待办请求，因此 `MatchController` 在生成每份观察者快照时另行投射 `local_pending_choice_request_ids`（`_get_pending_choice_request_ids(viewer_id)`）：只列出该观察者本人在 `_pending_card_choice` 与 `_pending_negation_choices` 中仍在等待提交的请求 ID，供界面判定本地窗口是否仍然有效。并行无懈会同时为全部存活玩家登记请求，其他玩家的请求编号必然占用单槽位字段；缺少这份按观察者投射的清单时，联机客户端会在任一后续快照把本人仍在等待的无懈窗口误判为失效并清空，导致非房主玩家卡在询问阶段。该清单不携带他人编号、候选或是否持有响应牌。

### 权威规则层

- `MatchController`：创建对局、推进阶段、执行区域移动、处理判定、护盾、伤害、失去体力、额外摸牌阶段、额外弃牌阶段、额外出牌阶段、濒死、死亡、连环、翻面、奖惩和胜负。相邻标准阶段、额外阶段、结束阶段到下回合均先完成当前规则时机，再交给 `GameFlowPacer` 延时进入下一阶段；响应提示同样通过请求 ID 防止迟到显示。`roundStart → phaseBefore → 翻面检查 → phaseBeforeStart → phaseBeforeEnd → phaseBeginStart → phaseBegin → phaseZhunbei` 使用稳定回合开始游标逐段发布，因此【振旗】等回合前选择必须完整结束后才会进入【加护】等准备阶段选择；背面角色在 `phaseBefore` 维护效果完成后翻回正面并直接完成跳过回合，不发布 `phaseBegin` 且不运行六阶段主体，也不派发回合尾 `phaseAfter`（翻面本质是跳过一整个回合，既没有回合开始也没有回合结束），只有依赖实际回合开始的效果才能在下一次真正进入 `phaseBegin` 时到期。准备与弃牌阶段的 Begin/End/After 选择会保存当前阶段并在提交后从唯一续接入口恢复，已完成时机不会重复派发，额外出牌阶段队列不会丢失；`phase_transition` 已存在时恢复入口保持幂等，不用同一业务键覆盖已经排队的额外阶段，阶段恢复若暴露新的技能后续则延后一帧继续排空。主动技能权威入口在枚举和提交两处统一校验持有者仍存活且未离场，并统一调用 `can_use_effect()` 屏蔽“非锁定技失效”下的主动、响应与查询钩子；半锁定技的锁定后段由订阅元数据独立放行。LAN 客户端也先读取远端公开快照复核该状态，再使用房主下发的私有技能白名单，旧按钮、旧请求或伪造动作均不能让失效角色发动技能。`execute_virtual_card_use(actor_id, definition_id, material_uids, target_ids, log_message, rule_overrides={})` 在材料仍由使用者拥有时构建虚拟牌代理；恰好1张材料时强制以该实体真实颜色覆盖调用方 `card_color`，多张材料时按全部材料聚合花色与颜色并写入代理牌，随后在移动材料、创建处理区表现前再次执行完整虚拟牌目标校验，并把原材料定义与逻辑定义写入使用表现快照供统一牌名横条绘制（多材料与无材料牌没有唯一原牌面，不写该快照字段）。AI 的动作、同步主动技能和普通选择完成后统一经过进度恢复出口；选择提交失败时使用规则层完整合法动作回退，有限重试后只终止对应无解请求并继续父流程。统一结算管线固定按“同一时机剩余触发 → 装备延后触发 → 通用规则后半段 → 技能自行登记的后续 → 阶段或父牌游标”恢复；通用规则后半段按嵌套层级后进先出，技能同层后续仍保持原登记顺序。响应、无懈、濒死救援、目标区域牌移动、重铸、弃牌阶段、回合开始、【杀】武器费用和伤害尾部都通过该边界等待插入事件，已消费牌只以稳定 UID 快照恢复结果。卡牌使用上下文累计直接响应数和真实响应者ID，反响应只归属直接父牌；【制动】可排除持有者本人响应，伤害来源上下文携带父牌UID与逻辑目标数穿过四个修改窗口。`damage` 先扣护盾后扣体力并独占伤害事件；`damage`、兼容 `damage_after`、`hp_reduced`、濒死、`damageSource/End/After`、按最终伤害点数逐次派发的 `damagePointAfter` 与属性连环之间均会检查嵌套屏障。`lose_hp` 绕过护盾与伤害事件，只在实际体力减少时与伤害共同汇入 `hp_reduced`；减少护盾只派发护盾变化时机，不属于伤害或体力减少。手牌限时视为效果以实体UID登记，进入持有者下个回合时锁定到期回合，回合结束或实体提前离开手牌区时恢复原牌名；通用手牌标记同样以实体UID保存，但只在移动确认成立后、实体真正离手前清除，移动被取消时仍保留。离场濒死者在标准濒死时机后跳过救援请求，死亡入口先复用 `restore_player_to_game()` 派发 `enterGame` 并清除限时离场标记，再进入 `dieBefore/dieBegin/die`，保证死亡技能、日志和公开快照均观察到已返场状态。弃牌阶段插入的额外出牌阶段在当前弃牌生命周期完成后执行，结束后直接进入结束阶段，不重复弃牌。
- `CardRuleService`：只做距离、攻击范围、配置化次数、通用目标、区域和延时锦囊同名校验；专属目标组合回调对应卡牌文件，不执行效果。`all_players/all_others` 自动展开时会逐名应用卡牌与技能目标限制，只保留合法角色并再次检查卡牌最少目标数，因此【破风】等限制可把群体锦囊收敛为少量目标，而不会被任一非法角色否决整张牌。`build_material_rule_overrides(material_cards, base_overrides={})` 供多材料转化统一生成带聚合 `card_color` 的规则覆写副本，使技能与装备源码的预览、AI 枚举和提交校验共用同一颜色事实。
- `CardEffectResolver`：纯卡牌源码调度器。它只保存 `host/state`，按卡牌 ID 调用 `resolve/resolve_target`，并按父牌 UID 把选择、响应和专用无懈结果交回原卡牌文件；不包含摸牌、回复、装备、群体响应或任何具体卡牌名称的效果函数。
- `CardUseEventService`：只构建 `CardUseEvent`、五组使用时机、四组动态逐目标时机、`contentBefore/content/contentAfter` 与 `orderingDiscard` 的事件拓扑；不读取 `GameState`、不执行牌效、不持有实体牌对象。
- `IdentityRules`：集中维护 2 至 10 人身份表、胜负条件和死亡奖惩类型；胜负生存集合只依据 `PlayerState.alive`，`out_of_game` 不等同死亡。控制器对完整身份表洗牌，不为领袖保留固定座次。另集中维护联机自选身份的唯一映射来源：`supports_lobby_custom_identity()` 判定模式支持性（过关斩将不支持），`get_lobby_slot_identities()` 返回大厅位置身份表（2v2 使用“上蓝下红”专属布局），`get_lobby_slot_match_seats()` 返回大厅位置到规则座次映射（2v2 为 `[0,3,1,2]`，其余一一对应），`requires_fixed_lobby_seat()` 判定模式是否强制固定座位（2v2 为 `true`，因为成队几何直接决定队友距离与行动顺序）；网关与大厅界面共用这四个入口，不各自维护第二份表。
- `CharacterSelectionService`：纯数据选将状态机，集中维护首次身份下的领袖先选、普通同时选将或最终座次身份自选、1至20张普通随机候选、仅首任领袖的领袖技固定候选、每人私有换将张数、候选私密性与统一完成条件。真人首任领袖在 `PHASE_LEADER` 的同一次 `select_character` 中确认武将、座次和身份，成功后立即从 `PHASE_CUSTOM` 待选集合排除；其余玩家最终自选不附加固定前缀，因此候选数严格等于房主设置。领袖技武将只在当前领袖身份中锁定换将。首任领袖为AI时允许先公开武将并延后占用最终名额，`retains_selected_character=true`、`local_selected_character_id` 和空候选只服务于该AI之后复用同一武将补选座次身份，不会发给已确认真人形成第二个面板。其他观察者仍只收到本人第一次 `local_identity`、候选、锁定/可换 ID 与剩余换将卡，不泄漏其他玩家身份或张数。`get_pending_player_ids()` 在领袖、普通其他玩家和最终自选三个阶段分别返回真实未确认集合，避免 AI 漏选或重复处理领袖。它不加载界面、不注册 AI，也不修改卡牌区域。控制器完成全员选择后先切换到 `game_start` 并同步亮将结果，发完默认4张起始手牌、旋转或应用最终座次后再次同步，随后才允许首轮 `roundStart` 创建技能询问。
- `RuleEventBus`：按优先级同步派发 `RuleEvent`。武将技能、装备扩展和模式规则可订阅事件，不需反向引用控制器。
- `RuleTimingCatalog`：无状态时机目录，集中保存228个不重复监听事件、4个主动技能入口，以及 `judgment/draw/play/discard` 到 `phaseJudge/phaseDraw/phaseUse/phaseDiscard` 的唯一主要阶段时机前缀映射。它不读取对局状态、不派发效果，只提供名称校验与稳定分类顺序；阶段跳过与阶段生命周期通过 `get_main_phase_timing_name()` 取得同一标准名称，不再在多个模块维护字符串分支。`damagePointAfter` 专门承载最终伤害的逐点触发，四个 `reincarnation*` 名称承载轮回生命周期，三个 `disableJudge/enableJudge` 名称承载判定区废除与恢复。
- `PhaseLifecycleService`：六阶段生命周期编排组件，由 `MatchController._begin_phase_lifecycle()` 与 `_finish_phase_lifecycle()` 注入宿主后创建。它按 `Before → Begin → 主体 → End → After` 推进，把唯一实例身份、阶段上下文与 `starting/body/ending` 状态写入 `_started_phase_lifecycles`；Begin 窗口排空后调用 `on_started` 建立阶段主体，取消或中立化时调用 `on_cancelled` 并如实返回 `false`，End 与 After 全部排空后清除实例并调用 `on_completed`。只有 `body` 状态受理结束请求，因此阶段 Begin 询问内确认跳过阶段必须走统一跳过入口 `skip_current_main_phase()`，不能请求结束阶段；被跳过或被取消的阶段不会伪造 End/After。摸牌阶段入口 `draw_phase(player_id, on_completed, instance_scope := "")` 额外接受**实例作用域**，独立额外摸牌阶段（`request_extra_draw_phase`）用它把生命周期键变成 `"<player>:phaseDraw:extra:<phase_id>"`，从而与同回合的正常摸牌阶段互不覆盖，也保证同一个技能连续请求多段额外摸牌阶段时每次都建立新实例。
- `RuleTimingService`：标准时机派发组件。它先调用兼容 `RuleEventBus`，再依据当前状态的存活座次把事件交给独立 `TriggerManager`，最后完成事件；它不执行任何具体牌效、伤害、移动或阶段逻辑。已有选择中断点的触发续列由统一结算管线分片恢复；纯同步父牌效无法跨帧保留调用栈，因此它新建且无选择的分片会在返回父逻辑前受控排空，不会让牌效越过未完成时机。
- `EventScheduler`：维护根事件、事件栈、`next`/`after` 队列、步骤游标、`goto`/`redo`、多通道暂停 token、选择请求与终局中断。长期根事件通过 `held_open` 等待后续子树，不占用暂停 token，也不会阻塞新阶段或卡牌事件。无法构造任何合法提交的单个选择可通过 `abort_choice()` 只中断所属事件并释放自己的暂停 token，不会扩大为整局中断。事件历史通过最新记录增量同步到 `GameState`，状态层与调度器使用独立数组但共享写入后不再修改的条目字典；状态广播只在条目数失配时复制数组引用进行全量校准，不随长局历史长度重复深拷贝第二份事件上下文。对外调试接口仍返回深拷贝，不能借共享存储修改归档。事件完成后立即释放含 `Callable`、可变上下文和步骤队列的完整 `GameEvent`；按ID快速查询只索引最多4096份与历史共享的最终摘要，旧事件仍从完整历史逆序恢复并提升回热索引，近期或重复规则查询保持常量时间而索引内存不随长局增长。同步 `record_event()` 只记录父ID关系，不进入长期根事件的待执行队列。事件状态仍区分 `finished`、`cancelled`、`neutralized` 和 `aborted`。
- `GameplayPauseService`：对局级令牌暂停组件。首个调用方申请时保存原场景树暂停状态并暂停对局，最后一个调用方释放后恢复；每次申请返回调用方必须自己保存的令牌 ID，`release_pause()` 只接受令牌 ID，因此任何调用方都不可能误释放他人的暂停，顺序不同的多次申请与释放也只按令牌集合是否为空决定恢复时机。状态变化通过 `pause_state_changed` 广播，`get_active_reasons()` 供界面与测试只读诊断；`MatchController` 同步持有 `EventScheduler` 全局 token，并在所有 AI 调度与动作入口查询同一状态。当前使用者包括机缘选择（原因 `opportunity_selection`）与阿哈时刻过场组件（原因 `ahha_moment_cutscene`）；过场组件除正常的播完释放外，还会在重新开局、对局终局、联机会话关闭与自带超时上限到期时释放自己的令牌。
- `GameFlowPacer`：对局流程节奏组件。它只按业务键管理可取消计时器与回调令牌，不读取 `GameState`、不决定阶段、不执行响应；重新开局会取消全部旧任务，场景暂停期间计时不推进。
- `TriggerManager`：先按 `player/source/target/global` 过滤技能持有者与 `RuleEvent` 角色关系，再按 `firstDo/lastDo`、技能优先级、起始座次和注册顺序排列触发器，并在执行前重新检查所有者生命周期与动态条件。同一时机内部始终沿用初次排列；回调内又创建暂停时机时，续列按最内层优先恢复，必须先完成子时机剩余处理器再返回外层座次。每个排序分片默认检查64项；同一 `RuleEvent` 对象重入会立即取消，新事件嵌套默认上限32层，超限只熔断最内层事件并发出可序列化故障。管理器同时跟踪同步活动栈与异步暂停续列；当阶段跳过等权威流程边界令旧时机失效时，`cancel_matching_dispatches()` 会以稳定原因终止所有匹配事件，恢复器只清理终态续列而不再执行剩余技能。
- `RuleModifierPipeline`：独立于触发器的纯查询修正链，供 `RuleQuery` 实现 card/target enabled、usable、respondable 和 in-range 查询。
- `RuleQuery`：只读合法性门面；不创建选择、不移动牌、不消耗次数。
- `MatchReplayRecorder`：对局回放录制组件。它只订阅牌桌已经收到的观察者裁剪快照、日志文本与桌面表现事件，把 `{"t":相对毫秒,"k":"s"|"l"|"p","d":数据}` 步骤以 `store_var` 流式写入临时文件（上限30000步，超出置截断标记）；表现步骤 `"p"` 为格式版本1的兼容性追加（旧读取端忽略未知类型），承载技能/防具发动提示、卡牌使用/展示/判定表现、区域移牌、摸牌批次边界与所有权释放的纯数据（稳定玩家 ID、名称与牌面快照，不含坐标），计数以 `presentation_count` 写入回放头。组件不读取 `GameState`、不常驻整局快照内存；保存时依据最近快照构建回放头（模式、玩家、视角、胜负、统计）并连同玩家在命名弹窗填写的自定义基础名（可为空，空值由存储层生成默认名）交给存储层，同一局重复保存复用首次文件名，保存后录制继续。离线、LAN 房主与客户端录到的都是本机视角，回放呈现与当局所见一致。
- `MatchReplayStore`：回放文件持久化边界（全静态函数）。回放为 GZIP 压缩容器：先写 `store_var` 回放头（含魔数 `LISBAM_REPLAY` 与格式版本1），后接连续 `store_var` 步骤；提供保存（可传自定义基础名，非法字符过滤、重名自动追加序号）、枚举（顶置条目在前，组内按保存时间倒序，条目附 `pinned` 标记）、读头、读步骤、重命名（重名追加序号不覆盖、顶置标记随文件迁移）、顶置读写（记录在回放目录内 `replay_pins.cfg` 元数据，不写入回放文件本体）、按玩家路径逐字节导出（自动补 `.lisbam_replay` 后缀）、校验后导入（重名自动追加序号，不覆盖）与删除（同步清理顶置标记）。默认目录 `user://replays/`，全部入口支持测试目录覆盖；二进制变体序列化完整保留64位整数精度。
- `MatchReplayPlaybackDriver`：对局回放重演驱动器。它按录制时间差顺序把回放步骤重新派发为快照、日志与表现信号（首步立即派发，相邻间隔超过2000毫秒按上限截断，未知步骤类型静默跳过），速度倍率仅允许1倍及以上加速；组件不理解快照语义、不渲染界面、不读取 `GameState`，空闲时关闭帧处理，牌桌把其快照信号接回唯一状态刷新入口、把表现信号接到目标线重演入口，实现正式桌面上的整局重演。
- `CardMovementService`：统一维护实体牌区域和牌面知识，追加 `CardMoveEvent` 历史，并在权威移动完成后发出唯一 `card_moved` 增量；同一实体在同一区域且持有者未改变时拒绝重复移动，控制器只把进入手牌和弃牌堆的有效增量转为客户端表现，规则调用点不得重复发信号。组件同时按“全局回合号+行动角色”维护出牌阶段进入弃牌堆的 UID 顺序索引；晚于状态创建时会一次性从既有历史重建，之后增量追加，使指定回合候选查询只处理该短桶和当前弃牌堆，而不扫描整局移动记录。

### 外部适配层

- `AICoordinator`：管理玩家与 AI 策略映射，把权威完整快照和合法动作交给策略选择；共享 `IdentityAIModel` 观察公开用牌，即使没有内置策略也保留忠反推断，并通过只读查询和变化信号提供给本地界面。
- 身份观察的联机同步：房主在四处权威观察点（公开用牌、技能公开目标、濒死救援、成功打出的【无懈可击】）之后分别调用 `MatchController._broadcast_identity_behavior()` 或 `_broadcast_identity_response()`，把公开行为本身广播给全部客户端；客户端在 `_on_network_game_event_received()` 的白名单分支里调用 `_apply_replayed_identity_behavior()` 或 `_apply_replayed_identity_response()`，用本地 `AICoordinator` 重放同一推断，从而让“自动标记身份”对非房主同样生效。广播载荷由 `build_identity_behavior_payload()` 与 `build_identity_response_payload()` 构建并被刻意裁剪：前者只含行为玩家稳定 ID、房主算好的只读 `ai_profile` 与公开目标，后者只保留 `source_id`、`target_id`、`negated` 三个公开键。网络因此只承载公开行为而不承载推断结果，隐藏手牌与完整结算上下文不会进入事件；客户端没有本地 `GameState` 时以最近一次房主快照作为身份模型的背景数据。
- `BasicAIPolicy`：示例启发式策略。它不能修改状态，只返回可序列化动作；卡牌基础价值、目标收益方向和无懈收益方向读取卡牌元数据，不维护具体卡牌 ID 表。策略、`NonameAIEvaluator` 与 `IdentityStrategyEvaluator` 分别缓存数据库返回的静态元数据独立副本；同一合法动作集合内按技能 ID 复用纯 AI 技能实例。`IdentityAIModel` 在普通行动、统一选择、无懈判断和装备材料排序的单次同步决策边界内，先完成固定身份观察同步，再额外遍历最多10名玩家1次建立玩家ID、存活身份人数、身份首名玩家与存活总数索引，并按需复用局势和反贼暴露判断；返回动作前连同技能实例一起清空，绝不跨决策缓存权威快照或决策结果。`NonameAIEvaluator` 统一对酒杀响应、最后【闪】保牌、预期伤害、护盾和属性连环进行评分，技能文件只叠加自身专属奖励。
- `NetworkGateway`：封装离线、局域网和远程模式。LAN 分支直接管理 `ENetMultiplayerPeer` 建房/加入、房主内存密码与公共 `has_password`、成员形象、位置、聊天历史、踢出及按远端地址计时的5000毫秒重新加入冷却、peer 与稳定玩家 ID 的大厅位置顺序映射、每发送端封包序号去重、真实发送者 actor 防伪、定向私有快照和只读表现事件；释放会话时先以 `OfflineMultiplayerPeer` 脱离 `SceneMultiplayer`，再关闭旧 ENet peer，使同端口可立即复用。对局内断线重连同样收敛在网关：房主开局时为每名远端真人签发32字符会话令牌，掉线时按令牌登记座位预约，客户端断线后以2秒间隔自动重拨最多15次并携令牌重新登记；令牌命中即重绑 peer 映射并以 `lan_match_peer_reconnected` 通知控制器解除离线托管，令牌还能直接接管房主尚未察觉掉线的旧连接，对局结束时预约整体失效；同一 ENet 房间内重开新局时预约与令牌按大厅位置迁移到重新洗牌后的座次（`_migrate_lan_session_bindings_to_new_seats()`），因此掉线玩家仍可携原令牌回到新座位。客户端不能上传状态、取得密码明文或伪造其他玩家操作。网关另集中承载对局内聊天：`send_match_chat_message()` 在离线模式本地回环、LAN 客户端上行 `match_chat` 封包、房主按连接绑定的稳定玩家 ID 反查署名后逐客户端中继并本地登记，历史上限100条并在大厅开局与会话结束边界清空（断线重连与同房重开保留），统一通过 `match_chat_received` 信号交给牌桌，条目只含序号、发送者稳定玩家 ID、署名与正文（不含时间字段），聊天不进入规则协议。REMOTE 继续保留外部适配器信号。开局绑定由 `begin_prepared_lan_match(broadcast_lobby_state)` 统一发送，房主在同一 ENet 房间内重开对局时改用 `rebroadcast_prepared_lan_match()` 重播开局绑定：该入口只发送开局绑定并清空对局内聊天，不重发大厅成员表，避免对局进行中把客户端切回大厅界面；会话令牌继续复用首次签发值并随重开一起迁移到玩家的新座次，因此在线连接与断线重连凭证都不受影响（重开可改变物理座次，故玩家重新绑定的稳定 ID 可能变化），触发条件由核心层判断（仅房主且房间已开局，即首次开局之外的“再来一局”路径）。客户端据此在新对局重置按局维护的表现幂等窗口与卡牌实体 UID 认领记录。网关另持有房间级“自选身份”与“固定座位”两个开关：建房与设置更新时后者经 `IdentityRules.supports_lobby_custom_identity()` 权威规范化、两者均随公共快照广播；静态 `get_lobby_display_slot_count_for()` 统一提供大厅视觉位置数（车轮战固定2位、自选身份等于规则人数、其余2至3人3位），房主换位校验与大厅界面共用；自选身份开启时开局映射按成员大厅位置经 `IdentityRules.get_lobby_slot_match_seats()` 绑定规则座次，座位是否固定由固定座位开关与 `IdentityRules.requires_fixed_lobby_seat()`（2v2 强制）共同决定：需要固定时直接采用该映射，否则 `_build_shuffled_lobby_slot_binding()` 用私有 `RandomNumberGenerator` 对整张“大厅位置 → 规则座次”映射做等概率洗牌（真人座次与 AI 补位座次一起重排），并通过 `get_lan_seat_lobby_slots()` 把“座位到大厅位置”的反向映射交给控制器；控制器把 `lan_custom_identity_enabled` 与 `lan_fixed_seat_enabled` 锁入 `match_options`，按位置身份表分配身份（不再洗牌或做2v2蓝红互换）而座位保持随机，映射尺寸与本次角色总数不一致时整表回退到座次身份表，随机座位时该反向映射按完整逆映射填满每一个规则座次（含 AI 补位座次），被放弃的开局由 `cancel_prepared_lan_match()` 一并清空该映射。同一 ENet 房间内的“重新开始”由 `MatchTable` 以 `prepare_lan_match_assignments(player_count, true)` 重新准备一次映射（允许在对局进行中执行），使每局座位都重新随机。
- `match_table.gd`：桌面协调器，只读保存控制器刚生成的裁剪快照，按玩家 ID 建立当帧索引，缓存不会在运行期间变化的卡牌、武将和势力定义，并按实体 UID 对账复用正式手牌节点与座位节点；本地手牌排序只复用当前只读快照引用，不逐牌深拷贝。对局时长使用仅在进行中启动的0.25秒 `Timer` 检查整秒变化，终局或返回主菜单后停止，不注册每帧 `_process`。它维护出牌临时选择、读取只读规则预览并构建 `PlayerAction`。手动选目标时，它把合法候选、已选目标与“当前处于手动选目标”三项状态传给武将牌组件；全体目标模式仍只显示“规则自动展开”。【桃】【酒】【无中生有】【闪电】和自身装备只有在规则预览确认本人是唯一合法目标时才自动锁定本人。主动技能创建可取消的内联选择后，原技能按钮保持选中与可点击，再次点击提交标准 `confirmed=false`；响应转化技能再次点击只退出材料转化模式。未被 GUI 消费的牌桌空白左键会同时收起已展开的对局记录与局内菜单；离线日志暂停时由始终处理的 `MatchLogPanel` 发出关闭意图，再由牌桌复用同一关闭入口。`MatchLogPanel` 独立保存本局完整纯文本日志：折叠时清空 `RichTextLabel` 排版文档，展开时一次恢复全部历史，展开期间同一帧的新增记录合并为一次追加和滚动；重新开局通过组件端口同时清空历史与正文。托管按钮与 `PlayerAutoManagedHandOverlay.cancel_requested` 都只构造 `set_auto_managed`，独立覆盖组件负责0.76透明度黑色滤镜、0.45秒省略号循环、文字区域取消意图与输入拦截；牌桌根据手牌、本地座位和当前手牌层级计算175像素高的覆盖矩形，并把技能栏提升到其上方，牌桌仍以快照禁用其他操作。本机获得的牌不再从右侧入场：桌面只登记飞行起点与门闸，等包含该牌的权威快照布局出它自己的最终槽位后才起飞，飞行牌面从该牌真实来源位置直接飞向该槽位（若该牌正在中央展示队列中，则接管那张牌面本身继续飞行，队列剩余成员重新以弃牌中心为轴居中），落地回调解除门闸后正式节点同帧出现在同一位置，同一帧还会把飞行牌面置为不可见、并在每次快照重配正式节点后把正式节点的禁用压暗观感镜像到飞行牌面上（`CardView.set_content_dimmed` 只改观感、不改可点击性），因此飞行途中与落地后的明暗完全一致，不会在牌进入手牌区后出现亮度跳变，也不会留下重叠的上层牌面拦截鼠标。同一次 `draw()` 的牌堆到手牌移动先按批次 ID 收集，完成后本机批次的每张牌以正面各自飞向该牌自己的槽位、其他观察者的批次只显示牌背并按42像素间距整体居中并行播放。每个已收齐的批次立即启动，多个玩家或连续摸牌的批次可以重叠播放。手牌容器侧的直接拖拽排序松手后按“释放点到稳定槽位”的绝对偏移做0.18秒落位过渡，待消费的释放点数量参与布局签名以保证松手帧必然重新布局。未起飞门闸的撤销以快照代次 `_local_hand_snapshot_generation` 为界：转移信号先于权威快照到达，而询问界面等入口会在同一帧用旧快照重新对账手牌，因此只有快照代次严格大于门闸登记代次时才把“快照里没有这张牌”判为已经离手；否则【风口】这类“一次性获得多张牌后立刻询问”的技能会让整批摸牌飞行被误取消，表现为摸牌跳过动画直接进手牌。它在主菜单发出开局信号前不调用 `MatchController.start_match()`，收到单机信号后统一开始离线对局（身份/斗地主/2v2）；局域网则协调连接入口、`OnlineLobbyPanel`、`NetworkGateway` 与房主权威控制器，客户端只绑定房主按大厅位置顺序分配的本地玩家 ID并渲染远端快照。局内重开先读取控制器的只读前置校验：失败时不清理旧表现并调用局内菜单恢复入口；通过后才清理旧表现并替换权威状态，若后置初始化仍失败则缓存同步拒绝原因并调用主菜单恢复入口。牌桌依据 `NetworkGateway.is_lan_client()` 统一隐藏非房主无法生效的局内权威控件；五谷等公共模态窗口保持在手牌层级之上，其牌位结构不变时复用原 `CardView`，只更新交互权限、领取虚影和领取者标签。菜单布局、联机大厅位置和选将候选布局由独立组件负责。身份徽记按公开身份、手动标注和自动忠反标记的优先级渲染，但不写回快照；本地标注与共享身份模型都按快照 `match_id` 收敛对局归属，`match_id` 变化即整体清空并重置身份观察（联机客户端牌桌跨局常驻、不经过新局重置入口，因此清空边界必须以对局 ID 而非场景重建判断，否则上一局的标记会留到新一局复用座次的武将牌上），同一 `match_id` 的重复快照与断线重连继续保留玩家已有标注。桌面只把各视图的统一信息信号连接到唯一 `InformationBoxLayer`，并在离线武将详情显示期间管理独立暂停令牌；信息组件本身不读取控制器或网络模式。桌面另协调局内聊天与对局回放的表现边界：局内菜单“聊天”按钮切换代码构建的 `MatchChatPanel`，网关 `match_chat_received` 条目同步窗口正文并按发言者玩家 ID 复用 `ChatBubbleView` 头顶气泡（本地锚定第一视角武将牌、其他玩家锚定座位牌，复用技能提示的逆变换定位）；桌面持有的 `MatchReplayRecorder` 在唯一快照入口 `_on_state_changed` 与日志入口 `_on_log_added` 处旁路录制（按 `match_id` 识别新局自动重开录制），结算面板命名弹窗确认后携自定义名触发落盘并以顶部横幅提示，返回主菜单丢弃未保存录制，空白点击、安卓返回、主菜单覆盖与新局重置统一收起聊天窗口与全部气泡。桌面另承载回放重演会话：主菜单“对局回放”页播放意图到达后校验非LAN会话、放弃残留权威对局并复用新局重置入口，把第一视角切到回放头的录制端视角，惰性创建 `MatchReplayPlaybackDriver` 与 `MatchReplayOverlay` 并把驱动器快照/日志信号接回 `_on_state_changed`/`_on_log_added`，使回放像真实对局一样在正式桌面重演；技能/防具发动、卡牌使用/展示/判定表现（去重通过后）、区域移牌、摸牌批次边界与所有权释放在各自信号入口以纯数据旁路录制为表现步骤，重演时经 `_on_replay_presentation_step` 把同一份数据送回与正式对局完全相同的表现处理器，中央飞牌、目标指示线（含借刀杀人等多段线）、移牌与同批摸牌动画按原表现流程复刻，坐标按重演布局重新解析；重演期间录制器旁路停用、结算模态不自动弹出、局内菜单与聊天按钮隐藏、牌桌快捷键失效，退出（覆盖层按钮、Esc 技能栏通过 `GameDatabase.get_skill()` 读取技能元数据深拷贝，其中布尔 `lock` 明确标识锁定技，布尔 `leader_skill` 明确标识只有 `identity=leader` 才实际拥有的领袖技。技能可覆盖纯查询 `locks_face_down()`（基类默认 正面”，因为翻面还可能由其他技能与机缘直接写入，判定只能放在核心。选将完成后，`MatchController` 根据武将源码直接引用的技能脚本为每名玩家创建独立实例并调用 `install()`；非领袖的领袖技在实例安装前被过滤且技能栏不创建按钮，其他不可发动、预留、被动、触发和锁定技能按钮保持禁用灰显且点击静默，可主动技能通过 `use_skill` 动作调用自身 `can_activate/activate`。描述为“出牌阶段开始时”的技能在 `phaseUseBegin` 回调内直接创建询问，不能延后到普通出牌按钮。出牌阶段主动技能先以 `button_ids` 完成当前 `chooseToUse`，再在同一事件链内创建后续选择；技能若同步完成且没有建立嵌套请求，也会由控制器统一恢复 AI 的下一次 `chooseToUse`，寒鸦【录事】等主动技能不需要自行调度 AI。技能基类自动把 `skill_id/skill_owner_id` 写入选择上下文；跨角色选牌与文字选项另保存真实选择者，提交的牌、目标或 `control_id` 回到同一运行时实例的 `continue_choice/continue_selection/continue_response`，额外摸牌、额外出牌或额外弃牌阶段完整结束后通过 `continue_extra_phase` 恢复（回调按 `context.kind/stage` 识别是哪一段，因此同一技能可以连续请求多段，例如【巡礼】的摸牌 → 出牌 → 弃牌）。技能顺序效果若被嵌套选择暂停，则用 `defer_settlement()` 登记纯数据步骤；控制器在选择、同一时机续列和装备触发均无等待后调用原实例的 `continue_settlement()`，避免业务函数在选择存在时继续同步结算。响应候选会同时查询技能实体转换钩子，但可转换材料默认禁用，只有玩家显式点击匹配技能后才以 `response_skill_id` 提交；控制器消费前重新复核技能、材料区域与转换条件。装备响应候选还受本次结算的共享语义约束：卡牌源码在响应上下文中写入 `ignore_armor=true` 时（青釭剑无视防具的【杀】），请求端口按控制器常量 `ARMOR_EQUIPMENT_SLOTS` 把结论固化为响应上下文 `ignored_response_equipment_slots`，候选构建、独立即时询问、判定失败重开与提交消费四个阶段都会重新读取该字段，因此被停用槽位的防具（八卦阵）不会出现在任何候选，也不能通过迟到提交发动；该字段随响应上下文逐层传递，内容层防具无需感知。同一规则时机出现多个可选技能时，`TriggerManager` 保存已排序续列，当前选择及其后续选择完全恢复后再从当前回合角色起按座次继续询问，不能覆盖后续技能请求。技能在确认支付费用、锁定效果或主动效果实际成立后调用 `SkillDefinition.announce_activation()`（跨角色领袖技用 `announce_activation_for_player()`）；控制器统一追加“角色发动了【技能】。”日志、保存公开只读 `skill_history` 并发出信号，同时派发带 `actual_activation=true`、原目标与唯一重复令牌的 `skillAfter`。需要“额外发动原技能”的组件稍后通过 `repeat_skill_activation()` 回到原触发回调或 `activate()`，不越过原技能费用、目标、轮回和通用限次；`repeated_activation=true` 防止【奇袭】类技能递归触发。`match_table.gd` 在发动者武将牌中心以高于手牌的黑色描边文字短暂显示技能名。AI 动作与预览也由技能文件提供，非领袖不会应用领袖技牌效钩子。`SkillButtonView` 与 `match_table.gd` 始终不能直接修改状态。

技能元数据中的 `half_locked=true` 表示正文同时具有非锁定前段与锁定后段；正文中“锁定技”标签位于非开头位置时，基类也会自动识别该结构。所有主动、响应、查询、异步恢复和额外阶段回调都通过 `can_use_effect()` 复核“非锁定技失效”状态；半锁定技后段订阅显式传入 `locked_segment=true`，只负责清理既有持续效果的维护回调使用 `maintenance=true`。该分段不复制技能实例，也不改变玩家可见原文。

技能“然后”步骤的每条队列记录都具有稳定 `settlement_id`、语义键、因果链访问表与链步数。独立的相同触发仍按 FIFO 分别执行；只有 `continue_settlement()` 中登记的子步骤继承当前因果链。同一链内完全相同上下文默认最多进入16次，即使上下文每次变化，整条链也默认最多512步；超限或 `continue_settlement()` 返回 `false` 都只丢弃异常步骤、发出 `settlement_faulted` 并让对局继续。统一结算管线同一时刻只允许一次延后唤醒，重入请求不会递归排空或叠加空闲帧回调。唤醒的活跃性由入口末尾的待办复查统一保证：入口会先作废旧唤醒再同步排空，而这次排空可能因为独立子阶段、待选请求或待判定门控提前返回且一项都没有消费；此时只要技能“然后”步骤、规则续接、装备排队触发或待派发触发仍有待办（并且不在等待选择或判定这类自带响应恢复入口的阻塞上），入口就立即重新登记唯一唤醒。缺少这条兜底时，在额外出牌阶段等子阶段内部登记的技能“然后”步骤会永久滞留——表现为技能效果已经扣除资源、后续步骤却不结算，流程也无法继续推进。

**子阶段归属的延后结算必须由子阶段自己排空。** 独立额外出牌阶段由外层规则续接持有（外层回合开始或阶段序列正在等待它结束），管线会在“栈顶父序列等待子阶段”的屏障处提前返回，以免越过外层时机。仅靠上面的唯一唤醒兜底并不够：唤醒只会再次撞上同一屏障，条目仍然排在屏障之后，形成零进展活锁（其外部表现是延后队列不为空、`has_pending_play_interaction()` 恒为真、`chooseToUse` 窗口永不重建）。因此每条延后结算记录在 `defer_skill_settlement()` 时写入 `registered_play_phase_id`（登记瞬间活动的独立阶段实例号，不在独立阶段内时为 `-1`），管线在屏障早退之前用纯查询 `_find_phase_scoped_deferred_settlement_index(phase_id)` 只取出**归属等于当前活动独立阶段**的条目，经既有 `_resume_deferred_skill_settlements(index)` 消费；`-1` 的父序列遗留条目一律不动，外层时机顺序不变。排空后按与普通出牌阶段完全相同的方式重建出牌窗口（复用既有的空闲窗口重建入口 `resume_play_phase_choice()`，不新增任何独立阶段专用的推进路径或结算队列）。单帧排空次数由 `max_phase_scoped_settlement_drains_per_pass`（默认 `8`）封顶，达到上限仍残留同阶段条目时调用 `_record_settlement_fault("phase_scoped_settlement_drain_limit", …)` 记录一次局部熔断；`get_stall_diagnostics()` 同时在只读诊断里暴露三元组“活动独立阶段 `phase_id` / 续接栈顶序列的 `enclosing_play_phase_id` / 阶段归属延后条目数量”，让同类问题在实机上可被直接观测而不必猜测。

**父序列遗留条目不得阻塞子阶段交互（同一屏障的对称缺陷）。** 上一段只保证「归属子阶段的条目能被排空」，但修复前的 `has_pending_play_interaction()` 仍把**任何**非空延后队列都当作“当前出牌阶段仍有未完成交互”。当屏障生效且队列里只剩 `-1` 的父序列遗留条目（这些条目在子阶段内**不可能**被消费）时，独立额外出牌阶段的 `chooseToUse` 窗口虽然已经建立，AI 动作却会被 `_schedule_ai_action()` 永久拒绝；而子阶段不结束，父条目也永远不会被排空，形成与前一段同形的零进展死锁（外部表现：延后队列恒非空、窗口在、没有任何计时任务、阶段停在原地）。修复由两处组成：①新增纯查询 `_has_blocking_deferred_skill_settlement()`，在屏障生效且存在活动独立额外出牌阶段时，只把「归属等于当前子阶段实例」的条目视为阻塞，其余条目交给管线按原顺序处理；②管线在屏障早退分支排空后统一调用 `_ensure_ai_progress_after_resolution()`，补齐子阶段自己的窗口与 AI 驱动（该分支是这种状态下本帧唯一会到达的统一出口）。真实触发组合是【风口】在 `gameStart` 登记的条目与【巡礼】在首回合 `phaseBefore` 插入的三段额外阶段同时存在，回归由 `tests/pre_game_deal_gain_test.tscn` 固定覆盖。

手牌临时牌名由 `CardInstance` 保存原定义与来源技能，只有统一移牌边界可以清除。实体在手牌区时，合法动作、显示与AI读取当前临时定义；实体作为使用或响应材料离手时，当前逻辑牌先保存该定义，再把持久实体恢复为原定义并移入处理区或弃牌堆。该模型保留唯一UID、花色、点数和区域历史，不为【药理】复制一张永久新牌。【亲酿】在实体进入接收者手牌后额外登记“下个回合结束”到期记录；实体提前离手时由同一移动边界恢复，不能由技能直接改写牌区数组。不改变牌名的 `hand_mark_tags` 使用独立来源字典；【鸣弦】通过其中的 `ignore_distance_limit` 使该实体【杀】在手牌内忽略距离，标签与规则在实体成功离手时一并清除，移动被时机取消时保留。临时牌名和标记可同时存在，清理一类状态不得覆盖另一类。

插画路径属于静态表现元数据，不写入 `CardInstance` 或对局快照。卡牌定义可直接提供 `art_path`；武将定义不维护该字段，`GameDatabase._load_characters()` 会根据每个武将源码文件的完整基础名，在 `res://game_data/characters/image/` 按 PNG、JPG 顺序自动发现同名资源，并只向对外武将元数据副本注入命中路径。该过程不修改 `CharacterDefinition` 源对象，也不依赖武将稳定 ID、中文显示名、技能或对局状态。

`CardView` 和全玩家共用的 `PlayerTargetView` 只把最终元数据中的 `art_path` 交给 `ArtworkLoader`，因此插画缺失不会影响规则层、AI 或网络层。同名 PNG 与 JPG 并存时选择 PNG；两种格式均缺失时不产生数据校验错误并显示占位图。本地玩家与其他玩家使用同一武将牌类和148.35×197.8像素的3:4原生场景规格，差异仅来自布局位置和快照可见性；装备横条读取141.35像素插画宽度，判定区和状态覆盖由独立无状态子组件渲染。正式卡牌统一为111×148像素的3:4规格。

濒死入口维护“存活角色体力不大于0时必须处于濒死或进入死亡确认”的权威不变量。`dyingBefore/dyingBegin` 的取消或中立化只有在处理器已恢复正体力、确认死亡或令角色离场时才能终止；单独设置事件标志不会让伤害尾部留下非正体力存活角色。

## 开局与选将边界

`MatchController.get_match_start_validation_error()` 是开局前不修改任何状态的只读校验边界，统一返回人数与全局数据配置错误；`MatchController.start_match()` 复用同一结果，只有空字符串时才取消旧任务并替换状态。随后控制器创建身份、空武将玩家状态和牌堆，并把阶段设为 `character_selection`。标准身份局使用同一对局随机源先为本地人类玩家分配有效座次，再对包含领袖的完整身份池洗牌，因而本地玩家、领袖和一号位三者互不绑定。领袖先获得候选并单独确认，控制器立即把领袖武将写入 `PlayerState` 且公开；随后其他玩家各自同时确认，具体选择在所有人完成前不进入其他观察者快照。开启最终座次身份自选时，真人首任领袖在第一次公开选将动作中同时确认最终座次身份，随后不再进入其他玩家选将流程；AI首任领袖只先亮将，待真人完成后复用同一武将补选剩余名额。全员完成后控制器统一公开非领袖武将、按武将配置初始化体力、安装每名武将直接引用的独立技能实例、每人摸4张起始手牌，并直接查找唯一领袖开始首回合；预留的 `first_turn_seat_number` 不参与标准身份局顺序判定。只有对局人数不少于5人时，领袖才在武将基础体力上限上增加1点。

首任AI领袖补选采用优先队列：全部真人确认后，控制器先检查该AI是否仍保留首次公开武将且尚未确认座次身份；若一号位与领袖仍空缺，则该AI先以同一稳定武将ID取得二者，再处理其他AI。真人已确认领袖时，首任AI领袖只按剩余名额补选，不能改写真人的最终选择或自身公开武将。

首任AI领袖首次确认时，控制器从服务提供的全部合法候选中使用本局 `RandomNumberGenerator` 取一张；领袖技固定候选仍位于普通随机候选前端并保持不可换将，但不构成AI取将优先级，普通AI继续取其首个未被确认占用的随机候选。该随机调用与身份、牌堆、候选生成共享同一对局随机源，因此同一种子可完整复现。

房主权威开局设置在 `start_match()` 创建新状态时复制到 `GameState.match_options`，当前对局不再读取菜单后续变化，其中 `mulligan_limit` 为 `0/1/2/3/4/5/10/-1`、`character_candidate_count` 为1至20、`character_replacement_count` 为 `0/3/5/8/10/20`。即使开启“自选全武将、座次与身份”，服务也先按第一次身份进入 `PHASE_LEADER` 并公开首任领袖武将，再进入 `PHASE_CUSTOM`：真人首任领袖阶段快照直接开放最终座次、身份控件与“所有武将”入口（`allow_all_characters=true`）；首次座次按该领袖旋转，使默认领袖与一号位组成真实状态。真人提交必须包含武将、座次和身份，座次全局唯一，身份总量等于标准身份分布，一号位与领袖身份双向联动。首任真人领袖成功提交后立即占用名额并从待选集合移除；首任AI领袖只先亮将，等真人完成后再占用剩余名额。最终自选候选严格等于设置张数，不附加领袖技固定前缀；服务保存不可变的首任领袖玩家 ID、首次生效值、预览值、最终稳定玩家ID、武将ID、座次号、身份ID、锁定候选和私有换将张数。控制器收到有效 `preview_custom_assignment` 后立即投射预览座次与身份、重排 `PlayerState` 显示顺序，并清空未确认角色的背景亮将；首任领袖继续占一号位时保留其公开武将，新一号位为AI时才应用其公开预览武将，并在AI最终确认时复用该稳定武将ID，未确认真人成为一号位时快照显式清空旧领袖武将。每次最终 `select_character` 只应用一次权威武将结果并按最终身份刷新基础体力，全部完成不会再次覆盖座次或武将。全部真人确认后，AI才从剩余座次和身份名额中完成选择。身份局在唯一首任身份尚未落定时可预留一号位；2v2 无首任身份绑定（`get_first_seat_identity()` 为空），但座次与蓝/红按开局表 `team2v2_identity_by_seat` 强制一致。AI 必须从完整可用座次中选合法绑定对并优先沿用首次随机座次，禁止无条件移除一号位以免最后一名 AI 提交无效座次。预览补位 `_apply_custom_assignment_preview` 同样遵守绑定表。

首任领袖公开武将是该稳定玩家不可改写的最终武将：真人在 `PHASE_LEADER` 第一次确认时已经同时落定座次身份，进入 `PHASE_CUSTOM` 后服务不再把该玩家列入待选集合；其余玩家才获得严格等于房主设置张数的随机候选。首任领袖为AI时服务保留其选择、清空候选和全武将入口（`retains_selected_character=true` 仅服务该 AI 补交座次身份，不用于真人首任领袖），AI驱动在真人完成后直接提交同一稳定武将ID补足座次身份，因而不会停住、抢占真人名额或在开局前后再次随机。

`AICharacterAdjustmentService` 是初次选将与技能安装之间的独立阶段组件。它只保存房主ID、可调整AI ID、当前目标和本次随机候选；房主点击AI武将牌后按本局1至20张普通候选数重新生成，确认时由 `MatchController` 重新初始化该AI的武将与体力，座次和身份保持不变。`StartingHandMulliganService` 是起始手牌发放与领袖首回合之间的独立手气卡张数/完成状态组件，支持关闭、一至五张、十张与无限张；实体牌洗回、重洗和重发仍由控制器通过 `CardMovementService` 执行。手气卡重发不进入普通摸牌生命周期，避免开局配置替换触发摸牌技能或被摸牌修正改变张数。各设置与阶段组件均遵循单一职责，阶段推进只由控制器编排。

`CardRuleService.normalize_targets()` 是多目标的统一权威顺序入口。群体目标牌从使用者开始按环形行动顺序展开：`all_players` 先结算使用者本人，`all_others` 先结算使用者的下一名存活角色；方天画戟和铁索连环等手动多目标牌也在提交后按相同行动顺序重排。【借刀杀人】在使用动作中保留“持刀者、被【杀】者”两名声明角色，`CardDefinition.get_resolution_target_ids()` 将实际目标时机收敛为唯一持刀者，`configure_requested_target_context()` 将第二名角色写入结算上下文，因此牌效不会再创建独立目标请求。【无懈可击】每轮把全部存活玩家加入同一公开响应名单，并为当前确有合法候选的玩家分别登记私有 `ChoiceRequest`；请求彼此并行，首个到达权威端且通过实体牌复核的响应取得本轮结算权，同轮其他请求立即以系统放弃关闭。成功响应后重新开启下一轮，直到完整一轮无人响应。公开 `simultaneous_response_display.responder_ids` 始终包含全部存活玩家，不携带候选数量；连环传导与濒死救援仍从当前回合角色开始按存活座次进行，若一名濒死响应者回复后目标仍未脱离濒死，下一轮从该响应者重新开始。

死亡结算先标记死亡并亮出身份，然后立即调用 `IdentityRules.evaluate_winner()`。该服务只把 `alive=false` 视为死亡；`out_of_game=true` 的角色仍计入身份局、斗地主与2v2阵营生存，虽然其继续从行动、距离、目标和响应集合排除。若已满足胜负条件，`GameState.game_over` 会成为规则操作与 `CardEffectResolver` 的统一终止条件：当前死亡弃牌、奖惩、群体牌后续目标、响应、伤害、回复、摸牌及使用牌结束区域移动全部停止。若对局继续，则清理死者区域并执行击杀奖惩。当前回合角色在自己行为的插入结算中死亡时，当前事件完整结算后直接从其下名存活角色开始新回合；若死于开始阶段事件或判定阶段，则由 `_start_turn()` 在该阶段结算返回后执行同一转交，不会停留在死亡角色的回合。

普通候选数量由房主 `GameSettings.character_candidate_count` 设置为1至20并在 `MatchController` 开局时锁定，默认5、实际不超过可用武将数量；所有拥有领袖技的武将由控制器扫描技能元数据后额外传给服务，固定前置且不占普通数量。人类、AI 和网络玩家都提交 `select_character` 标准动作；换将统一提交 `replace_character_candidate`，任何适配层都不能直接改候选数组、剩余张数、`character_id`、`character_revealed`、`hp` 或 `max_hp`。

选将完成后玩家数组从领袖旋转，使领袖成为一号位，并按旋转后的数组索引刷新“玩家1”“玩家2”“玩家3”等显示名；稳定 `player_id` 始终不变，继续用于网络、回放和实体所有权。

## 触发事件

标准技能时机由 `RuleTimingCatalog` 统一维护，共228个名称，覆盖游戏与阶段、使用牌与响应、伤害、体力与生死、牌移动、判定与拼点、选择、技能自身、轮回生命周期及武将模式规则。核心通过 `MatchController._emit_rule_timing()` 创建包含 `player_id/source_id/target_id/data` 的 `RuleEvent`，由 `RuleTimingService` 统一派发并记录历史。完整名称与制作语义以《内容制作指南》的“无名杀228时机系统”为准，架构文档不维护第二份易漂移清单。

阶段、伤害、用牌与移动组件只负责在自己的真实边界调用统一派发端口：阶段使用成功进入 Begin 后保存 `body/end_emitted/after_emitted` 生命周期游标，选择恢复时从游标继续而不重复主体或时机；选择窗口通过 `resume_phase` 暴露真实规则阶段。若某个 Begin 技能通过统一阶段端口跳过当前主要阶段，控制器先终止该阶段仍在活动或暂停的 Begin 事件，再移除生命周期、派发唯一 `Skipped` 时机并进入后继；同一 Begin 尚未询问的技能不得跨越阶段边界恢复，跳过阶段也不补造主体、End 或 After。`phaseUse` 的 Begin 或主体内选择必须等待父事件排空后再重建唯一 `chooseToUse`，只有已进入 End/After 的生命周期才由恢复器继续结束阶段；没有生命周期记录的独立规则结算不会被误判为阶段结束。额外出牌阶段在登记时把 `discard/finish/turn_complete` 明确后继与次数一同排队，不再从恢复后的临时阶段反推去向。伤害在濒死选择期间把 `damageSource/End/After` 保存在待收尾上下文；使用牌由 `CardUseEventService` 维护五组整牌时机和四组动态目标时机；区域移动由控制器语义端口在 `CardMovementService.move_card()` 前后派发复合生命周期。目录和服务均不反向调用这些业务组件，因此不会形成“时机服务执行牌效”的胖模块。

以下蛇形命名事件继续作为迁移期兼容层：

- `phase_start`：回合开始阶段。
- `phase_finish`：回合结束阶段。
- `card_used`：实体牌进入处理区并声明目标后。
- `damage_before`：伤害扣减前，可修改 `amount` 或取消。
- `damage_after`：护盾与体力扣减后、濒死结算前；即使护盾完整吸收伤害也会触发，并公开 `shield_absorbed` 与 `hp_lost`。
- `lose_hp_before` / `lose_hp_after`：独立失去体力流程，绕过全部伤害事件与伤害历史。
- `hp_reduced`：体力实际减少后的统一事件，通过 `reduction_type` 区分伤害与失去体力；护盾完整吸收时不触发。
- `shield_after`：角色实际获得护盾后触发，包含来源、实际增加量和累计护盾。
- `recover_after`：实际回复完成后。
- `dying_begin`：角色进入濒死流程时。
- `dying_end`：角色回复至1点体力或以上并完成求桃流程结算时；上下文包含最终体力和救援成功标志。

旧兼容技能可继续通过 `RuleEventBus.subscribe(event_name, owner, callback, priority)` 注册；新标准技能使用 `SkillDefinition.subscribe_timing()`，由基类绑定技能持有者 ID 和四角色关系。组件卸载时基类会同时清理普通总线与独立 `TriggerManager` 订阅。迁移期 `RuleEventBus` 同样拒绝同一 `RuleEvent` 对象重入，并使用默认32层嵌套上限，防止旧订阅在到达 `TriggerManager` 之前就耗尽调用栈。

兼容 `damage_after` 表示伤害事实，但技能原文精确写作“当你的体力值受到伤害”时还必须检查 `hp_lost>0`；护盾完全抵消不满足。直接失去体力不进入伤害事件，失去护盾既不进入伤害事件也不进入 `hp_reduced`，因此两者均不能触发该措辞。

## 状态可见性

`GameState.to_dict(viewer_id, reveal_private)` 是唯一快照入口：

- 本人可见自己的身份、手牌与木牛“粮”。
- 本人可见自己已经确认的武将；领袖确认后立即对所有人可见，其他玩家在全员完成选将后同时公开。
- 他人只看到手牌数量和“粮”数量。
- 装备区、判定区、体力、护盾、存活与连环状态始终公开。
- 处理区实体 UID 始终公开，但快照不额外暴露非公开牌面；UI 仅用该集合核对中央表现是否仍属于活动处理区生命周期。
- `reveal_private=true` 仅供权威 AI、服务器调试与回放使用。
- 非响应者的活动选择快照会清空卡牌、目标、按钮、控制项、已选结果与活动上下文；局域网客户端不能从他人请求推断私有候选。
- 局域网客户端不接收 `random_seed`；当前行动玩家额外收到仅属于自己的 `local_legal_actions` 以完成无状态 UI 预览。

## 设计边界

工程不实现国战身份、势力明置、双将、暗将和国战专属牌。当前武将目录登记35名武将，合计使用71个唯一正式武将技能（含由【升变】动态授予的【奇袭】）；技能目录另登记飞扬、跋扈、共苦3个斗地主模式技能。所有后续扩展应新增配置或独立组件，避免把角色 ID、UI 节点或网络模式硬编码进规则服务。

## 平台适配边界

Android 平台差异由表现与输入组件消化，不进入 `MatchController`、规则事件树或数据快照：

- `project.godot` 维护1280×720逻辑视口、`canvas_items + keep` 等比缩放、固定横屏方向、Vulkan Mobile渲染、HiDPI，以及触点到标准鼠标指针的GUI兼容入口。
- `CardInputArea` 只把标准指针或未启用模拟时的单指触摸转换为卡牌激活、说明与手牌拖动信号；启用触摸模拟鼠标时忽略原始触点，长按和拖动不会直接提交规则动作。
- `PlayerTargetInputArea` 只把标准指针或未启用模拟时的单指触摸转换为目标激活、武将详情和局部指针信号；启用触摸模拟鼠标时忽略原始触点，武将牌自身仍不读取合法目标规则。
- `AndroidBackAdapter` 只把系统返回通知转换为标准 `ui_cancel`，未消费的页面级回退再交给 `MatchTable` 协调主菜单或局内菜单。
- `AndroidDisplayStability` 只在Android启动与应用恢复时设置60 FPS上限和VSync；Vulkan Mobile渲染与固定横屏由项目配置维护，组件不进入逐帧业务循环。
- `MobileKeyboardGuard` 是无状态平台工具，只在Android释放当前`LineEdit/TextEdit`焦点并隐藏系统软键盘；主菜单、连接入口和联机大厅在页面切换边界调用它，文本框主动编辑期间不参与输入内容处理。
- `export_presets.cfg` 只描述 APK 包、Android SDK、架构、权限与启动入口，不固定产物保存路径；局域网仍由 `NetworkGateway` 使用相同 ENet 协议，Android声明`INTERNET`与网络状态权限。

## 事件运行时边界

`EventScheduler` 是所有可暂停规则流程的唯一运行入口。事件内容步骤接收 `(GameEvent, EventScheduler)`，通过 `create_child()` 插入主体子事件，通过 `create_event(..., queue="after")` 插入收尾事件；父事件在子事件和暂停 token 全部完成前不会推进步骤。长期 `RootGameEvent` 使用 `held_open=true` 留在栈底，空闲状态为 `waiting_children`，不会把生命周期等待误当作暂停。`finish()`、`cancel()`、`neutralize()` 和 `abort()` 具有不同的回放与触发语义，不能用单个 `cancelled` 布尔值替代。

事件排空采用协作式批处理：`max_operations_per_drain` 默认 `256`，单次达到预算后只登记一个带单调令牌的空闲帧续跑，显式 `drain()`、重置或终局会让旧续跑回调失效。小事件仍在一次调用内同步完成，大事件树会把执行权归还主循环，使输入、网络与 `StallWatchdogService` 不会被长同步栈饿死。事件内容若在没有子事件、暂停 token、终态或步骤游标变化的情况下连续停留于同一步，`max_repeated_step_executions` 默认 `2048` 次后以 `runaway_step` 只中断当前事件、清空其普通与 after 队列、记录 `fault` 历史并发送 `event_faulted`；父事件继续从标准结果回传边界收尾。该熔断只防御无等待同步自旋，不限制经过真实选择、网络等待或子事件返回的合法 `redo()`。

`GameFlowTransitionCoordinator` 是相邻阶段切换的唯一意图协调器，内部复用 `GameFlowPacer` 的 `phase_transition` 计时业务键但不承担玩法判断。`MatchController._schedule_phase_transition()` 必须在登记前确认对局ID、当前角色与当前阶段仍匹配，并把同一校验器交给协调器在到期时复核；仍有效的首条转换不会被重复或冲突恢复覆盖，已失效的旧任务才允许被新意图替换。协调器在执行业务回调前清空自己的待办，因此回调可安全登记下一阶段；重新开局与失败开局必须先调用 `cancel_pending()` 再清空其他流程计时器。

`ChoiceRequest` 的请求 ID、事件 ID、响应者、候选 UID、选择数量和 `base_context/active_context` 由权威端保存。技能临时替换选择上下文必须使用 `backup_context()`，取消或 AI 失败时使用 `restore_context()`；UI、AI、网络都提交 `ChoiceResponse`，迟到或跨事件响应会被拒绝。现有 `PlayerAction.choose_cards` 是桌面兼容封装，控制器会在边界转换成同一 `ChoiceResponse`。

`CardMovementService` 是迁移期的唯一实体牌移动入口。新代码必须传递 `event_id`、`reason` 和 `visible_to`，不得直接写入牌的 `zone/owner_id` 或同时修改多个区域数组。尚未迁移的旧规则操作只允许通过控制器兼容函数调用，并应在后续版本移除。

`CardUseEvent` 已是可暂停的真实调度栈父事件。实体材料先在 `lose` 子事件进入 `processing`，随后依次执行 `useCard0/useCard1/yingbian/useCard2/useCard`。四组目标时机采用“阶段优先、每次执行后重新读取目标数组”的 `redo` 循环：全部当前目标完成 `useCardToPlayer` 后才进入 `useCardToTarget`、`useCardToPlayered` 和 `useCardToTargeted`；每轮按当前行动座次生成遍历副本，并按目标出现次数判断是否已经触发，因此动态新增目标会补齐当前及后续时机。死亡、离场或 `excluded` 目标不会进入虚假 `content`。`directHit`、`excluded` 和 `customArgs` 保存在父事件共享上下文，直击同时限制【闪】和【无懈可击】响应。每个使用牌修改窗口按“派发 → 结果提交”两步执行，可选技能应答前不提交结果：`excluded` 与 `directHit` 在提交时与实时集合按首次出现顺序去重合并，`customArgs` 则以事件数据为权威最终值——控制器伤害加值端口在写入共享上下文时，会同步写回仍在等待应答的窗口事件，因此同步技能与异步选择恢复后的登记都不会被派发前快照覆盖。每个实际目标拥有独立 `content` 子事件，响应与装备选择直接挂在该事件下；全部同步效果和暂停 token 完成后只创建1次 `contentAfter`。响应牌不建立第二个 `CardUseEvent`，而是派发 `respondBefore/respondBegin/respond/respondEnd/respondAfter`；因此需要同时覆盖普通使用与响应使用的技能应订阅 `useCard` 和 `respond`，再按定义类别统一过滤。默认弃置通过 `CardUseEvent.after -> orderingDiscard -> cardsDiscard` 移出处理区，终局中断时不会提前回收。判定继续使用 `judge -> judgeResult -> cardsDiscard` 关系，判定牌先从牌堆进入 `processing` 并公开表现，再进入弃牌堆。

当前状态：当前标准身份局已登记卡牌的使用生命周期、逐目标效果、响应选择与处理区回收已经进入真实事件树；选择请求、暂停 token、触发排序、查询修正、虚拟牌、技能延迟结算、阶段生命周期游标和移牌历史均可关联稳定父事件。局域网 ENet 房间已经提供权威房主、成员大厅、私有快照、掉线 AI 托管与携会话令牌的对局内断线重连；公网匹配、主机迁移和回放执行器仍未提供。伤害前修改窗口已经进入可暂停步骤序列；宏观六阶段主体、伤害尾部、濒死、死亡与部分判定仍包含兼容段。因此“当前标准卡牌使用流程完成事件化并可局域网游玩”不等于“无名杀全部模式、武将和扩展包已完整复刻”。

## 停滞自修复边界

`StallWatchdogService` 是挂载在 `MatchController` 下的独立看门狗组件（缺失时由控制器兜底创建），采用与其他组件相同的解耦边界：只调用控制器三个公开端口，不直接读写事件栈、请求索引或玩法状态。

- `get_stall_diagnostics()`：返回“是否可监控、是否有人类待办、进度指纹”。进度指纹覆盖对局ID、动作序号、事件历史条数、事件分帧续跑、待办请求（含修订号）、活动暂停令牌、兼容选择与同时无懈数量、AI调度标记、阶段转换语义键、其他流程任务、机缘进度、换将过渡与判定标志；任何真实推进都会改变指纹。局域网客户端（非权威）与终局不监控；用户主动打开日志或武将详情造成的对局暂停不监控，机缘选择暂停仍继续监控。
- `is_waiting_for_human_input()`：判定是否存在“可以实际作答的人类”待办。AI、托管、死亡与无人认领座位不算人类待办；离场但存活的角色仍可作答。座位归属判定：离线模式为本地第一视角或控全接管，局域网房主模式为本机或已映射远端 peer。该函数为真时看门狗永远不会执行强制修复。
- `perform_stall_self_repair(repair_kind)`：执行分级修复并返回可序列化报告。`human_reminder` 只重发界面提示；`soft` 只重排既有异步任务（预开局AI统一分派 `_redrive_pre_game_ai_progress`、AI兼容选择重排、同时无懈AI计时器重启 `_redrive_pending_negation_ai_tasks`、机缘结算轻推）；`hard` 在软修复之上追加：孤儿暂停令牌清扫 `_release_orphan_runtime_pause_tokens`（gameplay/conquest_replacement按权威标志、choice按待办请求、未知通道按所属事件终态判定）、无人认领存活座位转入标准托管、死亡应答者待办关闭 `_close_unanswerable_choice_requests`（无懈走标准放弃提交，其余走统一中断保护）、连续两轮硬修复仍卡住的AI兼容请求强制中断。修复前后指纹对比决定“有效”；只有有效修复才写入对局日志并发出 `self_repair_performed` 信号，由牌桌经 `InformationBoxLayer.show_notice()` 显示提醒横幅。

看门狗以 `PROCESS_MODE_ALWAYS` 运行（机缘选择等待期间场景树暂停，而这正是需要监控的窗口），检测节奏与三级阈值全部为 `@export` 参数。托管接管、暂停恢复与看门狗软修复共用同一预开局AI分派与无懈重排入口，避免多份阶段清单彼此漂移；机缘代选统一走 `OpportunitySystem.choose_for_managed_player()`（AI估值+权威 `submit_choice` 复核），不形成第二条写路径。

## 对局模式

- 标准身份局 `identity` 与斗地主 `doudizhu` 共用 `MatchController` / `IdentityRules`。
- 机缘大乱斗 `opportunity_brawl` 是独立模式 ID，支持2至10人并继承身份分配、胜负、死亡奖惩与选将规则；只有该模式默认启用 `OpportunitySystem`，普通身份局保持原规则。
- 1v1车轮战 `wheel_duel` 由独立 `WheelDuelSelectionService` 管理公共候选槽、明暗可见性、`122221` 抓将游标、双方私有五将集合与最终三将顺序；槽位被选后写入 `picked_by_player_id` 而不从池中移除，观察者快照只投射 `self/opponent` 相对归属并保持槽位原始明暗状态，暗置槽仍不公开真实武将ID。快照的 `can_select` 在抓将阶段表示“当前抓将者是否为本观察者”，供界面逐槽决定可点击性；抓将仍由 `get_current_drafter_id()` 单点驱动，不存在双方并行的抓将游标。该服务不读取牌堆、体力、技能实例或UI节点。
- 过关斩将 `conquest` 由独立 `ConquestModeService` 集中维护关卡、难度、逐玩家复活次数、敌方集合与全局敌方机缘历史。角色总数支持2（离线单人：1玩家+1敌人）与4/6/8（局域网2至4名玩家+等量敌人），座次按“玩家1、敌人1、玩家2、敌人2”交替且偶红奇蓝；`configure_participants()` 接收玩家与敌人ID数组并为每名玩家独立授予难度机缘，旧 `configure()` 单人签名与旧存档标量字段（`player_id/enemy_player_id/player_revives_remaining`）继续通过回退读取保持兼容。单个敌方死亡只完成自身死亡与区域清理并保持阵亡，控制器必须以 `is_current_level_cleared()` 判定本层全部敌方均已阵亡后，才推进一次关卡、统一发放一次关卡奖励并原子预选全体新敌将；武将池充足时优先排除玩家武将和本批已选敌将，极端不足时由服务允许重复以保证流程可继续，任何回退也必须在状态写入前完成整批预选，不能产生半完成的层切换。胜负规则为全部红方玩家死亡才判蓝方胜。联机局的开局与整层换将后机缘经 `MatchController._begin_conquest_group_opportunity()` 按 `match_options.conquest_opportunity_choice_mode` 分流为全员同时投票或各自选择；临时退出存档仍仅限离线单人局。阵亡玩家只在完整关卡提升时由 `_revive_dead_conquest_players_for_new_level()` 复活并回到游戏初始状态（重置机缘历史与获得/临时技能、重装固有技能实例、恢复初始体力与复活次数、重摸开局手牌），复活先于本关全体机缘选择执行，`ConquestModeService.reset_player_revives_to_initial()` 负责按玩家ID恢复难度初始复活次数。
- 模式选择保存在 `GameSettings.next_match_mode`，开局锁定到 `GameState.match_mode`。
- 身份分配、胜负、队友关系、模式技能与开局体力加值集中在 `IdentityRules`，控制器只负责执行移动与安装。
- `PlayerState.wheel_duel_lineup`、`wheel_duel_lineup_index` 与 `wheel_duel_defeated_count` 保存对战阶段最小权威进度。完整阵容只进入本人或权威快照，公共快照只暴露当前已亮武将与累计阵亡数。
- 车轮战换将由 `MatchController` 编排区域移动、武将应用、单玩家技能重装、补满体力、摸4张与当前回合中断；胜负仍由 `IdentityRules.evaluate_winner()` 统一返回，避免选将服务或界面直接结束游戏。

### 机缘组件边界

- `OpportunityCatalog` 只保存106张机缘卡的稳定 ID、品质、需求钦定正文和可序列化效果参数，其中5张灰色机缘仅由过关斩将关卡或难度授予；目录不读取对局状态，也不执行任何效果。首次查询建立稳定ID和品质索引；完整定义接口继续返回独立副本，高频规则使用 `has_card/get_effect_id/get_effect_count/get_skill_id` 读取不可变标量。玩家机缘效果按只追加历史增量汇总；红色刷新机缘例外地通过控制器端口整体替换历史并主动失效缓存、重装机缘来源技能、按差额调整体力上限与额外手牌上限，过关斩将服务则在每次奖励追加后统一重建敌方ID、效果合计与有限技能机缘缓存，同一关内伤害、摸牌、次数、换将技能恢复均不再扫描完整历史或深复制定义。新增的单体翻面与全体其他角色翻面效果由解析器排入可暂停队列，逐名调用控制器公开翻面端口，嵌套结算结束后才继续下一张机缘。新增【祥音】【聚寇】【光覆】【血仇】四项技能机缘只声明 `skill_id`，不复制技能参数：轮回技（聚寇、血仇）由技能实例在 `bind()` 时经 `register_reincarnation_skill()` 建立轮回状态，限定技（祥音、光覆）的固有额度由 `SkillDefinition` 基类管理，目录不保存第二份次数或轮回配置。
- `OpportunitySystem` 是可插拔场景组件，负责每轮 `1/N` 同概率检定（判定点位于一名角色的**回合开始前**，此时该角色的回合事实尚未写入）、轮末保底、每人私有三选一、选择暂停令牌和从触发角色（即将开始回合的那名角色）开始的逆时针结算队列。**全部参与者同时选择**：进入 `choosing` 时一次性把全体参与者写入 `pending_chooser_ids`、`current_chooser_id` 置 `-1`，任一尚未提交的成员均可经同一 `submit_choice` 独立提交，不存在当前玩家阻塞后续玩家的串行游标，联机下每名客户端无需等待他人即可操作；内置AI在各自选择模式下于同一调用栈内批量估值提交（投票模式延后一帧以先公开“可投票”状态），空候选AI保留在集合中由看门狗按同一估值入口代选。`force_trigger_vote_for_players()` 在此之上提供全员同时投票流程：只抽取一组共享候选并复制给每名参与者，选择阶段只公开完成者ID；全部提交后按票数取最高者（平票用对局随机源在同票中随机），流程先进入默认持续2.0秒的 `revealing` 阶段并向所有观察者公开“玩家→票面”与当选机缘，再进入 `resolving`，把当选机缘写入每名存活参与者的公开历史并逐人结算。额外回合不进行触发检定；同一轮成功触发后不再重复触发。组件按局缓存五种随机品质的ID池，随机历史记录候选ID、逐玩家选票与当选ID；同步效果的结算者游标不单独触发整桌刷新。
- `AhhaMomentSystem` 是可插拔场景组件（`scripts/core/ahha_moment_system.gd`），负责欢愉技的回合开始前触发判定、参演序列构建与串行演出推进。触发概率与机缘选择使用同一算法口径（每轮开始时按在场角色数倒数锁定，整轮不变），**轮末保底也完全同构**：本轮所有普通回合开始前的判定都没有通过时，控制器在轮末调用 `try_trigger_at_round_end(finished_player_id)` 强制补触发一次，因此每轮必定有一次常规阿哈时刻演出；保底与逐回合判定共用同一轮次额度（`_triggered_this_round`），不掷骰、不消耗随机数、不写随机历史。机缘与阿哈时刻的**额度彼此独立**：同一轮内两者各自至多触发一次，额外回合不参与判定；技能请求的额外演出不写 `_triggered_this_round`，因此不占用该额度。判定点位于机缘判定之后、回合事实建立之前，因此演出期间 `current_player_id`、`turn_number` 与阶段游标都尚未更新。参演序列由纯查询入口 `build_performance_order()` 生成：第一排序键为技能元数据 `performance_number`（参演编号）升序，第二排序键为“以触发角色起算的座次正序”（轮末保底时以刚结束回合的角色起算），第三排序键为技能稳定 ID 字典序（`sort_custom` 不是稳定排序，同编号同座次必须靠它固定次序）；同一角色持有多个同编号欢愉技时它们全部进入队列并依次演出，不会被合并或只取首项。死亡、离场与临时失去欢愉技的持有者在构建与执行前各过滤一次。**场上没有任何可执行欢愉技时整段流程直接跳过**：不消耗随机数、不写入随机历史、不占用本轮额度，因此空候选判断必须位于随机取值之前（轮末保底同样遵守）。组件逐项串行执行 `SkillDefinition.perform_joy_skill()`，由技能在效果（含嵌套结算）结束后调用 `finish_joy_skill_performance()` 回报；全部结束后由 `_complete_all_performances()` 按触发来源分流——常规演出经 `continue_after_ahha_moment()` 交还回合开始链路，轮末保底经 `continue_after_round_end_ahha_moment()` 交还轮末流程，技能请求的演出只回调请求技能。存在嵌套结算屏障时通过 `defer_ahha_moment_resolution()` 登记通用续接，由 `ahha_moment_resolution` 分支恢复。组件不新增任何 `GameState` 字段，因此不改变存档、回放与联机快照结构；三种触发来源各写一条独立模板的公开日志（`阿哈时刻：…`、`阿哈时刻（轮末补触发）：…`、`额外阿哈时刻：…`），只用于区分来源。除常规回合开始前的概率触发与轮末保底外，组件还提供三条**技能请求**入口：`try_perform_single_joy_skill(player_id, skill_id, completion_context)` 令指定角色立即发动其指定欢愉技，`try_perform_all_owned_joy_skills(player_id, completion_context)` 令指定角色按参演编号顺序依次发动其**全部**可执行欢愉技（队列由 `_build_owned_performance_entries()` 构建，同一角色内部无座次差异，因此固定为参演编号升序 → 技能稳定 ID 字典序），`try_trigger_extra_moment(trigger_player_id, completion_context)` 立即触发一次完整额外阿哈时刻。三者都跳过触发概率判定与本轮额度，但仍要求参与者当前**确实可执行**（欢愉技标签、效果未被“非锁定技失效”压制、持有者存活且未离场），且同一时间只允许一场演出；演出完成后经 `continue_after_standalone_joy_performance()` 把控制权交回请求技能（`SkillDefinition.continue_joy_performance()`），**不推进回合开始游标**，因此只有常规演出才走 `continue_after_ahha_moment()`。三个入口都返回布尔值表示是否成功建立队列，请求方必须自行处理失败分支（例如【咬它】在目标没有任何可执行欢愉技时改为给予额外出牌阶段）。
- `MatchController._continue_turn_start_prelude()` 是回合开始前的唯一事件链，按“机缘选择判定 → 阿哈时刻判定 → 建立回合事实”固定顺序推进，两个 `allow_*` 参数区分首次进入与某环节结算后的恢复，避免同一环节被重复判定。原三处直接调用 `_begin_turn_after_opportunity()` 的位置（`_start_turn`、`_start_queued_or_normal_turn` 的待开始角色恢复、`continue_after_opportunity` 的回合开始前分支）统一改为进入该链，因此语义仍然只有一条。
- `GameState.to_dict()` 对普通观察者先复制机缘公共字段，再只投射该观察者的3张私有候选，不会先深复制全体2至10名角色的候选后再删除。已选完整机缘定义保留在组件私有结算映射；投票收齐前公共状态只承担阶段与完成进度，收齐后的 `revealed_votes` 和 `winner_card_id` 才是面向所有观察者的公开结果。
- `OpportunityEffectResolver` 只把机缘效果转换为 `MatchController` 的摸牌、体力、伤害、区域选牌、技能授予、座位/武将牌/手牌/装备交换、虚拟用牌、持续视为、限时离场、分类取牌与额外回合公开端口。批量实体移动按稳定UID逐张执行，目标选择、濒死、装备触发等嵌套流程通过 `defer_opportunity_resolution()` 和 `has_nested_settlement_barrier()` 完成后再继续下一张机缘。
- `MatchController.swap_player_seats()` 交换 `GameState.players` 中两名完整角色对象而不改变稳定玩家 ID；当前回合角色仍按 ID 保持，回合结束后从交换后的座次数组寻找下一名角色，因此座位变化会立即影响后续行动顺序。
- `grant_acquired_skill()`、`can_use_acquired_skill()`、`consume_acquired_skill_use()` 与 `remove_acquired_skill()` 组成局内技能生命周期端口；相同技能不重复安装，每回合限制按全局 `turn_number` 重置，累计限制在本次成功发动完整生效后移除技能。

### 过关斩将存档边界

- `ConquestSaveStore` 是纯静态持久化边界（`scripts/core/conquest_save_store.gd`）：只负责把控制器生成的可序列化存档字典写入 `user://conquest_save.dat`、读取并做版本/模式基础校验、以及清除文件；使用 `var_to_str` 文本格式完整保留64位整数与类型化数组，不读取 `GameState`、不理解规则语义、不持有节点。当前存档格式版本为1，版本不符或无法解析的文件统一按无存档处理。所有函数都接受可选路径参数，回归测试使用独立测试路径，绝不触碰玩家真实存档。
- `MatchController` 提供四个临时退出端口：`supports_conquest_temporary_exit()`（仅离线进行中的过关斩将）、`request_conquest_temporary_exit()`、`cancel_conquest_temporary_exit()` 与 `is_conquest_temporary_exit_requested()`。请求入口先尝试立即捕获，失败时只设置控制器私有挂起标志并写日志，不中断任何进行中的结算。
- 存档捕获共用同一空闲判定 `_is_conquest_settlement_quiescent()`（处理区、濒死队列、机缘流程、待办选择与判定、活动卡牌结算、延后技能结算、规则续接、待派发触发、伤害收尾、装备触发队列、回合尾部等待、独立阶段与额外弃牌阶段全部为空），并存在两级捕获点：
  - **出牌询问空闲点** `_try_capture_conquest_temporary_exit_at_play_idle()`：请求时若当前处于出牌阶段且空闲判定通过（另加技能多步间隔与已排队阶段切换检查），先以系统响应关闭常驻 `chooseToUse` 并排空事件树，再以 `resume_kind="play_phase"` 捕获。同一函数也挂在 `_begin_play_choice()` 顶部——每次操作结算完成、出牌询问即将重建时就是“操作后”的最近空闲点。常驻询问不属于结算，恢复时按当时合法动作原样重建，因此存档仍不需要序列化事件栈或选择请求。
  - **回合边界** `_try_capture_conquest_temporary_exit()`：挂在 `_start_turn` 入口，以 `resume_kind="turn_start"` 捕获尚未开始的下一回合。额外回合链的进度已随 `turn_flow` 入档，边界捕获不再要求额外回合队列为空；换将过渡仍然阻塞。机缘大乱斗的“回合开始前”机缘判定位于该捕获点之后，且只在自动触发模式生效；两者使用的 `resume_kind` 取值互不相同（存档为 `turn_start`，自动机缘为 `before_turn_start`），过关斩将不会因自动机缘改变存档边界。
  - 两类捕获都递增 `_ai_drive_token` 作废旧AI计时器、消费挂起标志、由 `_build_conquest_save_data(resume_kind, acting_player_id)` 构建存档并发出 `conquest_exit_save_ready(save_data)`。文件写入与返回主菜单由牌桌在信号回调中完成（写档后延迟一帧调用标准主菜单返回流程），规则核心不接触文件系统。
- 存档内容：`conquest_state` 全量、双方 `PlayerState.to_dict(本人, reveal_private)` 加每回合字段与完整回合/响应/伤害历史、摸牌堆与弃牌堆完整顺序、`match_options`、轮数/回合数/动作序号、恢复类型与行动角色、`phase_index`、`turn_flow`（额外回合链、额外出牌阶段计数/返回点/活动上下文、主要阶段转换、阶段生命周期游标、本回合用牌记录）、`CardInstance._next_uid`、随机源种子与内部状态，以及 `_capture_skill_runtime_states()` 反射捕获的全部技能实例可序列化脚本变量（限定技已用标记、每轮限次记录等跨回合状态；Object/Callable 等引用类型自动过滤，由恢复流程的 bind/install 重新建立）。
- `resume_conquest_match(save_data)` 与 `start_match()` 共用三个运行时重建入口：`_teardown_previous_match_runtime()`（上一局清理）、`_rebuild_match_rule_services_and_root_event()`（规则服务与长期根事件）与 `_reset_per_match_progress_state()`（每局私有游标），保证两条开局路径的清理与重建清单不彼此漂移。恢复路径跳过选将、起始手牌与手气卡：直接以 `PlayerState.from_authoritative_dict()` 重建双方角色与牌区、按存档顺序重建两个公共牌堆、`ConquestModeService.restore()` 绑定既有 `conquest_state` 而不重建关卡历史、`_restore_conquest_turn_flow_state()` 回填全部回合与阶段游标、`_install_all_character_skills()` 重装固有与模式技能、`_reinstall_saved_runtime_skills()` 补装获得/临时技能实例（保留存档限次记录）、`_apply_skill_runtime_states()` 回写技能内部状态。最后按恢复类型分流：`turn_start` 调用 `_start_turn(存档行动角色)` 开始下一回合；`play_phase` 恢复当前角色与出牌阶段、新建回合运行时事件并把恢复的阶段生命周期重挂到该事件（`_remap_restored_phase_lifecycle_parents()`），再经 `_begin_play_choice()` 与统一AI安全出口继续同一回合，不发生摸牌或阶段时机重放。恢复前 `get_conquest_resume_validation_error()` 在破坏旧状态之前完成深层校验：版本、模式、离线、恢复类型合法、行动角色存活、双方武将与全部实体牌（含视为牌原始定义）在当前目录中的存在性。
- 存档生命周期由界面层维护：过关斩将终局（`match_finished`）清除存档；全新过关斩将开局（主菜单或局内重开走 `start_match`）清除存档；恢复失败清除存档并提示。恢复成功不清除，未再次临时退出便放弃对局时保留旧检查点。主菜单按“选中过关斩将且存档可解析”切换主按钮文字，牌桌以同一条件分流“继续”与“新开局”，二者判断来源一致。

## 离场与内容扩展架构

`PlayerState.out_of_game` 是临时离场的唯一权威状态，不创建“半死亡”角色或 UI 专用状态。`out_of_game_until_round` 只记录“离场直到本轮结束”的自动返场轮数，默认 `-1` 表示普通离场且不自动返回。`GameState.get_alive_players()`、`get_next_alive_player()`、`get_previous_alive_player()`、`CardRuleService`、`MatchController`、`SlashCardEffect` 与 `SkillDefinition` 分层过滤离场状态：状态层处理下家与上家座次，规则层拒绝普通用牌和目标，控制器拒绝普通动作和资源变化，效果层中止已失效目标，技能基类停止普通订阅。离场技与机缘只通过明确参数获得严格限定的选择、虚拟用牌或资源例外，不会放宽其他角色的普通操作。

牌堆观看与排序由三个控制器端口组成：私有快照、按 UID 获得、按 UID 重排。它们不保存 UI 引用，也不把观看牌提前移入公共处理区。`choice_type="arrange"` 将顺序与顶行长度编码到 `ChoiceResponse`，`CardSelectionPanel` 只是该通用协议的一个视图实现，后续观星、预知和换序效果可直接复用。目标区域选牌同样保持视图通用性：【过河拆桥】与【顺手牵羊】只在规则上下文区分弃置/获得，窗口均使用固定尺寸、纵向区域与纵向滚动。面板只转发明置 `CardView` 的 `information_requested/information_dismissed`，牌桌再接入唯一 `InformationBoxLayer`；因此选择组件不持有信息框实例，也不会从牌背构造隐藏信息。

无材料虚拟牌沿用 `CardUseEvent`，但逻辑代理与实体材料严格分离。`VirtualCard.material_card_uids=[]` 表示没有实体费用；`virtual_proxy=true` 时 `lose` 子事件只处理真实材料数组。该约定让主动视为牌、响应视为牌、日志、时机、目标结算与回放保持同一事件树，且不会把代理牌错误当作玩家区域内的材料。

新内容的规则修正优先放入 `SkillDefinition` 的纯查询钩子，例如距离解除、外部弃置保护和无材料响应定义。`MatchController` 仅负责汇总实例和执行二次校验，`CardRuleService` 保持不依赖具体武将 ID；这使技能组件可独立安装、卸载、测试和复用。

## 轮回技与次数规则架构

轮回技遵循“技能效果与进度状态分离”：具体技能文件只判断触发条件并执行摸牌、回复、标记或伤害；`SkillDefinition` 提供 `begin/complete/get` 包装；`ReincarnationSkillService` 修改 `PlayerState.reincarnation_skills` 并派发生命周期；`MatchController` 只转发公开端口和广播新快照。局内技能按钮、武将悬停和右键详情从同一观察者快照取 `section_index`，交给无状态规则视图 `SkillDescriptionView` 分段着色。该数据流不把运行时技能对象、服务对象或界面节点写入快照。

限定技与觉醒技的固有额度保存在每个 `SkillDefinition` 运行时实例；觉醒元数据强制派生锁定与限定语义。控制器把普通限定技的已用稳定ID追加为公开 `used_limited_skill_ids`，并通过 `restore_limited_skill_use()` 只调用指定实例的 `restore_limited_use()`，使【光覆】等单项复原不重建其他技能或改动轮回状态；旧技能若另有私有已用标记，可在虚方法中同步清理。同一快照另写入 `used_intrinsic_use_skill_ids`，即 `get_used_limited_skill_ids(player_id, true)` 的结果，额外包含觉醒技：武将悬停资料与右键武将详情读取该字段判断“已释放”的整块变淡状态，技能按钮不使用它、仍只按 `used_limited_skill_ids` 显示限定技三态，而 `used_limited_skill_ids` 继续服务复原入口的候选集合，两者分开以保证界面需要不改变规则候选。`restore_character_card_skills()` 则只卸载并重建当前武将的全部固有技能实例，保留模式、临时和局内获得技能；轮回状态不属于实例，因此由服务在重绑定前另行重置为轮回数1、①并解除永劫。这样单项额度、脚本私有阶段次数和可序列化轮回进度各由自己的组件复原，不依赖反射修改任意变量名。

`reset_skill_play_phase_usage(player_id, skill_id)` 是“视为本回合未发动过某技能”的独立入口，只复原指定技能自己的出牌阶段额度，不重建实例、不改写限定次数、轮回进度、每回合次数与其他技能状态。它在目标实例声明的脚本变量中按项目统一命名约定（`_used_this_play_phase`、`_used_current_play_phase`）定位额度字段：布尔字段置 `false`，整数字段置 `0`，找不到约定字段时返回 `false`。之所以不复用 `restore_character_card_skills()`，是因为重建实例会连带清空技能自己保存的运行时记录（例如【弑魂】的上一批目标、【星落】的重铸序列）；技能若把阶段额度存在其他字段，覆写 `SkillDefinition.reset_play_phase_usage()` 即可，控制器无需增加分支。这类运行时记录应明确“由哪一节写入”：【弑魂】的 `_last_selected_target_ids` 只由①改写，②每次只读取其中通过存活、离场与目标技能限制复核的子集，因此反击不会因为个别目标阵亡而收缩记录，也不会在记录上留下“执行到哪一步”的中间态。

技能正文标签识别由纯静态函数 `SkillDefinition.description_declares_tag(description, tag)` 提供：它只承认未被引号包裹的标签声明，引号内的提及不计入，使技能引用他人技能类型时不会把自己算作同一类。该函数当前只服务“出牌阶段限一次”这一没有元数据标签的技能类型；【奇袭】的阶段额度复原分支与升变 AI 的目标优先价值共用它，规则层、AI 与内容测试因此不会出现两套识别口径。

**轮回技标签**是轮回技判定的唯一来源：每个轮回技在技能源码元数据中显式声明 `reincarnation=true`，`SkillDefinition` 只读取该字段、不再从正文推导，因此正文里只是引用他人轮回技的技能（例如【回涛】）不会被登记为轮回技。标签与正文的一致性由 `GameDatabase` 加载期双向校验：`SkillDefinition.description_declares_reincarnation_type()` 与欢愉技共用同一套识别口径（内部 `_description_declares_type_tag()`）——以正文**第一个句号**为类型段上界，只有出现在该上界**之前**、且右侧紧跟**逗号**的“轮回技”才算类型声明，句号不再作为类型声明证据。因此【升变】“轮回技，……”与【永劫】“锁定技，轮回技，……”算声明，而【回涛】“轮回技进入下一个轮回时……”、位于第一个句号之后的引用、以及句末式写法（如【咬它】“然后令一名角色发动其欢愉技。”）都不算。声明与标签不一致时写入 `validation_errors` 并阻止对局开始。该静态函数只用于校验，不参与任何运行期判定。

**轮回节阶段额度的两处结构性保证**（`MatchController` ↔ `ReincarnationSkillService` 的契约）：

- **归属节快照**：`begin_reincarnation_activation()` 在效果执行前把当时的 `section_index` 写入 `pending_activation_section_index`，`complete_reincarnation_activation()` 只消费该快照并在消费后复位。效果内部可能同步触发外部推进（例如【征服】在【堪杀】③的 `damage()` 内令全部翁法罗斯轮回技进入下一个轮回节），事后重读 `section_index` 会把推进后的节登记为“本次发动”，同时漏登记真正发动过的节；`cancel_reincarnation_activation()` 是与之配对的失败分支复位入口，只清空快照、不登记额度、不推进轮回节。
- **阶段实例号**：控制器持有唯一游标 `_play_phase_scope_sequence`，并在**唯一的重置入口** `_note_play_phase_entered(player_id)` 中先递增实例号、再调用 `reincarnation_skill_service.on_play_phase_started(player_id, scope_id)`。普通出牌阶段、由主要阶段转换得到的出牌阶段、排队额外出牌阶段、独立额外出牌阶段以及读档恢复进入出牌阶段这五条路径全部只调用该入口，不得直接调用服务。服务侧 `_effective_used_sections()` 在读取额度时比较实例号，不一致即惰性清空——于是“某个阶段入口漏调重置入口”不再导致额度跨阶段泄漏。`get_play_phase_scope_id()` 只读该游标，不参与结算顺序；`is_play_phase_of(player_id)` 供“是否自己的出牌阶段”判定使用，它读取选择窗口背后的真实规则阶段（`_get_effective_rule_phase()`），避免嵌套选择期间公开阶段临时为 `choice` 时整条额度登记被跳过。该游标随既有 `turn_flow` 存档字段一并存取，不新增存档版本。

`reset_all_other_skills()` 是“重置所有其他技能”的权威入口：它复用 `restore_character_card_skills()` 重建武将固有技能，从而一次性覆盖限定技额度、阶段次数与轮回进度，因此不必逐项列举。它必须把调用方传入的排除项实例完整保留——被排除的技能既不参与重置，也不能在重建后换成新实例，否则其限定额度标记会被清零并变成可重复发动。实现上先记下排除项旧引用，重建后卸载重建出的同名新实例、回填旧实例并**重新调用其 `install()`**：重建过程已统一卸载了旧实例，若不重装，回填进来的旧实例将不再持有任何时机订阅，其第二段延迟效果会永久失效。除固有技能外，局内获得技能的已用次数与统计基准在此处逐项归零，但来源标识与三类上限定义保持不变。

`reset_all_skills()` 是同一实现的“无排除项”公开端口，供【揭质】在结算目标为持有者本人时使用（技能原文“若目标为你，你重置你的所有技能”）。它与 `reset_all_other_skills()` 共享底层私有函数 `_rebuild_character_skills_and_zero_usage()`，两个公开端口只负责各自的前置校验、日志与状态广播，唯一语义差异是排除项为空字符串——即调用方技能自身的限定技标记、阶段额度与每局私有计数同样归零，**限定技（含【留白】）与全部固有技能都在重置范围内**。之所以不把排除项参数留在同一入口：`reset_all_other_skills()` 的名字与日志都以“除……以外”为前提，让它在空参数下表达“全部”会使调用方与维护者无法从签名判断实际语义。`reason` 参数只写入 `changeSkillsAfter` 时机数据与日志，不参与任何规则判定。

`remove_skill(player_id, skill_id, reason)` 是**「失去某个技能」的唯一通用入口**，供后续任何“失去技能”设计直接调用，不需要各自实现卸载流程：解析目标角色 → 取该玩家的技能实例表 → 卸载实例（释放时机订阅、持续标记与纯查询修正器）→ 从实例表移除 → 清空该技能在 `acquired_skills` / `temporary_skills` 中的记录 → 经 `reincarnation_skill_service.clear_skill_state()` 清理其轮回公开状态 → 写日志 → 广播状态。技能本来就不属于该角色时（既没有实例也没有记录）返回 `false`，不写日志也不广播，因此调用方无需前置判空。`remove_all_skills(player_id, reason)` 是批量入口：先快照当前技能ID（`skill_instances_by_player` 的键 ∪ `acquired_skills` 的键 ∪ `temporary_skills` 的键，按稳定ID去重）再逐个走同一通用接口，最后清空 `reincarnation_skills` 与 `recorded_card_names`，本次已无技能可失去时返回 `false`。**两个端口都不记录任何名单或标记**：失去是一次性移除，不是不可逆状态，因此之后通过机缘卡、军功、复原武将牌与换将等来源再次获得同一技能时照常安装与发动；相应地 `_install_all_character_skills()`、`_reinstall_character_skills_for_player()`、`grant_acquired_skill()`、`_reinstall_saved_runtime_skills()` 与 `restore_character_card_skills()` 五条装配路径都**不再做任何按技能ID的拦截**，只按各自来源正常装配。清理顺序中「先快照技能ID」必须在卸载之前完成，否则“曾拥有哪些技能”这一信息会随实例一起消失；【留白】的结束阶段回调还必须先把清算登记置为失效，以防御卸载自身实例时的重入。

`pick_random_candidate_index()` 统一技能侧的随机下标取得：传入候选数量，返回 `[0, 候选数量)` 内的下标，`候选数量 <= 0` 时返回 `-1`。接口刻意返回**下标**而非元素，使调用方对异构候选数组保有类型控制；每次调用都把候选数量与选中下标写入 `state.random_history`，使固定随机种子下的对局全程可复现、可回放。

`PlayerState.recorded_card_names` 是【解构】的公开记录容器：保存稳定牌ID、按记录先后排列并自动去重，跨回合与跨轮次保留。它同样进入 `to_dict` 的公开部分，因此界面、对手AI与局域网观察者读到同一份数据，而**不**放进仅本人可见的 `character_form_state`；展示名由 `GameSettings.resolve_card_name` 在读取时按当前名称模式解析，所以切换原文名与自定义名不会影响记录本身。控制器以 `record_card_name()`、`remove_recorded_card_name()` 与 `get_recorded_card_names()` 三个薄端口读写，技能不直接修改玩家状态数组。

记录容器的表现入口是一条**中性扩展**：`character_corner_text_entries` 的每个条目可携带 `view_kind` 稳定字符串，核心层只负责存取、排序与序列化，**不解释它的含义**。表现层用 `MatchTable` 的一张映射表把 `view_kind` 解析为公开快照字段（当前 `recorded_card_names` → 同名公开字段），再据此渲染按钮并决定是否显示只读窗口。因此新增一种“可查看数据”不需要改核心层，也不需要按技能名在 UI 里写分支。带 `view_kind` 的条目**不参与** `character_corner_text` 合成，所以该公开字符串的取值集合与本次改动前逐字节相同，依赖它的 AI 评估与既有断言不会连带回退。

技能侧把“候选是牌名而不是实体牌”也做成了纯呈现开关：`request_control_selection_for_player(..., card_name_view = true)` 在**同一个 control 请求**上追加 `context.card_name_candidates`，而 `control_options` 与 `choice_type="control"` 全部保持不变。面板据此把选项改画成隐藏花色点数的牌面，但提交的仍是一个普通 `control_id`，因此完整复用 `ChoiceRequest` 的 `control_ids` 白名单校验、AI 的 `selected_control_id` 通道与全部事件流程，无需新增响应类型。面板内部为这些牌面分配**负数占位UID**（实体牌UID恒为正），并且只在面板实例内维护占位UID到定义ID的映射；提交瞬间把占位UID换算回定义ID后立即丢弃，因此负数绝不会进入 `PlayerAction`、`ChoiceResponse`、网络消息或规则状态。让伪UID外泄或为新呈现方式新增响应类型都会破坏这条边界，是后续修改该面板时的首要复核点。

虚拟牌的目标重定向由 `CardRuleService._resolve_definition()` 提供：`validate_virtual_use()` 与 `list_legal_virtual_targets()` 读取 `rule_overrides["definition_patch"]` 后按键合并到基础定义上，使“效果取甲牌、目标模式取乙牌”成为通用能力。补丁只做字典键覆写，核心层不维护任何牌名或技能白名单；代价是调用方必须在**目标枚举、提交校验与最终结算三处传入同一份 `rule_overrides`**，否则会出现“能选中但提交被拒”或“提交通过但按原目标模式结算”。不携带 `definition_patch` 时函数行为与改动前完全一致，普通虚拟牌零额外开销。

虚拟牌的自动目标展开由 `CardRuleService.normalize_targets()` 在执行入口 `execute_cardless_virtual_card_use()` 内统一完成，它同样接受 `rule_overrides` 并读取合并后的定义：`all_others` 自动排除使用者，`all_players` 包含全场，`self` 与 `self_wounded` 自动以使用者为唯一目标。因此技能对这四种模式只需传空目标数组，**不要**再自行枚举——否则会出现“群体锦囊打到使用者自己”“只指定部分目标”“自指牌还要求玩家点击自己”三类偏差。其余模式仍需由技能先用 `list_legal_virtual_targets()` 枚举合法目标，再请求玩家选择。

这里有一条容易忽略的一致性约束：**目标展开与目标校验必须读取同一份定义**。首版只让 `validate_virtual_use()` 读取定义补丁，而 `normalize_targets()` 仍读原始定义，于是重定向后的虚拟牌在展开阶段用效果牌的目标模式、在校验阶段用补丁后的目标模式，两者互相否决，表现为“视为使用后无法触发”。修正方式是给 `normalize_targets()` 补上 `rule_overrides` 参数。

失去技能的状态对界面同样公开，但出口是**派生视图**而不是持久名单：`_append_limited_skill_usage_to_snapshot()` 为每名角色快照补上 `installed_skill_ids`（当前实际安装的技能ID，由 `get_installed_skill_ids()` 从技能实例表派生），`MatchTable._get_visible_skill_ids()` 与 `PlayerTargetView._request_character_information()` 据此裁剪技能栏、悬停武将资料与右键武将详情。这样做的直接收益是**收敛方向自动正确**：失去技能会卸载实例，列表随之收缩，该技能立即从三处消失；之后新获得的技能会立刻出现在同一份列表里并正常显示，界面不需要任何“是否发生过失去”的判断。快照缺少该字段时（旧回放文件、手动构造的预览快照）不做裁剪，与改动前的行为逐字节一致；技能声明里缺失定义的条目仍保留占位，以便配置错误被发现。界面**不能**按“是否失去过技能”整体清空技能列表或角标：`character_corner_text_entries` 不携带技能归属，主演、凶星等效果声明的条目与技能无关，整体清空会连它们一起抹掉；技能声明的角标由各技能在 `uninstall()` 内自行移除，技能产生的数据（记录牌名等）由 `remove_all_skills()` 一并清空，因此这条收敛责任落在规则层而不是表现层。过关斩将存档同样记录 `installed_skill_ids`，读档时由 `_install_all_character_skills(saved_installed_skill_ids_by_player)` 只装配记录内的技能，使“失去技能”这一一次性事实不会因为一次存读档而被撤销。

用牌历史采用“事实历史 + 限制豁免子集”模型。牌成功声明后始终增加完整回合与阶段历史；`does_not_count_toward_play_limit()` 为同一条事实增加豁免记录，`CardRuleService.get_grouped_play_count()` 在合法性查询时相减。`ignores_play_count_limit()` 只绕过本次使用前校验，不写豁免。需要“前X张”等真实序号时使用 `get_grouped_actual_play_count()`，不会错误把豁免牌从事实顺序中删除。

特殊武将的隔离位于数据池入口而不是UI：`GameDatabase.characters` 仍是完整静态图鉴，`get_selectable_character_ids()` 才是所有玩法随机池的默认来源。`MatchController` 的开局、AI调整、车轮战校验与过关斩将换将全部消费该过滤结果，因此未来新增 `special=true` 内容不会因遗漏某个模式界面而被普通抽取。

武将换形与区域废除保持两条独立边界：`replace_player_character_card()` 只替换静态武将资料与固有技能，保留稳定玩家ID、身份、牌区、标记和非固有技能来源；`set_player_zones_abolished()` 统一清理废除时的区域牌并更新公开可用性。换形在卸载旧固有技能的同时调用 `ReincarnationSkillService.clear_skill_state()` 清除这些技能的轮回登记，使新形态的轮回技从①与轮回数1开始；否则轮回节会继承只存在于旧技能实例中的运行时字段（例如【弑魂】记录的“上次指定目标”），而该字段已随实例销毁，导致技能停在需要它的分支且永久无法发动。`CardRuleService` 负责用牌目标拒绝，`MatchController` 的装备、延时锦囊、转移与判定传递入口负责最终防线。白厄与卡厄斯兰那只组合这些端口，不让通用层依赖具体武将ID。

## 音频表现层架构

音频层沿用与牌面表现相同的“核心层只发布只读负载、表现层不回读任何状态”边界。`MatchController` 提供单一信号 `voice_presentation_requested(presentation_data)` 与 `request_skill_voice()`、`request_card_voice()`、`request_effect_voice()`、`request_die_voice()` 四个公开端口；负载只包含类别、发动者玩家 ID、技能或卡牌定义 ID、武将 ID、两套牌名、动作模式与表现序号，全部是可序列化公开数据。其中效果音负载只含类别、玩家 ID 与效果标识，不携带任何武将或牌面信息；阵亡语音负载只含类别、玩家 ID 与阵亡武将 ID，二者在死亡结算中都已公开。因此广播任何一类负载都不会泄露隐藏身份与手牌。因此同一个信号既服务本地播放，也直接作为局域网表现事件广播，音频不需要独立的网络协议。

触发点集中在四处核心统一出口：技能实际成立时（`record_skill_activation()`）、卡牌声明使用时、响应牌消耗成功时（含技能转化响应）、死亡事实提交时（`DeathResolutionService._commit()`）。已登记的卡牌与技能因此不需要逐个改造；确需自定义时机时，内容层可显式调用 `SkillDefinition.play_voice()` 或 `CardDefinition.play_voice()`，核心层用3秒抑制窗口避免同一次发动重复发声，并以 `"voice_trigger": "manual"` 元数据支持技能完全接管时机。

全局效果音复用同一条信号与同一条广播链路，触发点是五组规则状态变化：伤害提交时按“护盾实际吸收量 → 伤害属性 → 伤害点数”推导标识、体力实际回复大于0时、失去体力直接扣减体力时、横置与解除连环时、装备牌进入装备区时按槽位取标识。效果音与技能、卡牌语音共用去重表，去重键以当前规则事件 ID 为令牌，因此伤害续接恢复或嵌套结算不会让同一次事件连播两次。终局 `win/lose/tie` 刻意不走这条通道：胜负是每个客户端各自的本地视角，由 `MatchTable` 在结算面板首次显示时直接调用 `AudioService.play_effect()` 播放，避免联机中所有客户端听到同一结果。

`MatchController` 与音频服务之间没有直接依赖：核心层只发信号，`GameAudioBridge` 作为场景级适配节点把信号转发给自动加载节点 `AudioService`。桥接节点挂在主场景根节点下，通过 `@export` 路径取得语音信号来源与主菜单节点，前者转发语音负载，后者以 `MainMenu.visibility_changed` 作为“主菜单 / 对局内”两种 BGM 场景的唯一锚点，因此选将与结算期间主菜单保持隐藏，战斗 BGM 自然延续。桥接节点本身不含播放逻辑，主场景重组时只需调整导出路径。

音频素材的发现不经过 `GameDatabase`：`AudioCatalog` 是纯逻辑组件，按约定命名推导候选路径并用 `ResourceLoader.exists()` 探测，加载成功的音频流进入缓存。它不持有节点、不播放、不读取对局状态，因此可被独立单元测试；测试通过注入内存探测器覆盖全部回退分支，不需要真实素材。`resolve_effect_path()` 只做一次精确文件名探测（`game_data/audio/effect/<效果标识>`），既没有多级回退也没有随机池，因此某个效果音是否存在完全由素材文件名决定——改了名字就等于删掉了这个音效，而运行时不报任何错误，只能靠测试中的实装标识清单兜住。

武将阵亡语音是唯一按**武将身份**（而不是技能或卡牌）解析的语音：`DeathResolutionService` 在死亡事实提交处调用 `MatchController.request_die_voice()`，负载只携带玩家 ID 与阵亡武将 ID，因此与技能语音共用同一条表现信号与联机广播通道，不需要额外的网络字段。素材目录 `game_data/characters/audio/die` 与技能音效目录分离，避免阵亡台词被误当成某个技能的配音；解析只做 `<武将ID>_<序号>` → `<武将ID>` 两级短路，没有跨武将共用的通用兜底层，因此某名武将是否拥有阵亡语音完全由素材文件名决定。

## 用牌禁令与虚拟手牌选择的架构（2026-10-04）

这两条机制是【独弈】【弃和】【自摸】的底座，都遵守“内容层只声明事实、核心层只做聚合与校验、表现层只读公开字段”的既有单向依赖。

**用牌禁令（`validate_card_action_permission`）**走纯查询修正管线，与 `modify_skill_distance_to_target`、`ignores_play_count_limit` 等既有钩子同构：

| 层 | 成员 | 职责 |
|---|---|---|
| 内容层 | `SkillDefinition.validate_card_action_permission(card, definition, card_action)` | 由具体技能（【独弈】）声明“这张**实体牌**在当前区域能不能使用或打出”；返回空字符串即允许 |
| 内容层 | `CardDefinition.CARD_ACTION_USE` / `CARD_ACTION_PLAY` | 动作类别的**唯一字面量来源**；`CardRuleService` 为避免反向依赖核心层，用同名常量镜像这两个值，两处必须同时改动 |
| 服务层 | `CardRuleService.validate_use()` | 使用前校验的第一个咨询点；被否决的牌不会进入任何目标枚举、界面候选或 AI 合法动作 |
| 服务层 | `CardRuleService.list_legal_targets()` | 目标枚举的咨询点；整张牌被否决时**直接返回空数组**，界面因此不会先给出可点击的目标再在提交时才拒绝（“不可使用却仍能指定目标”）。该钩子只拦**手牌路径**，`list_legal_virtual_targets()` 刻意不咨询它——禁令语义是“手牌中的牌不能使用”，虚拟牌是否受限由技能自己的钩子按区域判断，核心层不维护区域白名单 |
| 权威层 | `MatchController._build_response_choice_candidates()` | 打出校验的咨询点；被否决的手牌不会进入任何响应窗口，因此真人界面、AI 响应与联机校验读取同一份候选 |
| 权威层 | `MatchController.validate_skill_card_action_permission()` | 聚合全部已安装技能的返回值，取第一条非空原因；技能提供者缺失（脱离对局的纯规则构造）时视为无禁令 |

关键约束：**钩子是纯查询**（不消费次数、不移牌、不创建选择、不写状态），且**核心层不维护任何牌名或区域白名单**——是否只封锁“手牌中的”牌由内容层自己按 `card.zone` 判断。这样新增同类内容（例如“你不能使用装备牌”）只需写一个新技能文件，核心层与界面层零改动。

**虚拟手牌选择（`request_virtual_hand_card_target_selection`）**解决的是“视为使用一张牌并同时指定目标”这一互动：既要让玩家从一组**并不在手里**的牌里挑一张，又要复用既有的“选牌 + 选目标 + 权威复核”链路。

| 层 | 成员 | 职责 |
|---|---|---|
| 内容层 | `SkillDefinition.request_virtual_hand_card_target_selection(...)` | 把“候选牌名 + 每张牌的合法目标组合”翻译成标准 `choice_type=card_target` 请求；**占位 UID 的生成与回译全部封装在此**（`VIRTUAL_HAND_CANDIDATE_UID_BASE = 1000000000 + 序号`），技能侧不接触 UID 细节 |
| 内容层 | `SkillDefinition.validate_virtual_use()` / `MatchController.card_rules.list_legal_virtual_targets()` | 候选过滤与提交后复核读的是同一份规则查询，因此“界面里能选”与“核心层认可”同源 |
| 权威层 | `MatchController._submit_card_choice()` | 仍按“提交集合 ⊆ 候选集合 + 目标组合映射”做统一复核，**不需要为虚拟手牌新增协议分支** |
| 表现层 | `MatchTable` 的虚拟手牌模式 | 识别 `virtual_hand` 请求后把真实手牌动画移出、以摸牌动画渲染虚拟候选，请求结束后还原；**只读请求负载，不读技能实例、不写任何规则状态** |

- 占位 UID 之所以能直接复用既有协议：请求的合法性判据是**集合包含关系**而不是“UID 必须存在于手牌”，而基数 `1000000000` 远大于真实牌 UID 的取值范围，因此占位值不可能与真实牌冲突，也不会污染任何实体牌查询。
- 表现层与规则层的数据交换只有请求负载与 `ChoiceResponse`：虚拟候选的“无花色、无点数”（`suit = "none"`、`rank = 0`）是**请求负载里的事实**，不是界面自己推出来的，因此联机客户端与 AI 看到的也是同一份事实。
- 关闭/退出该模式时表现层必须清理全部虚拟视图与补间，并按真实手牌 UID 重放摸牌动画；规则层对此完全无感（它只看提交结果）。
- **候选组合的枚举责任在内容层**：协议只搬运“哪张牌名对应哪组有序目标”，因此目标上限 ≥ 2 的牌必须由技能自己给出完整候选池（当前实现用全体在场角色的行动顺序），再逐组交 `validate_virtual_use()` 权威筛选。核心层提供的 `list_legal_virtual_targets()` 是**单元素试算**的结果，只适用于“单目标牌有哪些目标”，把它当成多目标牌每一个位置的候选池会漏掉合法组合（【借刀杀人】在只有一名持武器角色时会退化为没有任何组合）。
- **取消按钮的“能不能点”与“给不给看”分成两个声明**：规则侧的 `allow_cancel` 决定请求是否接受空响应（`false` 时界面保持“可见但禁用”的既有灰显契约），表现侧的 `context.hide_cancel_button` 决定界面是否直接暗置按钮。表现层默认不改任何规则语义，只读该上下文键决定可见性。
