# 数据扩展指南

## 目录约定

- 卡牌源码：`game_data/cards`。
- 武将源码：`game_data/characters`。
- 技能源码：`game_data/skills`。
- 势力展示数据：`game_data/factions.json`。
- 实体牌堆数据：`data/decks.json`。
- 所有卡牌、武将和技能文件使用中文名称的连续小写拼音命名，不使用空格、横线或中文文件名。例如【顺手牵羊】使用 `shunshouqianyang.gd`。
- `GameDatabase` 会按文件名稳定排序扫描三个源码目录。新增文件不需要修改数据库、数组、枚举或注册表；ID 重复、空 ID、继承类型错误和引用缺失会写入 `GameDatabase.validation_errors` 并阻止开局。

## 新增卡牌

1. 在 `game_data/cards` 创建一个拼音命名的 `.gd` 文件，并继承 `CardDefinition`。
2. 在 `_init()` 中调用 `super({...})`，完整填写 `id`、`original_name`、`custom_name`、`type`、`subtype`、`effect_id`、`target_mode`、`min_targets`、`max_targets`、`distance_limit`、`play_limit`、`response_pattern`、`recast`、`delayed`、`description`、`resolution_mode`、`final_zone` 和 `provided_response_pattern`。
3. 在同一个文件覆盖 `resolve(resolver, card, actor_id, target_ids)`。可复用 `CardEffectResolver` 已公开的通用规则函数，也可在该函数中通过 `resolver.host` 的公开规则端口组合新效果；禁止直接修改 UI 节点。
4. 若卡牌需要保存整张牌共享状态或特殊逐目标语义，可覆盖 `resolve_target(...)` 并读取 `resolution_context`。普通逐目标牌无需覆盖，基类会自动调用 `resolve()`。
5. 延时锦囊覆盖 `resolve_delayed_judgment(match_host, player_id, card, negated)`，在自身文件维护判定条件、阶段跳过、伤害、传递和离区规则。可调用 `perform_judgment()`、`mark_player_phase_skipped()`、`discard_delayed_card()` 等公开规则端口。
6. 装备或其他进入区域后持续生效的卡牌可覆盖 `install_runtime()`；系统会按实体牌 UID 创建独立实例，并在换装、转移、弃置、死亡清区或重新开局时调用 `uninstall_runtime()`。持续实例不得把状态写入数据库静态定义对象。
7. `resolution_mode` 使用 `per_target` 时，每个有效目标分别创建一次内容结算；使用 `whole` 时，卡牌一次取得完整目标数组。装备、延时锦囊和需要共享公共牌池的效果通常使用 `whole`。
8. `final_zone` 使用 `discard`、`equipment` 或 `judgment`，决定卡牌展示层是否接管后续弃牌移动；最终权威区域仍以 `resolve()` 返回值为准。
9. `response_pattern` 表示该牌效可被何种响应处理；`provided_response_pattern` 表示该实体自身能提供的响应。普通锦囊可以填写 `response_pattern: "wuxie"`，但只有实际无懈牌才填写 `provided_response_pattern: "wuxie"`。
10. 可选填写 `art_path`，推荐使用 `res://assets/art/cards/<卡牌ID>.webp`；未填写或路径无效时自动显示占位图。
11. 若该定义需要生成实体牌，在 `data/decks.json` 的目标牌堆加入 `[花色, 点数, 卡牌ID]`。只新增不进入牌堆的规则入口时无需修改牌堆。
12. 运行烟雾测试，并同步更新《卡牌系统》和《游戏机制与玩法内容》中的规则、目标、伤害、回复、摸牌、次数、距离、概率、资源消耗和持续时间数值。

最小结构如下：

```gdscript
extends CardDefinition

## 【示例牌】卡牌源码。静态信息与效果入口均在本文件维护。


## 写入卡牌完整静态信息。
func _init() -> void:
	super({
		"id": "shilipa",
		"original_name": "示例牌",
		"custom_name": "示例牌",
		"type": "trick",
		"subtype": "normal",
		"effect_id": "example_draw",
		"nature": "normal",
		"target_mode": "self",
		"min_targets": 1,
		"max_targets": 1,
		"distance_limit": "none",
		"play_limit": 0,
		"response_pattern": "wuxie",
		"recast": false,
		"delayed": false,
		"description": "对自己使用，摸一张牌。",
		"resolution_mode": "per_target",
		"final_zone": "discard",
		"provided_response_pattern": "",
	})


## 目标未被无懈抵消时摸1张牌。
func resolve(resolver: Object, card: CardInstance, actor_id: int, target_ids: Array[int]) -> String:
	for target_id: int in target_ids:
		if resolver.host.resolve_trick_negation(actor_id, target_id, card.definition_id):
			continue
		resolver.host.draw_cards(target_id, 1)
	return "pending" if resolver.host.has_pending_card_choice() else "discard"
```

牌堆可以新增任意 ID，不需要修改 `GameState` 或 `MatchController`。启动前把 `MatchController.default_deck_id` 指向新牌堆即可。

## 新增技能

1. 在 `game_data/skills` 创建拼音命名的 `.gd` 文件，并继承 `SkillDefinition`。
2. 在 `_init()` 中填写唯一 `id`、玩家可见 `name`、稳定 `trigger`、`ui_enabled` 和完整 `description`。
3. 被动或触发技能覆盖 `install()`，通过 `host.event_bus.subscribe(...)` 或 `host.trigger_manager.subscribe(...)` 注册规则时机。技能失去或重新开局时基类 `uninstall()` 会按技能实例批量解除订阅。
4. 主动技能设置 `ui_enabled: true`，覆盖 `can_activate(context)` 与 `activate(context)`。技能按钮只提交 `use_skill` 标准动作，阶段、次数、目标、费用和效果仍由技能文件校验与执行。
5. 技能需要选牌、选目标或响应时，调用控制器公开的统一选择请求，不保存 UI 节点，不直接修改 `GameState` 数组。
6. 同一技能被多名玩家持有时，系统为每名玩家创建独立实例；运行时标记、次数和临时状态应保存在实例成员中，并为每个变量编写独占注释。
7. 新建技能文件会自动进入技能索引；要让某名武将持有该技能，在对应武将文件中直接 `preload` 该技能脚本。

## 新增武将

1. 先创建武将需要的技能文件；无技能武将可以传入空技能数组。
2. 在 `game_data/characters` 创建拼音命名的 `.gd` 文件，并继承 `CharacterDefinition`。
3. 对每个技能声明带独占注释的 `const ...: Script = preload("res://game_data/skills/<技能拼音>.gd")`。武将直接引用技能代码，不重复填写技能 ID 字符串。
4. 在 `_init()` 中填写 `id`、`display_name`、`gender`、`faction`、`max_hp`、`description`，并把技能脚本数组作为 `super(metadata, skill_scripts)` 的第二个参数。
5. `display_name` 必须填写玩家可见中文名，UI 统一通过 `GameDatabase.resolve_character_name()` 读取；`faction` 必须引用 `game_data/factions.json` 中已登记的势力 ID。
6. 可选填写 `art_path`，推荐使用 `res://assets/art/characters/<武将ID>.webp`；未填写或路径无效时自动显示占位图。
7. 不在 `MatchController`、选将界面或 AI 中编写 `if character_id == ...` 分支。所有登记武将会自动进入 `CharacterSelectionService` 候选池。

样例武将目前为开拓者、三月七、丹恒、姬子、瓦尔特、布洛妮娅、景元和卡芙卡，共8名；每名玩家默认候选5张，由 `MatchController.character_candidate_count` 调整。武将库少于配置值时实际候选数量自动缩减，单名玩家列表内不重复。

## 新增势力

1. 在 `game_data/factions.json` 的 `factions` 数组新增唯一 `id`。
2. `display_name` 填写完整势力名，用于武将牌悬停说明。
3. `short_name` 推荐使用1个中文字，用于武将牌左上圆形势力徽记。
4. `color` 使用不带 `#` 的六位十六进制 RGB 字符串，例如 `3f78a8`；修改后会同时影响势力圆徽和武将名竖条。
5. 势力元数据只负责界面展示，不替代主公、忠臣、反贼、内奸身份，也不参与距离、伤害或胜负判定。

## 新增 AI

实现 `choose_action(snapshot, legal_actions)` 并在 `AICoordinator` 中登记。AI 可以读取权威快照，但只能返回 `PlayerAction` 字典。不要让策略引用 UI 节点、网络连接或直接调用核心结算函数。

## 新增传输适配器

监听 `packet_ready_for_transport`，把字典编码后发送；收到数据后调用 `receive_transport_packet(packet)`。传输适配器负责连接、重试、加密和可靠性，`NetworkGateway` 负责协议与游戏消息分流。

## 注释与文档要求

所有新增变量必须有独占注释，说明用途、数据含义、范围、默认值原因和修改影响。新增或调整机制必须同步模块文档与《游戏机制与玩法内容》，记录所有具体数值。已有变量名和注释不得擅自删除或改写。
