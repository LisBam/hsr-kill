# 网络通信

## 终局统计快照字段

- 每名 `PlayerState` 的普通观察者快照新增公开累计字段：`total_damage_dealt`、`total_damage_received`、`total_healing_done`、`total_cards_drawn` 与 `total_kill_count`。这些字段不包含手牌、候选或随机信息，LAN 房主可随普通状态快照直接发送给所有观察者。
- 终局结算面板只消费上述字段和已经公开的角色资料；客户端不得从本地日志、动画或体力变化自行补算统计，也不得回传任何结算修改命令。

## 当前范围

项目已实现可直接游玩的局域网直连：一名玩家创建可选密码的 ENet 房间，其他玩家输入房主的局域网 IPv4 地址、端口与密码加入；成功登记后进入带玩家形象、座位、聊天和房间设置的联机大厅，由房主创建标准身份局、斗地主局、2v2局、1v1车轮战、机缘大乱斗或2至4名玩家协作的过关斩将。客户端在对局中意外掉线后支持携会话令牌自动重连并恢复原座位（见“掉线与会话结束”）。当前不实现公网房间发现、账号、匹配、NAT 穿透、主机迁移、旁观、回放下载或反作弊服务端。对局回放为纯本机功能：离线玩家、房主与客户端各自录制本机视角快照流并保存为本地 `.lisbam_replay` 文件，回放数据不经网络传输。对局中另提供“聊天”窗口与头顶聊天气泡（见“封包结构”的 `match_chat`）。

局域网使用 Godot `ENetMultiplayerPeer` 的可靠 RPC 通道。ENet 基于 UDP，系统防火墙必须允许游戏程序使用所选端口；默认端口为 `7000`，界面允许输入 `1024` 至 `65535`。房主最多接受 `9` 名远端客户端，加上房主最多 `10` 名真人。

## 玩家流程与人数规则

1. 主菜单顶部点击“联机设置”，切换到与“模式选择”对等的资料内容页，设置玩家名称并从当前 `GameDatabase.characters` 的全部现有武将牌中选择联机形象。形象列表与“所有武将牌”图鉴共用势力顺序：星穹列车、银河学者、贝洛伯格、仙舟联盟、匹诺康尼优先，其他扩展势力随后稳定排列；该顺序只影响本地浏览，不写入网络协议。
2. 返回主菜单后点击“局域网联机”；连接入口只读显示已保存的玩家名称，不能在该界面修改。
3. 房主填写端口与可选房间密码后点击“创建房间”；密码最长 `32` 个 Unicode 字符，首尾空白会移除，空值表示无密码房间。
4. 客户端填写房主 IPv4、相同端口与密码后点击“加入房间”。同机双实例测试可使用 `127.0.0.1`；密码错误时房主定向返回原因后断开该连接。
5. 成功登记后进入联机大厅。大厅同步玩家名称、稳定武将形象 ID、房主标记与0起始位置索引；名称和形象在已连接大厅中不能编辑。
6. 玩家点击空位置可请求换位。房主权威复核目标位置仍为空后广播完整大厅快照；位置只确定真人进入正式对局前的稳定玩家 ID 顺序，身份与最终领袖座次仍由规则独立处理。
7. 大厅至少登记 `2` 名真人后，房主才可开始对局。游戏总人数范围为 `2` 至 `10`，不得少于当前真人数；真人未占用的规则座位由内置 AI 补齐。过关斩将的大厅“人数”表示玩家数（`2` 至 `4`，不含敌方AI），真人数量不得超过该玩家数。
8. 房主可在大厅修改模式、总人数、密码与“自选身份”开关。当前 `identity` /“身份模式”、`doudizhu` /“斗地主”、`team2v2` /“2v2”、`wheel_duel` /“1v1车轮战”、`opportunity_brawl` /“机缘大乱斗”与 `conquest` /“过关斩将”均可实际开局；身份模式与机缘大乱斗支持2至10人，斗地主人数仅允许3或5，2v2固定4，1v1车轮战固定2，过关斩将为2至4名玩家（规则角色总数为玩家数两倍）。修改密码只影响之后加入的玩家，不会踢出已登记成员。
8.1. “自选身份”是房间级设置：创建房间表单与大厅“对局设置”弹窗各提供一个开关，默认关闭且不写入 `game_settings.cfg`。开启后每个大厅位置绑定固定身份，空位与玩家形象右上角显示身份徽记，玩家通过点击空位换位来自选身份。位置身份表：身份模式/机缘大乱斗按 `IdentityRules.IDENTITY_DISTRIBUTIONS` 固定顺序（如八人局一号位“领袖”、二三号位“忠臣”、四号位“内奸”、下排四位“反贼”）；斗地主按固定身份表（三人一号位地主，五人一号与三号位地主）；2v2 使用大厅专属“上排两蓝、下排两红”布局；1v1车轮战一号位红方先手、二号位蓝方后手。过关斩将真人固定红方、无位置身份，该模式下开关禁用并强制关闭。
8.2. 大厅视觉位置数由 `NetworkGateway.get_lobby_display_slot_count_for()` 统一计算：1v1车轮战固定2个位置（两名真人1v1、各自选将，不再绘制第三个空位）；自选身份开启时位置数等于规则人数（位置与身份一一绑定）；其余情况保持2至3人绘制3个居中位置的既有设计。房主换位校验与界面绘制共用该唯一规则，越界位置的换位请求会被拒绝。
9. 房主悬停远端玩家形象可发出踢出请求；房主本人、未知成员和已开始对局中的成员不能通过该入口移除。被踢成员按其远端网络地址进入 `5000` 毫秒（5秒）冷却；同一地址在冷却内重新登记会收到剩余秒数提示，冷却到期后可再次加入。密码错误、满员等普通拒绝不创建该冷却。
10. 大厅聊天单条最长 `200` 个 Unicode 字符，换行会替换为空格；房主最多保留并同步最近 `100` 条。聊天署名从房主成员表解析，客户端不能伪造显示名。桌面端通过发送按钮或回车提交后会在按钮焦点结算完成的下一帧恢复聊天输入框焦点，可直接继续输入；大厅关闭或房主设置模态打开时不会抢占焦点。
11. 玩家显示名最长 `20` 个 Unicode 字符，空名称回退为“玩家”。名称由 `GameSettings.online_player_name` 统一保存并用于当前大厅、玩家牌面与对局日志，不建立账号。
12. 联机形象保存并同步稳定武将 ID `GameSettings.online_avatar_character_id`；大厅客户端通过本地 `GameDatabase.get_character()` 解析插画，不在封包中传输纹理或节点。联机形象不参与对局规则。
13. `GameSettings` 使用本地 `user://game_settings.cfg`（格式版本1）保存联机名称、形象、游戏显示/节奏/下一局人数及六项房主开局配置；房主地址、端口、密码、聊天、成员表、连接 peer 和对局状态均不写入该文件。
14. 房主创建新局时会锁定“自选全武将、座次与身份”“自选所有AI的武将”“手气卡数量”“AI使用手气卡”“换将卡数量”“随机选将牌数”六项权威设置。手气卡内部值为 `0、1、2、3、4、5、10、-1`，其中`-1`为无限张；换将卡内部值为 `0、3、5、8、10、20`，随机选将牌数为1至20；客户端本地同名设置不能修改当前房间对局，局内菜单不显示这些控件。

房主明文密码只存在房主本机内存与显式请求的私有大厅快照中。广播给客户端的公共快照仅包含 `has_password` 布尔值，不包含 `room_password`。

当前没有自动房间发现。不同设备必须处于可互访的局域网，客户端需手工输入房主地址；访客 Wi-Fi 隔离、不同 VLAN 或防火墙阻断 UDP 时无法直连。

## 权威同步模型

局域网采用权威房主模式：

- 房主独占 `GameState`、牌堆顺序、身份、随机种子、事件运行时、技能实例和胜负结算。
- 客户端的 `MatchController.state` 始终为空，只保存最近一份观察者裁剪快照，不在本地运行第二套规则或随机数。
- 客户端只上传 `PlayerAction`；房主按阶段、玩家、实体 UID、目标、次数、距离、请求 ID 和候选集合再次校验。
- 房主为每名远端玩家分别调用 `GameState.to_dict(viewer_id, false)`，禁止把同一私有快照广播给全部客户端。
- 联网快照不发送 `random_seed`。客户端只能看到自己的身份、手牌、“粮”和私有选择候选；他人的隐藏身份与手牌牌面保持裁剪。
- 房主额外向当前行动玩家发送 `local_legal_actions`，客户端据此完成卡牌、目标与装备的无状态预览；该列表只控制界面，不能替代房主最终校验。
- 选将期间，快照额外携带仅属于观察者的 `character_selection`：首次分配身份只通过 `local_identity` 发给本人；首任领袖武将立即公开；本人候选、`locked_candidate_ids`、`replaceable_candidate_ids` 与 `replacement_cards_remaining` 只进入该观察者快照。换将使用 `replace_character_candidate` 标准动作，房主重新校验 actor、阶段、候选归属、当前领袖身份的领袖技锁定、剩余张数和随机池后才广播新私有候选；非领袖身份的领袖技武将不应被客户端或房主额外拒绝。
- 1v1车轮战同样复用定向 `character_selection`，但 `selection_kind="wheel_duel"`。公共 `pool_slots` 对明置槽发送 `character_id`，对暗置槽只发送 `slot_id/face_up=false`；抓取动作 `wheel_duel_pick` 只上传稳定槽ID。本人取得的5名武将与最终3名阵容只进入本人的定向快照；对手只收到取得数量和是否已确认阵容。阵容动作 `wheel_duel_submit_lineup` 上传按出场顺序排列的3个稳定武将ID，房主复核其属于本人五将且互不重复。
- 机缘选择使用 `GameState.opportunity_state` 的观察者裁剪快照。全体参与者、当前选择者、已完成选择者和流程阶段属于公共信息；序列化时先跳过全体 `options_by_player`，再只复制当前观察者自己的三张候选，已选完整定义只保存在房主组件私有结算映射且不写入普通客户端快照。客户端只上行 `choose_opportunity` 与稳定 `card_id`，房主再复核当前选择者、候选归属与流程阶段。
- 对战阶段 `PlayerState` 的 `wheel_duel_lineup` 与 `wheel_duel_lineup_index` 仅对本人或权威调试快照公开；`wheel_duel_defeated_count` 与当前已经亮出的 `character_id` 属于公共规则事实。换将、补满体力、摸4张和当前回合中断均由房主权威执行后广播普通状态快照，客户端不自行推演下一名武将。
- 自选模式仍先处理首任领袖公开选将。若首任领袖是真人，其第一份定向 `character_selection` 就同时携带当前可用座次、仍有名额的身份，以及供初始高亮与回包纠正的 `initial_seat_number`、`initial_identity`、`preview_seat_number`、`preview_identity`；客户端在同一个 `select_character` 动作中上传武将ID、座次号和身份ID，房主确认后立即令该玩家 `can_select=false`，后续 `PHASE_CUSTOM` 不再把此玩家列入待选集合。其余观察者进入最终自选后取得严格等于设置张数的本人随机候选和全部武将入口。有效组合使用 `preview_custom_assignment` 标准动作；房主校验后立即更新公开座次顺序、清空未确认AI的背景亮将，首任领袖仍为当前领袖时保持其已公开武将，只有AI成为新预览领袖时公开其新武将，而未确认真人成为新预览领袖时定向快照把 `leader_character_id` 置空，仍不发送其他真人的隐藏身份、候选、换将张数或具体选择。真人每次确认时立即写入该玩家的最终座次、身份与武将；真人全部确认后，房主才驱动AI占用剩余名额，完成时不再覆盖性重置已经投射的领袖、武将、座次或身份。
- 首任领袖为AI时，首次动作只公开其最终武将而不占用座次身份名额；进入最终自选后的内部快照可用 `retains_selected_character=true` 和 `local_selected_character_id` 返回该武将，并发送空候选。该字段只供房主AI在真人完成后复用相同ID补选剩余座次身份，不定向给已确认真人，也不会创建第二个玩家选将框。房主在AI补选分支只按最终身份刷新基础体力，不随机或改写武将 ID。
- 全部真人确认后，房主先处理带有首任领袖保留状态的AI；一号位与领袖名额仍空缺时，该AI使用首次公开的同一武将ID确认二者，再处理其他AI。该调度顺序只发生在房主权威端，客户端继续只接收自己的裁剪快照。
- AI武将调整阶段的公共 `pre_game_setup` 只包含房主稳定玩家ID和可点击AI玩家ID；随机候选与当前AI目标只定向进入房主的 `character_selection`。其他玩家只根据公共阶段显示等待文案。
- 手气卡阶段每名观察者只收到自己的 `starting_hand_mulligan`：是否仍需操作、是否可刷新、本人剩余手气卡张数和公共完成计数。其他玩家的剩余张数与牌面不进入快照；旧手牌洗回和新手牌重发继续按普通私有手牌移牌规则裁剪表现。最后一名玩家确认后，房主先将权威阶段切换为 `round_start`，随后才派发首轮 `roundStart`；之后的快照不再携带 `starting_hand_mulligan`，首轮技能选择按普通定向 `choice_request` 发送，不能遗留“等待其他玩家确认手气卡”的界面状态。
- `PlayerState` 额外同步 `auto_managed`、`auto_managed_offline`、`wine_used` 与 `wine_bonus`。酒状态是场上公开规则事实，所有观察者都可用它渲染下一张【杀】的伤害威胁，且不暴露任何手牌牌面。真人可只为自己的稳定玩家 ID 提交 `set_auto_managed` 开启或取消手动托管；房主注册或注销同一 `BasicAIPolicy`，并在选将、普通选择、同时无懈和出牌阶段从既有 AI 调度继续。已掉线时房主强制写入离线托管，玩家不能取消。
- 轮回技状态通过每名 `PlayerState.reincarnation_skills` 作为公共规则事实同步，内容只包含技能ID、轮回数、轮回节、永劫与通用限次，不包含手牌、随机源或技能运行时对象。客户端据此切换局内技能说明高亮，不自行推进轮回。两类用牌次数语义仍保留完整 `card_use_history/play_phase_card_use_history`，并以对应 `*_limit_exempt_history` 表示不计入上限的公开子集；房主是唯一写入方。
- 正式对局中的AI响应速度、游戏速度、下一局人数、按设置重新开局、全武将座次身份自选、AI武将调整、手气卡数量、AI手气卡、换将卡数量和随机选将牌数属于权威房主功能；局域网客户端的局内菜单不创建可见操作入口。卡牌名称、UI风格和自动身份标记等纯本地显示设置仍由每名玩家独立使用。后续新增以房主状态为准的局内功能也必须归入同一权威控件组。

真人成员在开局前按大厅 `seat_index` 从小到大绑定到不重复的稳定玩家 ID，空余玩家 ID 注册基础 AI。普通模式的2人房虽然显示3个视觉位置，真人仍只映射到规则允许的 `0..1`；1v1车轮战大厅只显示2个位置。物理座次在身份确定后继续以领袖为一号位旋转，稳定玩家 ID 不随座次变化。

自选身份开启时的映射例外：真人不再按先后顺序压缩，而是由 `IdentityRules.get_lobby_slot_match_seats()` 把大厅位置直接绑定到规则座次（身份模式、斗地主、机缘大乱斗与车轮战为一一对应；2v2 把“上蓝下红”的大厅布局换算回“一/四同队、二/三同队”的规则座次，即大厅位置 `0/1/2/3` 分别绑定规则座次 `0/3/1/2`）。空位对应的规则座次由 AI 补齐并使用该位置的固定身份。开局时房主把 `lan_custom_identity_enabled` 锁入 `match_options`，`_create_players` 按 `IdentityRules.get_distribution()` 固定顺序赋身份，不再洗牌、不做2v2的50%蓝红互换；身份开局公开性仍遵循各模式既有规则（身份局仅领袖明置）。

过关斩将例外：座次固定按“玩家1、敌人1、玩家2、敌人2……”交替排列，真人成员按大厅位置从前到后映射到偶数玩家座位（稳定 ID `0、2、4、6`），奇数敌方座位与未被真人占用的玩家座位均注册基础 AI；`match_start` 与权威控制器使用规则角色总数（玩家数×2），身份表按偶红奇蓝交替且不发生领袖旋转。房主的难度与“机缘选择”（投票选择/各自选择）设置在开局时锁入 `match_options`，机缘投票的共享候选与逐人提交完全复用既有 `opportunity_state` 观察者裁剪协议，每票在结果公布前不进入其他观察者快照；阵亡玩家在关卡提升进入下一关时由房主权威复活并回到游戏初始状态，复活结果随普通状态快照广播，客户端不自行推演。对局中的断线托管、令牌重连与重开人数锁定沿用通用规则，联机过关斩将不提供临时退出存档。

## 通信模式

- 自选确认补充：房主接受真人首任领袖或后续玩家的完整 `select_character` 提交后，立即按已确认与预览结果重排公开座次身份，并只应用该提交者的武将一次；真人首任领袖的随机历史只能出现1条选将记录，后续全部完成不再向客户端广播一次覆盖性的座次或武将重置。当前一号位领袖已确认武将时，定向 `character_selection.leader_character_id` 返回该实际武将而不是首任旧武将；当前一号位是尚未确认真人时返回空字符串，不得继续展示旧领袖牌。客户端仍只接收自己的候选、身份和换将张数。
`NetworkGateway.Mode` 包含：

- `OFFLINE`：本地回环，发送动作后立即触发接收信号。
- `LAN`：内置 ENet 局域网会话，支持建房、加入、大厅、定向快照和表现事件。
- `REMOTE`：保留给未来公网传输适配器，继续通过 `packet_ready_for_transport` 交付封包，不自动连接服务器。

`NetworkGateway.LanRole` 包含 `NONE`、`HOST` 和 `CLIENT`。房主固定使用 ENet peer ID `1`；客户端无权发送快照、开局通知或权威表现事件。

局内日志展开和武将详情打开的暂停只适用于 `OFFLINE`。LAN 与 REMOTE 打开日志或详情时继续运行，客户端不得通过本地界面暂停权威对局。

## 封包结构

```json
{
  "protocol_version": 8,
  "message_type": "command | snapshot | choice_request | choice_response | game_event | lobby_join | lobby_state | lobby_seat | lobby_chat | lobby_rejected | match_start | match_chat",
  "transport_mode": "offline | lan | remote",
  "sequence": 1,
  "payload": {}
}
```

- `protocol_version` 当前固定为 `9`。版本6保留版本5的机缘大乱斗与既有大厅协议，并新增断线重连握手：`match_start` 携带会话令牌，对局中的 `lobby_join` 可携带重连令牌；版本7在版本6基础上向 `lobby_state` 公共快照新增 `custom_identity_enabled` 自选身份开关字段；版本8在版本7基础上新增对局内聊天 `match_chat` 消息类型（客户端上行与房主中继下行共用同一类型）；版本9在版本8基础上移除大厅聊天与对局聊天条目的 `time_text` 字段（聊天界面统一不显示时间）；旧协议封包不接受。
- `sequence` 由每个发送端单调递增。接收端按真实 peer ID 记录最近序号，小于或等于已接收值的重复包直接丢弃。
- `command` 负载为 `PlayerAction.to_dict()`。房主先验证封包真实发送 peer 绑定的玩家 ID 与 `payload.actor_id` 完全一致，再交给规则控制器；`choose_opportunity` 只允许绑定玩家为自己提交当前候选的稳定 ID；`set_auto_managed` 还会确认操作人就是该真人角色，托管中的真人常规动作会被拒绝，控制器内部 AI 动作不写入网络 payload。
- `snapshot` 负载为面向单一观察者裁剪的 `GameState` 字典，并可附加 `local_legal_actions`、私有 `character_selection`、私有 `starting_hand_mulligan` 与观察者本人的机缘候选。
- `choice_request` 在 LAN 中使用现有 UI 兼容选择字典，并只定向发送给实际选择者；`choice_response` 保留通用 `ChoiceResponse` 协议，当前桌面也可通过 `command/choose_cards` 上行相同结果。
- `game_event` 只承载日志、公开牌面表现、按观察者裁剪的移牌动画、摸牌批次、技能/装备提示、公共选牌展示、动作拒绝与终局提示，不修改客户端规则状态。
- `match_chat` 是对局内聊天专用消息：客户端上行 payload 只含 `message` 正文；房主校验发送者属于当前对局玩家后，以连接绑定的稳定玩家 ID 反查署名（不采信 payload 自报身份），构建含 `sequence`、`sender_player_id`、`display_name`、`message` 的条目逐客户端中继并本地登记（条目不携带时间字段，聊天界面不显示时间）。正文最长 `200` 个 Unicode 字符、换行替换为空格；历史最多保留 `100` 条。历史在大厅“开始游戏”创建新局与会话结束时清空，断线重连与同房间局内重开保留；聊天不进入 `MatchController` 规则协议，也不修改任何规则状态。离线模式由网关本地回环同构条目，无网络封包。
- `lobby_join` 提交显示名、形象 ID 与加入密码；对局中的 `lobby_join` 改为携带 `rejoin_token` 承担断线重连语义，不再接受普通加入。`lobby_state` 广播公共成员、位置、模式、人数、自选身份开关、密码状态和聊天历史；`lobby_seat` 与 `lobby_chat` 是客户端大厅上行；`lobby_rejected` 定向返回密码错误、踢出原因、踢出后的冷却剩余秒数或重连凭证失效原因；`match_start` 只发送接收者自己的稳定玩家 ID，并附带房主签发的32字符十六进制 `session_token`，重连成功的回发包额外携带 `rejoined=true`。这些消息不进入 `MatchController` 规则协议。

所有 payload 只允许字符串、数字、布尔、数组和字典，禁止节点引用、资源运行时实例与 `Callable`。

## 选择请求与公共展示

响应、弃牌、区域选牌、技能选目标和文字选项继续使用 `ChoiceRequest/ChoiceResponse` 的稳定 ID、事件 ID、玩家 ID、数量范围与候选校验。LAN 房主在界面请求真正发布时才把完整候选定向发送给对应远端玩家；响应提示延迟仍遵循游戏速度设置。

非响应者的 `GameState.to_dict()` 会清空卡牌、目标、按钮、控制项、已选结果和活动上下文。五谷丰登的 `public_card_choice_display` 与无懈可击的 `simultaneous_response_display` 仍属于全体观察者可见公共快照，但不包含其他玩家私有候选、是否持有响应牌或候选数量。

机缘选择会暂停权威玩法树，但不会暂停通信。`NetworkGateway` 与机缘选择弹窗均使用 `PROCESS_MODE_ALWAYS`，因此 LAN 客户端仍能接收私有候选、提交 `choose_opportunity` 并接收下一名选择者的快照；暂停只阻止普通规则、AI与牌桌操作继续推进。房主可在连续AI选择之间不发送中间快照，只在下一名需要真人/远端输入或全体选择完成时广播公共进度；真人提交与跨客户端轮转仍逐次发送，不能以批处理为由延迟真实玩家候选。

卡牌移牌表现按观察者裁剪：摸牌和无关玩家之间的私有手牌转移只发送实体 UID 与牌背语义；牌进入弃牌堆、来自公共区域，或观察者是转移当事人时才发送完整牌面。使用、展示和判定牌属于公开表现，但发送前移除 `known_to` 与 `private_owner_id` 等内部知识元数据。

## 掉线与会话结束

- 真人可在局内自行开启托管：房主保留原玩家状态、写入 `auto_managed=true` 并注册基础 AI；其手牌、目标、技能、响应和结束阶段等真人输入均被拒绝，直到本人提交取消托管。该规则不改变体力、手牌、次数、概率或 AI 策略数值。
- “控制所有角色”是纯离线开局选项，不进入大厅设置、网络动作或远端快照。创建或加入LAN会隐藏该项；即使本地配置保存为开启，房主创建LAN对局时也把 `match_options.control_all_characters_enabled` 强制锁定为 `false`，客户端仍只能提交其连接绑定玩家的动作。
- 客户端在对局中掉线：房主保留该稳定玩家状态，立即注册基础 AI 托管并写入 `auto_managed_offline=true`，从当前选将、普通选择、同时无懈或出牌阶段继续流程，同时按该玩家的会话令牌登记断线座位预约。离线托管不能由客户端取消，只能通过携令牌重连恢复。
- 断线重连：房主正式开局时为每名远端真人随同 `match_start` 签发由16随机字节编码的32字符十六进制会话令牌；令牌只保存在双方内存，同一房间存续期间稳定不变，重开对局复用同一令牌。客户端在对局中收到 `server_disconnected` 后不清理对局绑定，而是每 `2` 秒自动重拨原地址端口，最多尝试 `15` 次；连上后以携 `rejoin_token` 的 `lobby_join` 完成握手。房主命中预约后恢复原稳定玩家 ID、显示名与座位，回发带 `rejoined=true` 的 `match_start`，随后解除该玩家离线托管、注销基础 AI，并重发裁剪快照与仍在等待的选择请求；对局日志记录重连恢复。重连期间客户端保留对局界面并常显顶部横幅，重试用尽或凭证被明确拒绝时按普通会话关闭返回主菜单。
- 双端断线感知存在时差：若客户端先于房主发现连接失效并重连，其令牌仍绑定旧连接，房主直接用新连接接管并断开旧 peer，不触发中间的托管接管。
- 对局中的新连接只承担重连语义：存在已签发会话令牌时，新连接获得 `5` 秒登记宽限，必须在宽限内提交携有效令牌的 `lobby_join`；令牌缺失、错误或未命中时定向拒绝，宽限到期未登记则直接断开。房间内不存在任何可重连身份时保持既有的立即断开。没有中途加入。
- 预约的失效边界：对局结束（胜负或平局）与房主重开新局时清空全部断线座位预约，旧对局的令牌不再能恢复座位；重开时掉线玩家已被移出真人映射，其座位由 AI 正常补位。
- 客户端在大厅离开：房主移除成员并广播最新成员表。大厅阶段掉线没有重连，按普通离开处理。
- 房主断开或关闭房间：客户端自动重连会因目标不可达而重试直至用尽，然后返回主菜单；当前版本不进行主机迁移。
- 同一局域网房间内重新开始时保持真人玩家映射和游戏总人数，不允许在重开时改变总人数。

## 组件边界

- `NetworkGateway`：ENet 生命周期、密码校验、公共大厅、座位与聊天权威状态、踢出、按远端地址记录的5秒重新加入冷却、peer 与玩家映射、序号去重、actor 防伪和定向传输；另负责会话令牌签发、断线座位预约、重连握手校验与客户端自动重连循环，重连成功与状态变化通过 `lan_match_peer_reconnected`、`lan_reconnect_state_changed` 信号通知上层。静态 `build_match_seat_player_ids()` 与 `get_match_role_count_for_mode()` 集中维护“真人可占稳定ID序列”和“大厅人数到规则角色总数”的模式换算（过关斩将真人占偶数座位、角色总数为玩家数两倍），牌桌与开局映射共用该唯一来源。静态 `get_lobby_display_slot_count_for()` 集中维护大厅视觉位置数规则（车轮战2位、自选身份等于规则人数、其余2至3人3位），房主换位校验与大厅界面共用；网关另持有房间级 `custom_identity_enabled` 自选身份开关，随公共快照广播，不支持位置身份的模式（过关斩将）强制规范化为关闭，开局映射在开关开启时按大厅位置直接绑定规则座次。关闭、拒绝或连接失败时先从 `SceneMultiplayer` 卸载旧 peer，再关闭 ENet 套接字，因而可立即使用同一端口再次创建房间。
- `MatchController`：权威状态、动作校验、每观察者快照、选择请求、手动/掉线 AI 托管和表现事件裁剪；收到重连信号后解除离线托管、注销基础 AI 并补发裁剪快照与待决选择请求，在开局与终局时使网关座位预约失效。
- `GameSettings`：将游戏显示/节奏/下一局人数、六项房主开局规则及最长20字符的联机玩家名称、稳定武将形象 ID 持久化到 `user://game_settings.cfg`；不持有或保存 ENet、房间成员、密码或对局状态。
- `OnlineSettingsPanel`：作为主菜单客户区内容页编辑联机名称与武将形象，形象候选自动覆盖数据库全部现有武将牌；不创建网络连接，也不覆盖顶部导航。
- `LanLobbyPanel`：只读显示 `GameSettings.online_player_name`，收集 IPv4、端口、初始总人数、密码与“自选身份”开关（仅创建房间时作为房间初始设置生效），只发出建房、加入和返回意图；成功登记后隐藏。
- `OnlineLobbyPanel`：渲染位置、聊天、房间摘要、房主设置、开始与离开操作，只发出纯数据意图，不直接操作 ENet 或 `GameState`。“对局设置”弹窗含“自选身份”复选框（不支持的模式禁用并取消勾选）；自选身份开启时按 `IdentityRules.get_lobby_slot_identities()` 向每个位置组件传入绑定身份，房间摘要追加“自选身份：开”。
- `OnlineLobbyAvatar`：根据稳定武将 ID 显示由空位同规格边框包裹的148.35×197.8像素原始插画与上方玩家名。插画用圆角 Alpha 遮罩真实裁去四角，再绘制透明中心无阴影边框，并提供空位点击及稳定的房主悬停踢出入口；不复用正式武将牌场景。右上角另含48×22像素身份徽记：自选身份开启时显示该位置绑定身份的中文文案与主题身份语义色（`identity_leader` 等），空位与玩家形象共用同一徽记，空身份时隐藏。
- `MatchTable`：协调主菜单、大厅、网关和控制器，不直接修改 `GameState`。它把“记录”旁的托管按钮转换为标准动作，并仅按快照显示手牌黑色输入遮罩、动态“托管中.”至“托管中...”文字和牌面托管状态。断线自动重连期间经 `InformationBoxLayer.show_notice()` 常显顶部横幅并保留对局界面，重连结束改用默认停留时长展示结果文案，失败清理仍由会话关闭回调统一执行。主动离开未开局房间时会复位 `LanLobbyPanel` 的会话标记与建房/加入按钮，再隐藏入口，下一次打开可直接再次创建房间。
