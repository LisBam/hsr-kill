# 网络通信

## 当前范围

网络模块只提供底层通信封装和状态同步结构，不实现房间大厅、账号、匹配、断线重连、主机迁移、反作弊或复杂帧同步业务。该边界符合当前“预留联机接口”的开发范围。

## 通信模式

`NetworkGateway.Mode` 包含：

- `OFFLINE`：本地回环，发送动作后立即触发接收信号。
- `LAN`：局域网分支，封包通过 `packet_ready_for_transport` 交给未来 ENet/WebSocket 适配器。
- `REMOTE`：远程联机分支，使用相同封包结构交给远程传输适配器。

切换 LAN 或 REMOTE 只改变网关状态，不会自动连接服务器。
局内日志展开暂停只适用于 `OFFLINE`：本地牌桌可暂停 SceneTree 并在收起日志时恢复。LAN 与 REMOTE 展开日志时继续运行，客户端不得用本地界面暂停权威远程对局。

## 封包结构

```json
{
  "protocol_version": 2,
  "message_type": "command | snapshot | choice_request | choice_response",
  "transport_mode": "offline | lan | remote",
  "sequence": 1,
  "payload": {}
}
```

`command` 负载为 `PlayerAction.to_dict()`；`snapshot` 负载为按观察者裁剪后的 `GameState.to_dict()`。所有负载只允许字符串、数字、布尔、数组和字典，禁止节点引用与回调。选将使用 `action_type=select_character`，武将稳定 ID 存放在 `payload.character_id`；服务仍会校验阶段、玩家和候选列表。

协议版本2统一使用 `leader` 身份值，并在选将快照中使用 `leader_player_id` 与 `leader_character_id`。版本1的 `lord`、`lord_player_id` 和 `lord_character_id` 不再接受；旧客户端或历史封包必须由外部适配器显式迁移，不能与版本2静默混用。

`GameState.public_card_choice_display` 属于全体观察者可见的公共快照，不按当前选择者裁剪。五谷丰登使用该字段同步 `kind`、标题、提示、当前操作玩家 ID、最初固定牌位、公开牌面快照和领取者玩家 ID；客户端自行从公开玩家快照解析领取者武将名。私有 `current_choice_request.card_ids` 仍只发给实际选择者，旁观客户端只能显示公共牌位，不能据此提交其他玩家的选择。

`GameState.simultaneous_response_display` 同样属于全体观察者可见的公共快照，用于【无懈可击】同时询问。该字段只同步 `kind`、轮次 ID、原锦囊 ID、当前目标 ID 和全部存活 `responder_ids`，不包含候选 UID、候选数量或是否持有无懈。每名实际拥有合法候选的玩家分别收到自己的 `choice_request`；权威端按合法 `choice_response` 到达顺序接受首个响应，并立即关闭同轮其他请求。迟到响应继续按失效请求拒绝，不能翻转已经进入下一轮的链状态。

选将阶段的候选列表属于玩家私有信息，只能进入对应观察者的选将快照。领袖确认的武将立即公开；非领袖只公开确认状态，具体武将 ID 必须等所有玩家完成后才随 `PlayerState.character_id` 同时公开。网络适配层不得广播完整候选映射或未公开选择。

响应、弃牌、区域选牌和技能选目标优先使用 `ChoiceRequest/ChoiceResponse`。请求负载包含 `request_id`、`event_id`、`actor_id`、`choice_type`、牌/目标/按钮候选、各维度选择数量、强制/取消规则和活动上下文；`card_target` 可在活动上下文中携带可序列化的牌到目标映射。响应负载包含同一请求/事件 ID、`confirmed`、实体牌 UID、目标 ID、按钮 ID、控制项、客户端序号和 source；当前已接入的卡牌与技能选择完整消费牌和目标数组，按钮与控制项字段作为后续对应界面的协议预留。现有 `action_type=choose_cards` 仍作为离线桌面兼容封装，权威端会完整保留牌与目标数组并按同一校验路径处理。未注册 AI 的远程角色会保持请求等待状态，权威端不得根据其是否持牌直接替其响应；候选快照必须按观察者裁剪，不可见手牌只能发送牌背语义。

远程请求由 `NetworkGateway.choice_request_received` 和 `choice_response_received` 承载。请求 ID 只在当前事件仍为 PENDING、响应者匹配、候选仍存在且数量满足时有效；对局结束、事件取消/中立化或断线托管会释放对应 `PauseToken`，迟到响应直接拒绝，不得覆盖权威状态。

## 推荐同步方案

采用权威房主或服务器模式：客户端只发送动作，权威端校验并结算，随后广播递增 `action_sequence` 的状态快照或事件增量。客户端不得上传完整状态覆盖服务器。私有快照应按接收者分别生成，防止其他玩家手牌和身份泄漏。

后续业务层至少应实现：

- 权威端在每局开始前随机分配房间成员座次，分配完成后再把本局玩家 ID 与稳定座次绑定；客户端不得自行把本地成员固定为一号位。
- 客户端动作序号去重。
- 权威动作序号缺口检测与快照补发。
- 对局随机种子和牌堆顺序只保存在权威端。
- 重连时发送完整裁剪快照。
- 超时托管时把玩家控制权交给 `AICoordinator`。
