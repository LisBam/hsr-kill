# 无名杀运行逻辑重构分析

## 一、分析目标

本文档记录本地无名杀源码、当前 Godot 规则层与交互层的对照分析，目标是为后续重构提供统一、长期有效的架构依据，使项目逐步具备与无名杀一致的操作逻辑、游戏流程和事件运行逻辑。

当前工程已经能够运行标准身份局基础流程，但其核心仍属于“同步控制器 + 自动响应 + 直接状态修改”模型。无名杀的核心则是“事件树 + 可暂停选择 + 触发器队列 + 嵌套结算”模型。因此，后续重构重点应放在事件运行时，而不是继续向 `MatchController` 添加卡牌和技能分支。

## 二、总体结论

当前工程与无名杀的主要差异如下：

- 无名杀使用 `GameEvent` 表达阶段、出牌、响应、伤害、濒死、死亡和玩家选择，当前工程主要使用同步函数表达这些过程。
- 无名杀允许任意规则事件暂停并等待本地玩家、AI 或网络玩家返回选择结果，当前工程仅在出牌阶段接收少量高层 `PlayerAction`。
- 无名杀的技能触发会按时机、角色座次、技能优先级和 `firstDo/lastDo` 规则排序，当前 `RuleEventBus` 只按全局优先级同步广播。
- 无名杀把使用牌拆分为声明、逐目标触发、逐目标效果、后续结算和区域移动等多个事件，当前工程直接调用 `CardEffectResolver.resolve()` 完成大部分流程。
- 当前工程的数据层、稳定实体牌 UID、状态快照、规则服务和效果执行器可以保留，但 `MatchController` 应逐步退化为协调器。

## 三、无名杀启动流程

无名杀身份局的核心启动链如下：

```text
身份模式 start
  -> 准备玩家与牌堆
  -> chooseCharacter
  -> gameStart 触发
  -> gameDraw
  -> phaseLoop
  -> 玩家 phase
  -> 下一个存活玩家
```

身份模式入口位于 [`mode/identity.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/mode/identity.js)。选将结束后触发 `gameStart`，随后为全部玩家发放起始手牌，再创建永久循环的 `phaseLoop` 事件。

当前工程的 `MatchController.start_match()` 已经实现相近的宏观顺序：

```text
创建状态
  -> 创建玩家与身份
  -> 创建并洗牌
  -> 进入选将
  -> 应用武将
  -> 发放4张起始手牌
  -> 主公开始首回合
```

相关实现见 [`match_controller.gd`](../scripts/core/match_controller.gd)。该部分可以保留业务规则，但应在后续迁移到标准事件调度器中。

## 四、GameEvent 事件运行时

无名杀的核心对象是 `GameEvent`。阶段、使用牌、响应、伤害和玩家选择都被表示为事件，而不是仅依靠阶段字符串或同步函数。

一个事件主要包含以下信息：

- `name`：事件稳定名称。
- `parent`：父事件，用于形成嵌套结算链。
- `next`：当前事件执行期间插入的子事件队列。
- `after`：当前事件主体完成后执行的后置事件队列。
- `content`：事件具体执行内容。
- `result`：子事件或玩家选择产生的结果。
- `step`：分步事件当前执行位置。
- `finished`：事件是否已经结束。
- `player/source/target`：事件涉及的角色。
- `card/cards`：事件涉及的虚拟牌与实体材料牌。

核心实现见 [`gameEvent.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/gameEvent.js)。

事件提供以下关键控制方法：

- `finish()`：结束事件主体，但仍允许处理必要的结束触发和后置队列。
- `cancel()`：取消事件并触发对应取消时机。
- `goto(step)`：跳转到指定步骤。
- `redo()`：重新执行当前步骤。
- `insert()`：向当前事件插入子事件。
- `insertAfter()`：向当前事件插入后置事件。
- `trigger()`：创建并安排规则触发事件。

事件执行过程可以抽象为：

```text
start
  -> Before 触发
  -> Begin 触发
  -> 执行 content 当前步骤
  -> 等待 next 子事件全部完成
  -> End / Omitted / After 触发
  -> 执行 after 队列
  -> 完成
```

`game.createEvent()` 只负责创建事件并挂入当前事件的 `next` 队列，不直接执行效果。根事件由 `game.loop()` 启动，子事件由父事件的 `waitNext()` 依次执行。相关入口见 [`game/index.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/game/index.js)。

### 分步内容编译

无名杀旧式规则大量使用以下写法：

```javascript
"step 0";
// 创建子事件或等待玩家操作
"step 1";
// 读取 result 并继续处理
```

`StepCompiler` 会把这些步骤编译为独立内容单元，使事件能够在暂停、子事件或网络响应结束后从正确步骤继续执行。相关实现见 [`StepCompiler.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/GameEvent/compilers/StepCompiler.js)。

Godot 重构不需要复制 JavaScript 字符串步骤语法，但必须保留同等能力：事件状态、步骤游标、子事件等待、恢复执行和结果传递。

## 五、回合与阶段流程

无名杀完整回合不只是六个阶段字符串，而是一条可触发、可插入、可取消和可跳过的事件链：

```text
phaseBefore
  -> phaseBeforeStart
  -> phaseBeforeEnd
  -> 翻面与跳过检查
  -> 更新当前回合角色
  -> phaseBeginStart
  -> phaseBegin
  -> phaseZhunbei
  -> phaseJudge
  -> phaseDraw
  -> phaseUse
  -> phaseDiscard
  -> phaseJieshu
  -> phaseEnd
  -> phaseAfter
```

阶段实现集中在 [`content.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/content.js)。

阶段流程还会维护：

- 全局回合数和轮数。
- 每名玩家的回合历史。
- 使用牌、响应、伤害、跳过阶段和发动技能记录。
- 当前回合角色。
- 本轮开始角色。
- 角色翻面导致的整回合跳过。
- 死亡或离场角色的阶段终止和回合转交。

### 出牌阶段

`phaseUse` 会持续创建 `chooseToUse` 事件：

```text
创建 chooseToUse
  -> 玩家使用牌或发动技能
  -> 返回 result.bool = true
  -> 再次创建 chooseToUse
  -> 玩家取消或点击结束
  -> 返回 result.bool = false
  -> 结束出牌阶段
```

当前工程虽然允许连续提交 `use_card`，但没有显式的 `chooseToUse` 事件上下文，因而无法在技能、响应、联机和回放中准确恢复出牌状态。

### 弃牌阶段

无名杀在弃牌阶段创建真实的 `chooseToDiscard` 事件，由玩家、AI 或网络端选择需要弃置的牌。当前工程会自动从手牌末尾弃牌，操作表现和规则扩展能力均不等价。

## 六、玩家操作与选择逻辑

无名杀的 UI 不直接调用“使用卡牌”“造成伤害”等规则函数，而是操作当前事件的临时选择状态。

主要选择事件包括：

- `chooseToUse`
- `chooseToRespond`
- `chooseCard`
- `chooseTarget`
- `chooseButton`
- `chooseControl`
- `chooseBool`
- `chooseToDiscard`

`game.check()` 根据当前事件的以下字段计算合法选项：

- `filterCard`
- `filterTarget`
- `filterButton`
- `selectCard`
- `selectTarget`
- `selectButton`
- `forced`
- `filterOk`

选择校验实现见 [`check.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/game/check.js)。

用户点击卡牌、目标或按钮时，只会更新当前选择集合：

```text
ui.selected.cards
ui.selected.targets
ui.selected.buttons
```

随后重新执行 `game.check()`，即时刷新合法卡牌、合法目标和确认按钮。点击实现见 [`ui/click/index.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/ui/click/index.js)。

确认后才写入事件结果：

```text
event.result = {
  cards,
  targets,
  buttons,
  bool: true
}
```

随后关闭选择界面并调用 `game.resume()`，恢复被暂停的事件。

完整操作模型为：

```text
事件创建选择请求
  -> 游戏暂停
  -> UI / AI / 网络提交选择结果
  -> 写入 event.result
  -> 恢复事件
  -> 继续后续步骤
```

当前 [`player_action.gd`](../scripts/data/player_action.gd) 只有少量高层动作，无法表达响应、弃牌、选择按钮、发动技能、选择控制项和同优先级技能排序等结果。

## 七、本地、AI 与网络的统一操作入口

无名杀对同一个选择事件采用三种输入来源：

- 本地玩家：显示界面并暂停事件。
- 在线玩家：把事件名称、参数和设置发送到远端，等待远端结果。
- AI：在同一个事件中执行合法性检查和启发式选择。

三种来源最终都写入相同的 `event.result`，之后继续同一条规则链。因此，AI 和网络并不是另一套规则实现。

联网选择时，`GameEvent.send()` 会在远端重建选择事件，本地权威端调用 `player.wait()` 并暂停。`player.unwait()` 收齐所需结果后写入当前事件并恢复执行。

当前 `NetworkGateway` 已具备动作封包入口，但还没有事件请求、请求 ID、等待结果、超时托管和断线恢复等业务能力。

## 八、卡牌使用流水线

无名杀使用一张牌不是直接执行最终效果，而是一条多级事件流水线：

```text
实体牌移入 ordering/处理区
  -> useCard0
  -> useCard1
  -> yingbian
  -> useCard2
  -> useCard
  -> 逐目标 useCardToPlayer
  -> 逐目标 useCardToTarget
  -> useCardToPlayered
  -> useCardToTargeted
  -> 卡牌 contentBefore
  -> 每个目标执行卡牌 content
  -> contentAfter
  -> effectCount 重复检查
  -> 弃牌、装备区或判定区移动
```

核心实现位于 [`content.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/content.js) 的 `useCard` 内容。

该流程保证技能能够在以下时机介入：

- 卡牌刚被声明时。
- 指定目标前后。
- 单个目标即将结算时。
- 单个目标结算完成时。
- 卡牌所有目标结算完成后。
- 实体牌离开处理区前后。

当前 [`match_controller.gd`](../scripts/core/match_controller.gd) 中的 `_execute_card_use()` 会直接把卡牌移入 `processing_area`，随后调用 [`card_effect_resolver.gd`](../scripts/core/card_effect_resolver.gd) 的 `resolve()`。虽然效果执行器职责已经分离，但仍缺少：

- 每个目标独立的子事件。
- `useCardTo...` 系列稳定触发时机。
- `contentBefore` 与 `contentAfter`。
- 卡牌被取消、无效或排除后的状态表达。
- 虚拟牌和实体材料牌的分离。
- `ordering` 区域。
- 卡牌结算中途产生的玩家选择。

## 九、触发器排序

无名杀触发规则事件时，会确定一个起始角色，并按座次遍历所有角色。技能触发顺序同时受到以下因素影响：

- 事件角色类型：`player`、`source`、`target`、`global`。
- 当前回合或事件起始角色。
- 角色座次顺序。
- 技能优先级。
- `firstDo` 和 `lastDo` 特殊分组。
- 同优先级技能的玩家选择。
- 技能是否仍满足实时触发条件。

触发器安排逻辑位于 [`gameEvent.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/gameEvent.js) 的 `trigger()`，实际执行位于 [`content.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/content.js) 的 `arrangeTrigger`。

触发器还支持：

- `untrigger()` 终止后续触发。
- `filterStop` 动态停止触发链。
- 触发技能插入新的子事件。
- 技能在执行前重新验证触发条件。
- 控制死亡角色或离场角色是否仍能执行事件。

当前 [`rule_event_bus.gd`](../scripts/core/rule_event_bus.gd) 只按全局优先级同步调用回调，不能表达座次顺序、同优先级选择和嵌套触发。

## 十、伤害流程

无名杀伤害本身也是独立事件：

```text
damageBegin1
  -> damageBegin2
  -> damageBegin3
  -> damageBegin4
  -> 防具与伤害修正
  -> 扣减体力
  -> damageZero 或 damage
  -> dying
  -> damageSource
```

伤害实现位于 [`content.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/content.js) 的 `damage` 内容。

多级 `damageBegin` 时机允许不同类型技能按稳定顺序修改伤害来源、属性、数值、是否防止以及是否取消。当前工程只有 `damage_before` 和 `damage_after`，不足以直接承载无名杀技能库。

## 十一、濒死、救援与死亡

角色体力不大于0时，无名杀会创建 `dying` 事件，而不是直接自动消耗一张桃。

```text
进入 dying
  -> 触发 dying 时机
  -> 创建 _save 救援事件
  -> 按行动顺序询问角色
  -> chooseToUse 桃或合法救援技能
  -> 若仍未脱离濒死则继续询问
  -> 无人救援时创建 die 事件
```

濒死和死亡实现位于 [`content.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/noname/library/element/content.js) 的 `dying` 与 `die` 内容。

死亡后还会执行：

```text
标记死亡并调整存活座次链
  -> 亮出身份
  -> die 触发
  -> 清理技能和标记
  -> 弃置手牌、装备和判定牌
  -> dieAfter
  -> 身份模式 checkResult
  -> game.over
```

身份胜负判断位于 [`mode/identity.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/mode/identity.js) 的 `checkResult()`。

当前工程已经实现伤害、连环、濒死、死亡奖惩和胜负终止等基础规则，但救援、无懈可击、闪、杀等响应主要使用自动策略，无法形成真实交互窗口。

## 十二、源码快照、版本与证据边界

本次对照以仓库内的无名杀源码快照为唯一行为依据，不以界面名称或网络文章的概括为依据。源码目录为：

```text
无名杀参考代码/无名杀诗笺版Windows64位/resources/app/
```

版本需要区分两个层次：

- [`game/update.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/game/update.js) 与 [`game/asset.js`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/game/asset.js) 标示游戏规则源码为 `v1.10.16`。
- [`package.json`](../无名杀参考代码/无名杀诗笺版Windows64位/resources/app/package.json) 的 `1.9.0` 是 Electron 包装层版本，不能当作规则版本。

本文的“无名杀行为”均指该 `v1.10.16` 快照在标准身份模式下的语义。十周年 UI 扩展只用于确认交互显示和额外技能提示，不作为规则权威源；Godot 复刻应优先对照 `noname/library`、`noname/game`、`mode/identity.js`、`card/standard.js` 与角色技能文件。

证据优先级固定为：

1. 规则入口与事件运行时：`init/onload.js`、`game/index.js`、`library/element/gameEvent.js`、`library/element/GameEvent/*`。
2. 通用规则内容：`library/element/content.js`、`library/index.js`、`library/element/player.js`。
3. 模式规则：`mode/identity.js`。
4. 卡牌与技能定义：`card/*.js`、`character/*/skill.js`。
5. UI 扩展：只补充显示和交互时机，不覆盖前四级规则。

后续实现若与当前项目设计发生冲突，必须在文档中标记“源码等价行为”和“项目有意差异”，不能把简化流程描述成已经复刻。

## 十三、启动根事件与身份模式精确流程

源码不是在 `identity.start` 函数返回后直接调用下一个同步函数。`init/onload.js` 在扩展启动完成后先创建竞技场，再创建根 `game` 事件，将 `lib.init.start` 作为根内容，最后进入 `game.loop()`。因此 Godot 的启动器应有一个稳定的根事件，所有后续流程都挂在它下面：

```text
加载库与扩展
  -> 创建竞技场/玩家节点
  -> 创建 RootGameEvent
  -> RootGameEvent 调用 mode.start
  -> identity.start 准备玩家、牌堆和模式变量
  -> chooseCharacter / chooseCharacterOL
  -> gameStart 触发器
  -> gameDraw
  -> phaseLoop
```

`mode/identity.js` 的标准离线选将并不是“主公先选、其余角色永远自动获得固定候选”的单一路径：主公、非主公的候选生成、玩家选择和 AI 赋值由 `chooseCharacter` 内的身份与座次分支共同决定；联机使用 `chooseCharacterOL`，还要同步候选、身份隐藏和远端结果。当前项目“主公先选、其他玩家同时自动赋值”的流程可以作为项目玩法，但必须标记为**尚未达到标准身份局完全等价**。

`gameStart` 触发后才进入 `gameDraw`；身份模式的起始手牌数量由模式和配置决定，当前项目固定发 4 张只能视为当前玩法参数，不能写成无名杀通用规则。`phaseLoop` 是可重复的长生命周期事件，内部创建每名玩家的 `phase`，而不是简单的 `while` 循环；它在玩家死亡、离场、回合插入和胜负结束后都要重新检查下一位角色。

## 十四、事件终止、恢复与暂停通道的精确定义

### 事件终止三态

`GameEvent` 的三个操作语义不同，Godot 必须保留三态而不能用一个 `cancelled` 布尔值替代：

| 操作 | 源码语义 | 子事件/触发影响 | Godot 契约 |
|---|---|---|---|
| `finish()` | 正常结束当前内容 | 仍可进入结束阶段及 `after` 队列 | `FINISHED`，完成收尾但不伪造取消时机 |
| `cancel()` | 取消当前事件 | `untrigger()`，可触发 `<name>Cancelled`，阶段标记 skipped，然后结束 | `CANCELLED`，保留取消原因与触发链 |
| `neutralize()` | 使事件效果中立化 | 标记 `neutralized`，触发 `eventNeutralized`，可 `unneutralize()`，再结束 | `NEUTRALIZED`，效果无效但仍可记录“事件发生过” |

例如无懈可击通常不是简单删除原 `useCard` 事件，而是让对应卡牌/目标效果变成 neutralized；技能取消则使用 cancel 语义。回放和触发器必须能区分三者。

### 事件栈与当前事件

`GameEventManager` 维护 root、event stack 和 temporary event。当前事件只能来自临时事件、栈顶事件或根事件，不能由任意代码直接替换。`start()` 将事件压栈，执行结束后出栈；`waitNext()` 先等待全部子事件和暂停通道，再执行 `next[0]`，子事件结果复制回父事件的 `result`。

Godot 必须禁止“全局 current_event = 新事件”的写法，统一使用 `scheduler.create_child(parent_id)` 和 `scheduler.push(event_id)`，否则嵌套触发、旧响应恢复和回放顺序都会失真。

### 暂停不是一个布尔值

源码 `PauseManager` 维护相互独立的 `pause`、`pause2`、`pause3`、`over`、`delay` 等 Deferred 通道；`waitPause()` 只有在所有激活通道都完成后才返回。动画延迟、远端等待、UI 选择和结算结束可能同时存在，单一 `paused = true/false` 无法表达这种组合。

Godot 应实现带 token 的暂停原因：

```text
PauseToken { token_id, channel, owner_event_id, reason, resolved }
PauseRegistry.active_tokens
```

事件恢复条件为“本事件没有未完成的子事件，且 `PauseRegistry` 中与本事件或全局结算相关的 token 全部 resolved”。网络断线托管、动画跳过和对局结束必须分别释放自己的 token，不能互相误解为恢复全部事件。

## 十五、选择事件的真实状态机与备份恢复

`chooseToUse`、`chooseToRespond` 并非一次函数调用，而是可循环改变上下文的事件：

```text
准备基础过滤器
  -> onChooseToUse/onChooseToRespond 技能预处理
  -> game.check 计算当前合法卡牌、目标和按钮
  -> 本地暂停 / 远端 send / AI 选择
  -> 取消、失败或成功
  -> 技能 chooseButton / chooseControl 子选择
  -> backup(skill) 替换当前选择上下文
  -> 重新 check 并继续
  -> useResult 或 respond 子事件
```

技能按钮选择成功后，源码会临时生成 `<skill>_backup` 技能，调用 `event.backup()` 替换 `filterCard`、`filterTarget`、选择数量、视为牌和提示；用户取消或 AI 失败时通过 `event.restore()` 恢复基础上下文，并把失败技能加入 `_aiexclude` 后 `redo()`。因此“取消技能选择”不一定结束整个 `chooseToUse`，而可能只是回到基础选择窗口。

Godot 的 `ChoiceRequest` 必须包含 `base_context` 与 `active_context` 两份快照，并支持：

- `backup_context(skill_id, generated_card, filters, select_ranges)`；
- `restore_context()`；
- `redo_current_step()`；
- `exclude_candidate(candidate_id, reason)`。

网络端只传输可序列化的候选和结果，不传输脚本闭包；权威端根据技能 ID 和选择参数重新构建 `active_context`。

## 十六、过滤器与修正器：两条不能混淆的规则管线

无名杀的 `game.checkMod()` 是独立于触发器的查询管线：它收集拥有 `mod` 的技能，按优先级排序，把前一项返回值传给下一项。该过程可能修改数值、范围或布尔值，但不是触发事件，也不产生 `Begin/End` 时机。

### 牌与目标合法性顺序

标准 `filterCard` 的最小等价顺序为：

```text
cardAiIncluded
  -> cardEnabled / cardEnabled2
  -> cardUsable / cardUsable2
  -> selectTarget 修正
  -> 若必须指定目标，至少存在一个合法目标
```

标准 `filterTarget` 再执行：

```text
target.isIn
  -> playerEnabled 修正
  -> targetEnabled 修正
  -> card.filterTarget
  -> targetInRange 修正与距离计算
```

响应牌还要先经过 `cardRespondable`，并检查来源角色的 `norespond`、当前事件类型和无懈相关修正。`targetEnabled2/3` 是特殊技能查询，不能和普通 `targetEnabled` 混为一谈。

Godot 应提供纯查询接口 `RuleQuery.card_enabled`、`card_respondable`、`card_usable`、`target_enabled`、`target_in_range`，以及单独的 `RuleModifierPipeline`。查询接口不得直接移动牌、消耗次数或写入选择状态；消耗与统计由确认后的事件步骤完成。

### 距离与座次

`get.distance` 以 `nextSeat/previousSeat` 的循环座次为基础，排除离场和无距离角色，应用全局、攻击范围、装备和方向修正，最终距离至少为 1；存在 `raw`、`absolute`、`left`、`right` 等不同口径。当前项目仅按存活数组计算距离，缺少死亡座次链和方向修正，不能声称已等价。

## 十七、卡牌使用、响应与无懈可击精确顺序

### `useCard` 顺序修正

源码的稳定顺序如下，之前文档把两个 `...ed` 时机放到了卡牌主体之后，现更正为主体之前：

```text
实体材料牌 lose -> ordering
  -> useCard0
  -> useCard1
  -> yingbian
  -> useCard2
  -> useCard
  -> 按行动顺序逐目标 useCardToPlayer
  -> 逐目标 useCardToTarget
  -> 逐目标 useCardToPlayered
  -> 逐目标 useCardToTargeted
  -> contentBefore
  -> 每个目标的卡牌 content
  -> contentAfter
  -> effectCount 重复结算
  -> 清理取消回调/处理区回收
```

其中 `useCardToPlayered` 和 `useCardToTargeted` 的“ed”并不表示卡牌 content 已经完成，而表示对应目标触发阶段的后半段已经到达；技能可以在这两个时机修改目标、取消目标或准备无懈。目标在进入每个子事件前必须重新检查 `isIn`、`excluded`、`directHit`、`customArgs` 和死亡/离场状态。

### `respond` 与响应牌移动

`chooseToRespond` 成功后才创建 `respond` 事件。`respond` 会记录响应历史，调用实体材料牌持有者的 `lose(..., ui.ordering)`，触发 `respond`，然后由 ordering 相关后置事件处理回收。响应不是“把牌从手牌数组删除并写一个 bool”，它与使用牌一样必须保留材料牌、来源、`respondTo` 和后续触发信息。

### `_wuxie` 的交替状态

标准牌包中的 `_wuxie` 是一个强制、静默、全局加载技能，监听 `useCardToBegin` 与 `phaseJudge`。它的核心不是“发现无懈就把原事件取消”，而是：

1. 判断当前牌是否可无懈、目标是否被 `directHit` 排除、来源/目标是否有 `noWuxie` 或 `wuxieEnabled/Respondable` 修正。
2. 按当前回合座次收集拥有无懈能力的角色。
3. 为每名候选角色创建 `type = wuxie` 的 `chooseToUse` 请求，只允许使用或视为使用【无懈可击】。
4. 首个成功结果成为 `wuxieresult`；若使用的是另一张无懈，则沿父事件向上翻转 `state`，形成“无懈无懈”的交替链。
5. 成功响应通过 `useResult` 进入普通 `useCard`，并以 `respondTo = [原使用者, 原牌]` 关联原事件。
6. 没有任何成功响应时，原卡牌继续；成功结果则由原事件读取 `wuxieresult`/`wuxieresult2` 决定是否中立化或继续。

因此 Godot 需要 `WuxieChainState { root_event_id, source_event_id, state: 1/-1, responded_by, response_result }`，不能用单个 `card.cancelled` 表达无懈。无懈候选的合法性查询还要独立于普通卡牌目标查询，支持判定牌、锦囊牌、多目标牌、`nowuxie`、`directHit` 和技能修正。

## 十八、牌堆、处理区与卡牌信息可见性

### 牌堆耗尽与洗牌

`get.cards()` 在牌堆为空时先调用 `game.washCard()`：把弃牌堆洗回牌堆，清理临时已知者和会消失的牌，并触发洗牌相关事件；若洗牌后仍无牌，源码直接 `game.over("平局")`。因此“牌堆为空返回空数组”不是完整规则，Godot 必须把牌堆耗尽作为可结算的平局结束原因。

### 统一移动事件

牌的移动至少分为 `cardsGotoOrdering`、`cardsGotoPile`、`cardsGotoSpecial`、`lose`、`gain`、`equip`、`addJudge`、`cardsDiscard` 等事件。`lose` 会记录原区域 `h/e/j/s/x`、虚拟牌映射、获得标签、移动历史和知识清理；与使用牌或响应关联时，会在父事件 `after` 队列插入 `orderingDiscard`，而不是立即把处理区牌塞进弃牌堆。

Godot 应把区域定义为枚举并通过唯一 `CardMoveEvent` 写入：

```text
DECK / HAND / EQUIP / JUDGE / PROCESSING / SPECIAL / DISCARD / VOID
```

每次移动必须携带 `move_id`、`event_id`、`from_zone`、`to_zone`、`card_ids`、`visible_to`、`reason`、`related_event_id`。任何卡牌效果不得直接操作区域数组。

### 实体牌、虚拟牌与知识

实体 `Card` 具有稳定 `cardid`、花色、点数、名称、增益标签和已知者集合；`VCard` 是逻辑牌，可拥有 `name/suit/number/nature/storage` 和多个实体材料牌 `cards`。虚拟牌不能被压扁成没有来源的普通卡牌，否则无法正确处理视为牌、无懈、装备和移动历史。

知识状态至少需要：

- `known_to`：哪些角色知道实体牌的完整牌面；
- `shown`：公开展示是否已发生；
- `private_owner`：仅持有者可见的手牌信息；
- 洗牌时清理弃牌中临时知识；
- 牌移动时按 `visible`、`give`、`showCards` 等原因更新可见性。

普通客户端只能收到自己有权知道的牌面；回放若需要全信息，应保存独立的权威事件日志，而不是把完整状态广播给客户端。

## 十九、伤害、濒死与死亡的补充契约

伤害事件至少要保留 `damageBegin1..4`、数值/属性/来源修正、`damageZero`、`damage`、`dying`、`damageSource` 的独立步骤。`changeHp` 不是简单赋值：它要产生体力变化历史，并在伤害为 0、被防止和实际扣血之间保持可查询结果。

`dying` 事件会登记濒死队列，并从当前阶段、伤害来源、濒死角色、己方控制角色和首位玩家中确定救援起点，反复创建 `_save` 选择事件；救援结果必须写回同一个濒死事件，直到体力恢复或创建 `die`。角色死亡后才从 `game.players` 移到 `game.dead`，清理临时技能、标记、手牌/装备/判定牌，并执行 `die`、`dieAfter` 与模式 `checkResult`。

Godot 需要把“体力变为 0”“进入濒死”“死亡确认”拆成三个状态，而不是在伤害函数中一次完成；否则救援技能和死亡触发无法插入。

## 二十一、现有架构中应保留的部分

以下模块符合后续事件化重构方向，应保留并逐步接入新运行时：

- `GameDatabase`：稳定静态内容索引。
- `CardInstance`：实体牌 UID 与区域信息。
- `PlayerState`：玩家权威状态。
- `GameState`：对局状态根对象。
- `CardRuleService`：只读合法性判断。
- `CardEffectResolver`：卡牌具体效果组件，但需要由标准卡牌事件调用。
- `IdentityRules`：身份分配、胜负与死亡奖惩规则。
- `CharacterSelectionService`：选将数据状态机。
- `PlayerAction`：可以继续承担高层命令，但不能单独承担全部选择结果。
- UI 快照边界：继续禁止界面直接修改权威状态。
- 网络权威端校验原则：客户端只提交动作或选择结果。

## 二十二、目标架构

```text
EventScheduler
  |- GameEvent
  |- ChoiceRequest / ChoiceResponse
  |- TriggerManager
  |- PhaseEvent
  |- CardUseEvent
  |- DamageEvent
  |- DyingEvent
  `- DeathEvent

UI / AI / Network
  `- 只提交 ChoiceResponse 或标准命令
```

### GameEvent

建议提供：

- 稳定事件 ID。
- 事件名称和类型。
- 父事件 ID。
- `next` 和 `after` 队列。
- 当前步骤和执行状态。
- 事件结果。
- 来源、玩家、目标和卡牌上下文。
- `finish`、`cancel`、`goto`、`redo`、`insert`、`insert_after`。
- 是否允许死亡或离场角色继续执行。

### EventScheduler

建议负责：

- 根事件和当前事件栈。
- 子事件顺序执行。
- 事件暂停和恢复。
- 等待选择请求。
- 选择结果写回。
- 对局结束后的统一中断。
- 防止旧请求恢复已经失效的事件。

- `request_id`
- `event_id`

- `button_ids`
- `control_ids`
- `min_count`
- `max_count`
- `forced`
- `can_cancel`

建议至少包含：

- `target_ids`

### TriggerManager

## 二十三、状态结构补充建议

为支持无名杀式运行逻辑，`GameState` 后续需要补充：

- 离场状态与死亡后可触发状态。
- 牌面已知者信息。
- 虚拟牌材料或特殊区域引用。

事件栈本身不应完整广播给普通客户端，但权威端、回放和调试器需要能够记录事件摘要。

## 二十四、重构顺序

### 第一阶段：事件运行时

实现 `GameEvent` 与 `EventScheduler`，优先完成：

- 父子事件。
- `next` 与 `after`。
- 顺序执行。
- `goto` 与 `redo`。
- `finish` 与 `cancel`。
- 结果向父事件传递。
- 对局结束后中止后续结算。

### 第二阶段：通用选择协议

实现 `ChoiceRequest` 与 `ChoiceResponse`：

- 本地玩家提交响应。
- AI 消费相同请求并返回响应。
- 网络端接收裁剪后的请求并返回响应。
- 请求 ID 防止旧响应污染新事件。
- 支持确认、取消和超时托管。

### 第三阶段：触发器系统

实现：

- 事件名注册。
- 角色类型匹配。
- 座次排序。
- 技能优先级。
- `firstDo/lastDo`。
- 同优先级选择。
- 事件取消和终止。

### 第四阶段：回合流程事件化

把当前 `_start_turn()` 拆为：

- `PhaseLoopEvent`
- `TurnEvent`
- 六个阶段事件
- 回合开始和结束事件
- 阶段跳过和翻面事件
- 当前角色死亡后的回合转交

### 第五阶段：卡牌使用事件化

实现标准 `CardUseEvent`：

- 声明使用。
- 实体牌移动到处理区。
- 卡牌前置触发。
- 逐目标触发。
- 逐目标效果。
- 后置触发。
- 最终区域移动。

随后让 `CardEffectResolver` 只处理单个效果步骤，不负责整张牌的完整生命周期。

### 第六阶段：伤害与死亡事件化

依次迁移：

- 回复事件。
- 伤害事件。
- 失去体力事件。
- 濒死事件。
- 救援选择事件。
- 死亡事件。
- 死亡奖惩和胜负检查。

### 第七阶段：UI、AI、网络与回放

- UI 根据 `ChoiceRequest` 动态生成卡牌、目标、按钮和控制项选择。
- AI 不再调用专用自动响应函数，而是消费合法选择请求。
- 网络发送事件请求和选择结果。
- 回放记录选择结果、随机结果和事件摘要。

## 二十五、明确不建议的重构方式

以下方式会继续扩大耦合，不应采用：

- 继续在 `MatchController` 中添加卡牌名称分支。
- 为每张牌单独制作一套 UI 选择流程。
- 让 UI 直接调用伤害、摸牌、弃牌或区域移动函数。
- 让 AI 直接修改 `GameState`。
- 只增加更多 `RuleEventBus` 事件名而不引入可暂停事件。
- 让网络客户端上传完整状态覆盖权威端。
- 用动画完成回调代替规则事件状态。
- 把虚拟牌错误表示为没有来源信息的普通实体牌。

## 二十六、验收标准

### 事件运行时

- 子事件必须在父事件继续前完成。
- `after` 事件必须在主体结束后依次执行。
- 暂停事件不能继续推进步骤。
- 旧选择结果不能恢复已经结束或取消的事件。
- 对局结束后不能再执行后续目标、响应、伤害或区域移动。

### 阶段流程

- 准备、判定、摸牌、出牌、弃牌和结束阶段均是独立事件。
- 阶段可以被跳过、插入、取消或重复。
- 出牌阶段会持续等待使用牌，直到玩家明确结束。
- 弃牌阶段由合法选择结果决定弃置内容。
- 当前回合角色死亡后能够在当前事件结算完成时正确转交回合。

### 卡牌流程

- 一张牌可以在声明、指定目标和目标结算时被技能修改。
- 多目标牌按稳定行动顺序逐目标结算。
- 单个目标死亡或失效不会破坏其他目标的合法结算。
- 虚拟牌能够保留全部实体材料牌信息。
- 使用牌结束后实体牌进入正确区域。

### 触发器

- 技能按优先级和座次顺序执行。
- `firstDo` 必须先于普通触发器。
- `lastDo` 必须晚于普通触发器。
- 同优先级技能能够产生真实玩家选择。
- 技能执行前必须重新检查当前状态是否合法。

### 操作协议

- UI、AI 和网络提交相同选择时得到相同规则结果。
- 非当前响应者不能提交选择结果。
- 选择数量、卡牌区域、目标状态和规则限制必须由权威端复核。
- 超时托管必须产生与普通 AI 相同格式的响应。

### 可复现与回归

- 固定随机种子能够复现身份、武将候选和牌堆。
- 选择结果和随机结果可以被回放系统复用。
- 回放不依赖当前 UI 节点存在。
- 无头测试能够验证完整事件顺序。

## 二十七、实施重点

后续第一项实现工作应是事件运行时和选择协议，而不是继续扩充卡牌效果。只有先建立可暂停、可嵌套、可恢复和可排序的事件系统，后续武将技能、装备技能、响应窗口、AI、网络和回放才能共用同一套长期稳定的规则基础。

## 二十九、可执行验收场景

下列场景是复刻无名杀运行逻辑的最小回归集。每个场景都应记录事件树、暂停 token、选择请求、移动事件和最终状态，不能只断言界面文字。

### 场景 1：根事件和阶段循环

固定随机种子启动标准身份局，验证事件链为 `Root -> identity.start -> gameStart -> gameDraw -> phaseLoop -> phase`；根事件结束前不得出现脱离父事件的阶段事件。选将结果、起始手牌和首回合角色必须可从事件日志定位。

### 场景 2：子事件阻塞与 after 队列

在卡牌效果中插入一个需要本地选择的子事件，再插入一个 `after` 移牌事件。验证选择未返回前父事件步骤不推进；子事件完成后结果复制回父事件；主体结束后才执行 `after`。

### 场景 3：技能 backup/restore

进入 `chooseToUse`，选择一个 `chooseButton` 技能，生成备份技能并改变视为牌过滤器；随后取消按钮选择。验证上下文恢复为基础 `filterCard/filterTarget/select`，失败技能只进入本次事件的排除集合，不污染玩家永久技能。

### 场景 4：多目标牌时机顺序

使用一张两目标锦囊，在每个时机写入事件日志。严格断言：`useCard0 -> useCard1 -> yingbian -> useCard2 -> useCard -> ToPlayer -> ToTarget -> ToPlayered -> ToTargeted -> contentBefore -> content -> contentAfter`；某一目标死亡或被排除时，其他目标仍按规则继续。

### 场景 5：无懈交替

让角色 A 使用可无懈锦囊，角色 B 使用无懈，角色 C 再使用无懈。验证 `WuxieChainState.state` 依次为 `1 -> -1 -> 1`，每张实体材料牌各自经过 `respond/useCard` 和 ordering，原卡牌不是被直接删除；设置 `nowuxie/directHit` 后验证候选列表被正确裁剪。

### 场景 6：响应与可见性

让角色 A 只能看到自己的手牌，角色 B 通过公开展示获得其中一张。验证 B 只收到被展示牌的牌面，其他手牌仍为未知占位；牌进入 ordering、弃牌堆和洗牌时，知识集合按源码语义更新。

### 场景 7：牌堆耗尽

构造牌堆与弃牌堆均为空的状态，调用摸牌事件。验证先创建洗牌/尝试事件，确认无法获得牌后产生 `GameEndEvent(reason = DECK_EMPTY_DRAW)`，结果映射为平局，而不是让后续摸牌继续执行。

### 场景 8：濒死救援和死亡

将角色体力降至 0，验证顺序为 `damage -> dying -> _save(choice)* -> die 或恢复 -> dieAfter -> checkResult`。救援选择可以由本地、AI、网络任一来源提交，三者必须写入同一种结果结构；死亡事件完成前不得提前从事件树删除。

### 场景 9：终止语义

分别对同一类事件调用 `finish`、`cancel`、`neutralize`。验证三者的状态、取消触发、`eventNeutralized`、阶段 skipped、after 队列和回放文本均不同；对局结束后所有未解决选择 token 都被标记为终止，不得恢复旧事件。

### 场景 10：联机超时托管

在远端选择请求未返回时制造断线和超时，验证请求 ID 不变、权威端只接受当前请求、托管 AI 返回与普通 AI 相同格式的 `ChoiceResponse`，旧客户端迟到的结果被拒绝且不改变事件状态。

## 三十、重构完成定义

只有同时满足以下条件，才可把“已复刻无名杀运行逻辑”写入项目状态：

- 根事件、事件栈、子事件、after 队列和多通道暂停均有可观察实现。
- 选择事件能由本地、AI、网络共同驱动，并支持 backup/restore、取消、超时和旧响应拒绝。
- 触发器排序与 `checkMod` 查询链分别实现，且都有独立回归测试。
- 使用牌、响应、无懈、伤害、濒死、死亡和移牌均通过事件树结算。
- 实体牌、虚拟牌、材料牌、处理区回收和观察者可见性不会丢失。
- 牌堆耗尽平局、取消、中立化和对局结束中断均有明确终局原因。
- 回放可以只依赖事件/选择/随机/移动日志重建规则结果，不依赖 Godot 场景节点或动画回调。

在达到上述定义前，项目文档应使用“事件化迁移中”“规则部分等价”或“当前玩法差异”等表述，不应使用“已完整复刻”。
